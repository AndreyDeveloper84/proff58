# ТЗ для разработчика 1С: обмен с сайтом «Профессионал»

Документ описывает, что нужно реализовать в 1С 7.7 для обмена с сайтом — простым
языком. Технический контракт «поле в поле» — в [`docs/1c-api-spec.md`](1c-api-spec.md).
Модель статусов заказа — в [`docs/order-lifecycle.md`](order-lifecycle.md).

Направление обмена:

```text
1С -> сайт
```

Сайт не подключается напрямую к базе 1С. 1С сама отправляет HTTP-запросы в API сайта.

## 1. Цели интеграции

Нужно реализовать четыре группы обмена:

1. Обновление остатков (дельта-обменом: снимок → только изменения).
2. Обновление цен (так же — только изменения).
3. Передача новых и изменённых позиций номенклатуры.
4. Обработка заказов: получение новых заказов с сайта, резервирование, изменение статусов.

На текущий момент в коде сайта уже реализованы:

- `GET /api/1c/snapshot/`
- `POST /api/1c/products/import`
- `POST /api/1c/products/update`
- `POST /api/1c/prices/update`
- `POST /api/1c/stocks/update`
- `GET /api/1c/sync/<batch_uid>`

Заказы **реализованы и работают** (#50):

- `GET /api/1c/orders/new` — забор новых заказов;
- `POST /api/1c/orders/confirm` — подтверждение приёма/резерва и движение статуса.

То есть интегрироваться можно по всем направлениям: товары, цены, остатки и заказы.
Финальный контракт по заказам — раздел 15.

## 2. Среды

Тестовый контур:

```text
https://dev.proff58.ru/api/1c/
```

Боевой контур:

```text
https://proff58.ru/api/1c/
```

Сначала вся разработка и приёмка выполняются только на тестовом контуре.

## 3. Авторизация

Каждый запрос должен содержать заголовок:

```http
X-Api-Key: <ТОКЕН>
```

Требования:

- токен для теста и прода разный;
- токен не писать в логи;
- токен не хранить в открытом виде в коде обработки;
- при ответе `403` автоматически не повторять запрос, а показать ошибку настройки.

## 4. Общий формат данных

Все `POST`-запросы передают JSON:

```json
{
  "items": [
    {
      "external_id": "1c-000123"
    }
  ]
}
```

Требования:

- `Content-Type: application/json`;
- кодировка `UTF-8`;
- `items` не должен быть пустым;
- максимум строк в одном пакете: `1000`;
- большие выгрузки отправлять частями.

Числа можно передавать строкой или числом, десятичная запятая тоже допустима:

```json
"5900.00"   5900   "5900,00"
```

Булево: `true`/`false`, либо `1`/`0`, либо `"да"`/`"нет"`.

## 5. Ключ связи товара

Главный ключ связи товара между 1С и сайтом:

```json
"external_id": "1c-000123"
```

Допустимые синонимы:

| Поле | Назначение |
|---|---|
| `external_id` | главный код/GUID товара в 1С |
| `code_1c` | синоним `external_id` |
| `sku` | артикул |
| `article` | синоним `sku` |

Обязательное правило:

```text
external_id должен быть стабильным и уникальным.
```

Артикул может быть неуникальным. Если сайт найдёт несколько товаров по одному
артикулу, строка будет ошибкой конфликта и не обновится.

## 6. Что 1С имеет право менять

1С является источником истины только для:

- кода товара, артикула, исходного названия;
- бренда, если он ещё не заполнен на сайте;
- штрихкода, единицы измерения, исходной группы 1С;
- цены, старой цены, типа цены;
- остатка, резерва, доступного остатка;
- активности товара в 1С.

1С не должна перезаписывать:

- категорию сайта, витринное название, описание;
- SEO, фотографии, характеристики сайта, статус публикации.

## 7. Передача новых позиций

Endpoint:

```http
POST /api/1c/products/import
```

Назначение:

- создать новую позицию на сайте, если её ещё нет;
- обновить базовые 1С-поля существующей позиции;
- передать начальную цену и остаток.

Пример:

```json
{
  "items": [
    {
      "external_id": "1c-000123",
      "sku": "BOSCH-GSB13RE",
      "barcode": "4600000000017",
      "name": "Дрель ударная BOSCH GSB 13 RE",
      "brand": "Bosch",
      "unit": "шт",
      "source_group": "Электроинструмент/Дрели",
      "is_active": true,
      "price": "5900.00",
      "old_price": "6500.00",
      "currency": "RUB",
      "price_type": "retail",
      "stock": "7"
    }
  ]
}
```

Ответ:

```json
{
  "batch_uid": "0f3c1e54-...",
  "status": "accepted",
  "accepted": 1
}
```

Импорт номенклатуры асинхронный. После ответа `202 Accepted` нужно опрашивать статус:

```http
GET /api/1c/sync/<batch_uid>
```

## 8. Обновление существующих позиций

Endpoint:

```http
POST /api/1c/products/update
```

Назначение:

- обновить только уже существующие позиции;
- новые позиции не создавать.

Если товар не найден по `external_id` или `sku`, строка попадёт в `skipped`.
Этот режим нужен для безопасных регулярных обновлений, когда нельзя случайно
наплодить новые карточки.

## 9. Дельта-обмен: снимок позиций (`GET /snapshot/`)

Чтобы не гонять весь прайс/остатки каждый раз, цены и остатки обновляются
**дельтой**: 1С сначала **забирает снимок** актуальных позиций сайта, сравнивает
у себя и шлёт обратно (в `prices/update` / `stocks/update`) **только то, что
изменилось**. Сравнение выполняется на стороне 1С.

Endpoint (метод `GET`, заголовок `X-Api-Key`):

```http
GET /api/1c/snapshot/?limit=1000&offset=0
```

Снимок отдаётся постранично. Параметры:

| Параметр | По умолчанию | Правила |
|---|---|---|
| `limit` | `1000` | целое > 0; больше `1000` обрезается до `1000`; `0`/отрицательное/нечисло → `400` |
| `offset` | `0` | offset-режим (как было): целое ≥ 0; иначе `400` |
| `after_id` / `after_code_1c` | — | **keyset-режим** (быстрее на большом каталоге): курсор по последней позиции |

Предел страницы (`1000`) — это серверная настройка `ONEC_MAX_ITEMS`; запрос
большего `limit` молча обрезается до неё (это не ошибка). При ошибке параметров
ответ — `400` с телом `{ "detail": "<причина>" }`.

Две схемы обхода (выбираете одну):
- **offset** — идти `offset=0,1000,2000…` пока `next_offset ≠ null`. Просто.
- **keyset** (рекомендуется при больших объёмах) — передать `after_id=0` для первой
  страницы, затем брать из ответа `next_after_code_1c`/`next_after_id` и подставлять в
  `after_code_1c`/`after_id`, пока `next_after_id ≠ null`. Не делает дорогой `count`.

Ответ (всегда `200 OK`):

```json
{
  "count": 5230,
  "limit": 1000,
  "offset": 0,
  "next_offset": 1000,
  "next_after_code_1c": "1c-000999",
  "next_after_id": 12345,
  "results": [
    { "code_1c": "1c-000123", "price": "5900.00", "currency": "RUB", "stock": "7.000", "reserved": "2.000", "available": "5.000" }
  ]
}
```

| Поле | Смысл |
|---|---|
| `count` | всего позиций (offset-режим); в keyset-режиме — `null` (не считаем) |
| `next_offset` | `offset` следующей страницы; на последней / в keyset — `null` |
| `next_after_code_1c`, `next_after_id` | курсор следующей keyset-страницы (передать в `after_code_1c`/`after_id`); на последней — `null` |
| `code_1c` | код 1С позиции (ключ сравнения) |
| `price` | актуальная цена; `null`, если не задана |
| `currency` | валюта (всегда есть, по умолчанию `RUB`) |
| `stock` | физический остаток сайта |
| `reserved` | зарезервировано заказами сайта |
| `available` | доступно к продаже (`stock − reserved`) |

Важно:

- числа отдаются **строками**; `null` бывает только у `price` (цена не задана);
  `stock`/`reserved`/`available` присутствуют всегда (по умолчанию `"0.000"`),
  `currency` — всегда (по умолчанию `RUB`);
- сортировка **стабильна** (по `code_1c`, затем по внутреннему id) — постраничный
  обход не теряет и не дублирует строки;
- **признак конца обхода** — `next_offset: null`; запрос с `offset` за пределами
  выборки отдаёт пустой `results` и `next_offset: null` (не ошибка);
- `price` в снимке — это **основная (розничная) цена** позиции. Другие типы цен
  (`price_type`, напр. `wholesale`) в снимок **не входят** — сверять по ним дельту
  через снимок нельзя (оптовые цены 1С обновляет полным проходом по своим данным);
- `available` отдаётся «как есть», в т.ч. может быть `≤ 0` (тогда позиция считается
  отсутствующей);
- в снимок попадают **все позиции с `code_1c`** (даже скрытые на витрине);
  `code_1c` должен быть **уникальным**;
- 1С присылает обратно только **`price`** и **физический `stock`**;
  `reserved` и `available` ведёт сам сайт — **1С их не передаёт**.

Алгоритм в 1С:

```text
offset = 0
повторять:
    GET /snapshot/?limit=1000&offset=offset
    сравнить каждую строку со своими данными
    если цена отличается  -> в пакет prices/update
    если остаток отличается -> в пакет stocks/update
    offset = next_offset
пока next_offset != null
отправить накопленные пакеты в /prices/update и /stocks/update
```

## 10. Обновление цен

Endpoint:

```http
POST /api/1c/prices/update
```

Назначение:

- быстро обновлять цены;
- хранить разные типы цен независимо.

Пример:

```json
{
  "items": [
    { "external_id": "1c-000123", "price": "5900.00", "old_price": "6500.00", "currency": "RUB", "price_type": "retail" },
    { "external_id": "1c-000123", "price": "5400.00", "currency": "RUB", "price_type": "wholesale" }
  ]
}
```

Поля:

| Поле | Обязательное | Описание |
|---|---:|---|
| `external_id` / `code_1c` / `sku` / `article` | да | идентификатор товара |
| `price` | да | актуальная цена |
| `old_price` | нет | старая цена |
| `currency` | нет | по умолчанию `RUB` |
| `price_type` | нет | по умолчанию `retail` |

Ответ приходит сразу:

```json
{ "created": 0, "updated": 1, "skipped": 0, "uncategorized": 0, "errors": 0, "batch_uid": "0f3c1e54-..." }
```

## 11. Обновление остатков

Endpoint:

```http
POST /api/1c/stocks/update
```

Пример:

```json
{
  "items": [
    { "external_id": "1c-000123", "stock": "7", "reserved": "2", "available_stock": "5", "warehouse": "main" }
  ]
}
```

Поля:

| Поле | Обязательное | Описание |
|---|---:|---|
| `external_id` / `code_1c` / `sku` / `article` | да | идентификатор товара |
| `stock` | да* | физический остаток |
| `reserved` | да* | резерв |
| `available_stock` | да* | доступно к продаже |
| `warehouse` | нет | склад, по умолчанию `main` |

\* Обязательно **хотя бы одно** из трёх полей остатка. Строка только с идентификатором,
без `stock`/`reserved`/`available_stock` → `400`. `stock: "0"` (ноль) — валиден.

Если `available_stock` не передан, сайт считает:

```text
available_stock = stock - reserved
```

Если `available_stock > 0`, товар в наличии; если `<= 0` — отсутствует.

## 12. Проверка результата фонового импорта

Endpoint:

```http
GET /api/1c/sync/<batch_uid>
```

Пример ответа (есть ошибки → статус `partial`):

```json
{
  "batch_uid": "0f3c1e54-...",
  "status": "partial",
  "finished": true,
  "rows_total": 100,
  "rows_ok": 98,
  "rows_error": 2,
  "created": 30,
  "updated": 68,
  "skipped": 0,
  "uncategorized": 5,
  "errors": 2,
  "finished_at": "2026-06-16T08:55:00Z",
  "error_details": "1c-000777: Неоднозначный артикул"
}
```

Статусы:

| Статус | Значение |
|---|---|
| `running` | импорт ещё идёт |
| `ok` | всё обработано без ошибок |
| `partial` | часть строк обработана, часть с ошибками (`rows_error > 0`) |
| `error` | прогон упал целиком |

## 13. Ошибки и повторы

| HTTP-код | Что значит | Что делать 1С |
|---|---|---|
| `200` | запрос обработан | разобрать счётчики |
| `202` | задача принята в фон | опрашивать `sync/<batch_uid>` |
| `400` | неправильный формат данных | не повторять, исправить данные |
| `403` | неверный токен | не повторять, проверить настройку |
| `404` | не найден `batch_uid` | проверить сохранённый UID |
| `503` | сайт не смог поставить задачу в очередь | повторить позже |
| `5xx` | временная ошибка сайта | повторить позже |

Ретраи: 2с, 4с, 8с, 16с — максимум 4–5 попыток. На `400` и `403` повтор не делать.

## 14. Расписание обмена

| Операция | Частота |
|---|---|
| `snapshot` (GET) | перед циклом сверки цен/остатков (забрать снимок и сравнить) |
| `prices/update` | каждые 5–15 минут или по факту изменения |
| `stocks/update` | каждые 5–15 минут или по факту изменения |
| `products/update` | 1–4 раза в сутки |
| `products/import` | ночью 1 раз в сутки или вручную |
| `sync/<batch_uid>` | каждые 5–15 секунд после `products/import` / `products/update` |
| `orders/new` (GET) | каждые 1–5 минут |
| `sales/upload` | ночью 1 раз в сутки (первый запуск — за 90 дней) |

## 15. Заказы — модель на 3 осях

Контракт финальный, **эндпоинты реализованы и работают** (`orders/new` → `200`,
`orders/confirm` → per-item-результат). Можно интегрироваться.

### 15.0 Главное про статусы

Статус заказа на сайте — это **три независимых поля-оси** (полная модель:
[`docs/order-lifecycle.md`](order-lifecycle.md)):

| Ось | Поле | Кто двигает |
|---|---|---|
| Обработка | `fulfillment_status` | **1С / менеджер / кладовщик** |
| Оплата | `payment_status` | сайт (ЮKassa / менеджер) — **1С не трогает** |
| Выгрузка в 1С | `sync_1c_status` | сайт (`exported`, когда 1С забрала заказ) |

Поэтому 1С двигает **только** ось обработки (`fulfillment_status`) и сообщает
результат резерва. **Оплату 1С не передаёт.** Статус выгрузки сайт ставит сам.

### 15.1 Получение новых заказов

```http
GET /api/1c/orders/new
```

- 1С забирает заказы, которые ещё не выгружены (`sync_1c_status = pending`);
- сайт по факту выдачи сам переводит их в `exported`;
- `payment.status` в ответе — это **информирование** об оплате, 1С его не меняет.

```json
{
  "items": [
    {
      "site_order_id": 123,
      "order_number": "P-2026-000123",
      "created_at": "2026-06-16T10:30:00+03:00",
      "fulfillment_status": "new",
      "customer": { "type": "b2c", "name": "Иван Иванов", "phone": "+79000000000", "email": "client@example.com" },
      "delivery": { "method": "delivery", "address": "Пенза, ул. Московская, 1", "comment": "Позвонить за час", "cost": "0.00" },
      "payment": { "method": "online", "status": "paid" },
      "totals": { "items_total": "5900.00", "delivery_total": "0.00", "total": "5900.00", "currency": "RUB" },
      "items": [
        { "line_id": 1, "external_id": "1c-000123", "sku": "BOSCH-GSB13RE", "name": "Дрель ударная BOSCH GSB 13 RE", "unit": "шт", "quantity": "1.000", "price": "5900.00", "total": "5900.00" }
      ]
    }
  ]
}
```

> Стоимость доставки пока **не передаётся**: `delivery.cost` и `delivery_total`
> всегда `"0.00"`, `total` равен `items_total`. Поле наполнится, когда на сайте
> появится расчёт доставки в чекауте; до тех пор не полагаться на него.

1С сохраняет `site_order_id`/`order_number`, чтобы не плодить дубли. Один заказ
может прийти повторно, пока 1С не подтвердила приём — обработка должна быть
**идемпотентной**.

### 15.2 Подтверждение заказа и резервирование

```http
POST /api/1c/orders/confirm
```

1С присылает статус обработки и результат резерва **раздельно** (не одним полем).

`fulfillment_status` — только из набора оси обработки:

| Значение | Смысл |
|---|---|
| `confirmed` | принят, резерв подтверждён (товар закреплён) |
| `assembling` | собирается |
| `ready` | собран (самовывоз/передача в доставку) |
| `shipped` | передан в доставку |
| `completed` | выдан / доставлен |
| `cancelled` | отменён |

Резерв — **атрибут результата**, не статус. Успешный резерв двигает обработку в
`confirmed`:

```json
{
  "items": [
    {
      "site_order_id": 123,
      "order_number": "P-2026-000123",
      "onec_order_id": "1c-order-987",
      "onec_order_number": "УТ-000987",
      "fulfillment_status": "confirmed",
      "reserve": { "ok": true, "reserved_until": "2026-06-17T10:30:00+03:00" },
      "comment": "Заказ принят и зарезервирован"
    }
  ]
}
```

Если товара не хватает — заказ **остаётся** `fulfillment=new`, причина по строкам:

```json
{
  "items": [
    {
      "site_order_id": 123,
      "onec_order_id": "1c-order-987",
      "fulfillment_status": "new",
      "reserve": {
        "ok": false,
        "lines": [
          { "external_id": "1c-000123", "requested": "3.000", "available": "1.000", "error": "Недостаточно остатка" }
        ]
      },
      "comment": "Недостаточно товара на складе"
    }
  ]
}
```

`reserved_until` — это срок «жёсткого» резерва в 1С. Не путать с резервом 15 минут
на оси оплаты сайта (он снимается автоматически, если онлайн-оплата не пришла).

### 15.3 Изменение статусов заказа

Тем же эндпоинтом — меняем только `fulfillment_status`:

```json
{
  "items": [
    { "site_order_id": 123, "onec_order_id": "1c-order-987", "fulfillment_status": "shipped", "tracking": "PEK-123456", "comment": "Передан в доставку" }
  ]
}
```

Правила:

- идентификатор заказа — `site_order_id` **или** `order_number` (один обязателен);
- `onec_order_id`/`onec_order_number` — id заказа в 1С, стабильный;
- повторная отправка того же статуса безопасна (идемпотентность);
- **недопустимые переходы сайт отклоняет** по матрице прав
  ([`order-lifecycle.md`](order-lifecycle.md), разд. 7) — нельзя, например,
  `completed` сразу из `new`;
- `payment_status` и `sync_1c_status` 1С не присылает.

Сайт по смене статуса: сохраняет его, пишет историю и при подписке шлёт клиенту
уведомление в MAX (переходы `confirmed/ready/shipped/completed`).

## 16. Продажи — источник блока «Хиты продаж»

На главной сайта есть блок «Хиты продаж». Он обязан показывать то, что **реально
продаётся**, поэтому нужна выгрузка продаж из 1С: сайт видит только собственные
заказы, а основной оборот идёт через магазин.

**Что отправлять:** `POST /api/1c/sales/upload`, конверт как у остальных методов.

| Поле | Тип | Обяз. | Прим. |
|---|---|---|---|
| идентификатор | строка | да | `external_id` / `code_1c` / `sku` / `article` |
| `date` | `ГГГГ-ММ-ДД` | да | день продажи (дата документа реализации) |
| `quantity` | число (3 знака) | да | продано за день, строго больше нуля |

```json
{
  "items": [
    { "external_id": "1c-000123", "date": "2026-07-01", "quantity": "3" },
    { "external_id": "1c-000456", "date": "2026-07-01", "quantity": "12" }
  ]
}
```

**Как это устроено на стороне сайта (важно для выгрузки):**

- Гранулярность — **день**, а не документ. Несколько реализаций одного товара за
  день можно слать отдельными строками: сайт их сложит.
- Ключ идемпотентности — (товар, день). Повторная отправка того же дня
  **перезаписывает** количество. Поэтому выгрузку можно безопасно повторять, а
  возврат или исправленный документ отправлять той же строкой с новым итогом.
- Продажа товара, которого нет в каталоге сайта, не ошибка: строка попадёт в
  `skipped`.
- Рейтинг считается за скользящее окно 90 дней. При первом запуске выгрузите
  продажи за последние 90 дней, дальше достаточно прошедших суток.

Пока выгрузки нет, блок на главной честно называется «Новинки каталога» —
хитами товары не объявляются без данных о продажах.

## 17. Что должен сдать 1С-разработчик

1. Отправку новых/изменённых позиций (`products/import`, `products/update`).
2. Дельта-обмен цен и остатков: забор снимка (`GET /snapshot/` постранично),
   сравнение у себя и отправку **только изменений** в `prices/update` / `stocks/update`.
3. Настройку тестового и боевого URL и `X-Api-Key`.
4. Разбиение больших выгрузок на пакеты до 1000 строк.
5. Логирование запросов/ответов без токена.
6. Ретраи на `503`, `5xx`, timeout; на `400`/`403` — без повтора.
7. Опрос `GET /sync/<batch_uid>` после фонового импорта.
8. Получение заказов (`orders/new`) с идемпотентным сохранением.
9. Подтверждение резерва и движение `fulfillment_status` (`orders/confirm`),
   **без передачи оплаты**.
10. Ежесуточную выгрузку продаж (`sales/upload`) с гранулярностью по дню и
    первичной заливкой за 90 дней.
11. Инструкцию, где в 1С включается расписание обмена.

## 18. Проверка приёмки

Товары/цены/остатки (доступно сейчас):

- отправить 1 новый товар через `products/import`;
- дождаться `sync/<batch_uid>` со статусом `ok` или `partial`;
- забрать снимок `GET /snapshot/` — позиция в нём присутствует;
- обновить цену (`prices/update`) и остаток (`stocks/update`);
- повторить запросы — дубли товаров не создаются;
- строка без идентификатора → `400`; запрос без токена → `403`; больше `1000`
  строк → `400`; `snapshot` без токена → `403`, `?limit=0` → `400`.

Заказы:

- сайт отдаёт новый заказ в `orders/new` (`fulfillment_status: new`);
- 1С создаёт заказ у себя и шлёт `orders/confirm` с `fulfillment_status: confirmed`
  и `reserve.ok: true`;
- сайт показывает заказ подтверждённым;
- при нехватке товара 1С шлёт `reserve.ok: false` — заказ остаётся `new`;
- повторная отправка того же подтверждения не создаёт дублей;
- оплату 1С не присылает — ось `payment` живёт на сайте.
