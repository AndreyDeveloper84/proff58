# Жизненный цикл заказа — модель на трёх осях

Источник истины по статусам заказа в проекте «Профессионал». Любой код и любое
ТЗ (включая обмен с 1С — `docs/1c-api-spec.md`, `docs/1c-developer-task.md`)
должны опираться на эту модель, а не вводить свои статусы.

## 1. Три оси вместо одной цепочки

У заказа **не один** статус, а **три независимых поля-оси**. Каждая описывает
свой процесс и двигается своим участником. Это убирает «гибридные» статусы вроде
«подтверждён, но не оплачен» и сохраняет полную историю заказа.

```python
class Order(models.Model):
    fulfillment_status = models.CharField(...)  # обработка
    payment_status     = models.CharField(...)  # оплата
    sync_1c_status     = models.CharField(...)  # выгрузка в 1С

    @property
    def display_status(self) -> str:  # производный статус для клиента/менеджера
        ...
```

Почему так: оплата, обработка и синхронизация идут параллельно. «Оплата при
получении» = `payment=pending` + `fulfillment=assembling` одновременно. Возврат
после доставки = `fulfillment=completed` + `payment=refunded`, история цела. Это
стандарт зрелого e-commerce (Shopify, Saleor).

## 2. Ось обработки — `fulfillment_status`

Бизнес-движение заказа от оформления до выдачи. Двигают: менеджер (в 1С) и
кладовщик. Переходы ограничены матрицей прав (раздел 7).

| Статус | Когда наступает | Кто ставит | Уведомление MAX |
|---|---|---|---|
| `new` | Заказ оформлен на сайте | Система (авто) | «Заказ №… принят»* |
| `confirmed` | Менеджер проверил наличие, комплектность, контакты в 1С | Менеджер | «Заказ №… подтверждён» |
| `assembling` | Заказ взят в сборку | Менеджер / Кладовщик | — |
| `ready` | Собран: готов к выдаче или передаче в доставку | Кладовщик | «Заказ №… готов» (самовывоз) |
| `shipped` | Передан в доставку, есть трек-номер | Менеджер | «Заказ №… передан в доставку» |
| `completed` | Товар выдан / доставка завершена | Система / Менеджер | «Спасибо за покупку» |
| `cancelled` | Отмена из любого статуса (клиент, менеджер, нет товара) | Менеджер / Админ | «Заказ №… отменён» |

\* Уведомление `new` уходит, только если клиент уже открыл бота MAX. Для гостя
сначала кнопка «Отслеживать в MAX» на странице «Спасибо за заказ» — иначе бот не
может написать первым.

**Важно:** `confirmed` — момент, когда товар гарантированно закреплён за клиентом.
До него резерв мягкий.

## 3. Ось оплаты — `payment_status`

Движение денег. Двигают: система (уведомление кассы — АТОЛ Pay, см.
[payments-atolpay.md](payments-atolpay.md)) для онлайн-оплаты; менеджер — для B2B
по счёту и оплаты при получении.

| Статус | Когда наступает | Кто ставит | Уведомление MAX |
|---|---|---|---|
| `pending` | Заказ создан, оплата ожидается. Запущен резерв товара: B2C — 30 мин (#568, настройка `RESERVATION_TTL_B2C_MINUTES`), B2B — 24 ч вместе со счётом (#559) | Система (авто) | — |
| `paid` | Касса подтвердила оплату (статус перезапрошен у неё, а не взят из уведомления); или менеджер отметил оплату по счёту | Система / Менеджер | «Оплата заказа №… получена» |
| `expired` | Оплата не пришла в срок, заказ отменён, резерв снят. B2B: счёт не оплачен за 24 ч (`invoice_lifecycle`). Онлайн-оплата: резерв истёк, а касса подтвердила, что денег нет (`payments/expiry.py`) | Система (Celery) | — (покупателю уходит письмо об отмене) |
| `partially_refunded` | Частичный возврат проведён, остаток платежа не возвращён | Менеджер (`payments.services.refund`) | «Оформлен частичный возврат по заказу №…» |
| `refunded` | Возврат проведён полностью (сумма возвратов = сумме платежа) | Менеджер (`payments.services.refund`) | «Возврат по заказу №… выполнен» |

**Что происходит, когда резерв истёк** (`reserved_until` в прошлом). Работают два
независимых janitor'а:

* `orders.release_expired_reservations` (каждые 10 мин) — снимает резерв у любого
  неоплаченного заказа: `reservation_status → released`, товар возвращается в
  остаток. Статусы заказа не трогает. Из-за интервала фактическое освобождение
  может отставать от `reserved_until` до 10 минут; API отдаёт «честный» признак
  `reservation_expired`, не зависящий от лага.
* `payments.expire_unpaid_online_orders` (каждые 5 мин) — только заказы с
  онлайн-оплатой в статусах `new`/`confirmed`: спрашивает кассу и, если денег нет,
  **отменяет заказ** (`fulfillment=cancelled`, `payment=expired`) и пишет покупателю.
  Заказ, по которому покупатель прямо сейчас проходит оплату в банке, ждёт ещё
  `PAYMENT_IN_FLIGHT_GRACE_MINUTES` (15). Заказ с нерассчитанной доставкой
  (`delivery_calc_status=manual_required`) не отменяется: оплатить его нельзя.
  Таблица решений — [payments-atolpay.md](payments-atolpay.md) §6.

Заказ с оплатой при получении автоматика не отменяет: он остаётся `pending`, а
наличие при выдаче подтверждает менеджер.

**Нажал «Оплатить» — окно начинается заново.** Старт оплаты продлевает резерв до
полного срока (30 мин для B2C), но никогда не укорачивает уже удержанный (24 ч
после ручного расчёта доставки) и не продлевает дальше двух часов от оформления
заказа — иначе товар можно было бы держать без оплаты сколько угодно. Если срок
вышел и продлить его нельзя, оплата не открывается («срок оплаты истёк»). Если
резерв к этому моменту снят, товар удерживается заново; товара нет — оплата не
открывается.

Способы оплаты: карта и СБП через АТОЛ Pay, наличными при получении, безналичный
счёт (B2B). Для наличных и B2B-счёта `payment_status` остаётся `pending`, пока
обработка идёт независимо.

### Заявка покупателя на возврат денег

Покупатель сам деньги не возвращает — он подаёт заявку в карточке заказа
(`POST /api/payments/orders/{number}/refund-request/`, правила —
`apps/payments/refund_requests.py`, решение владельца от 17.09.2026):

* только по заказу, оплаченному онлайн (`paid` / `partially_refunded`);
* до получения заказа и 14 дней после (`Order.completed_at` ставится при переходе
  в `completed` — из админки или от 1С);
* одна открытая заявка на заказ; после отказа или частичного возврата можно подать новую.

Менеджер решает в админке «Оплата → Заявки на возврат» (очередь — пункт меню
«Просят вернуть деньги»): «Вернуть деньги» (вся сумма или часть, через
`payments.services.refund`) или «Отклонить» с причиной — её покупатель видит в
кабинете. Товар на склад возвращает 1С, сайт остатки не трогает. О новой заявке
сотрудникам уходит письмо (событие `refund_requested`).

**Заявку за покупателя подаёт сайт**, когда заказ отменён, а деньги за него
получены онлайн (DRF-2736): оплата пришла после отмены либо заказ отменили уже
оплаченным. Товара покупатель не получит, поэтому обычное решение — вернуть всё
(пустое поле суммы = весь остаток). Отказ и частичная сумма не запрещены, но
страница решения предупреждает: деньги останутся у магазина, а гость подать
заявку заново не может. Так закрывают заявку, когда деньги вернули в личном
кабинете кассы (заказ станет `refunded` сам, по уведомлению кассы) или когда
удержание оговорено с покупателем.

Заявки, платежи и возвраты из админки не удаляются. Заказ «отменён, оплата
получена» вовсе без заявки (создание сорвалось, заказ отменили до появления
автоматики) находит и чинит janitor — каждые 5 минут. Если у отменённого заказа
оплачены два платежа, после возврата одного заказ остаётся `partially_refunded`,
а на второй заводится новая заявка.

**`paid` ≠ подтверждение заказа.** `paid` означает только «деньги получены».
Подтверждает заказ менеджер на оси обработки (`confirmed`).

## 4. Ось выгрузки в 1С — `sync_1c_status`

Техническое событие синхронизации. Особенность: сайт **не отправляет** заказ в
1С — **1С сама приходит на сайт и забирает** новые заказы. Поэтому это отдельная
ось, не встроенная между бизнес-статусами.

| Статус | Когда наступает | Кто ставит |
|---|---|---|
| `pending` | Заказ создан, ждёт, пока 1С его заберёт | Система (авто) |
| `exported` | 1С забрала заказ. Сохраняются `external_order_id` и дата выгрузки | Система (по запросу 1С) |

Пример связки: заказ сайта №1234 ↔ заказ 1С №0000456 (`external_order_id`). После
`exported` менеджер работает с заказом уже в 1С, а статусы обработки возвращаются
на сайт через обмен.

## 5. Как три оси работают вместе — сценарии

Оси комбинируются **без новых статусов**:

**Онлайн-оплата (розница, happy path)**
```
Оформлен:    fulfillment=new       payment=pending  sync=pending
Оплачен:     fulfillment=new       payment=paid     sync=pending
1С забрала:  fulfillment=new       payment=paid     sync=exported
Подтверждён: fulfillment=confirmed payment=paid     sync=exported
Выдан:       fulfillment=completed payment=paid     sync=exported
```

**Оплата при получении** (оплата висит `pending`, обработка идёт)
```
Собирается:      fulfillment=assembling payment=pending sync=exported
Выдан и оплачен: fulfillment=completed  payment=paid    sync=exported
```

**Слот доставки** (#569, B2C + курьер). При оформлении покупатель выбирает
дату и интервал (`DeliverySlot`, справочник ведёт менеджер в админке). Заказ
хранит FK на слот и **снимок** (`delivery_slot_snapshot`) — история не «плывёт»
при правке слота. Занятость слота = число заказов с `fulfillment != cancelled`:
место освобождает **только отмена заказа** (менеджер/1С); истечение 30-минутного
резерва товара (#568) слот не освобождает — брошенные заказы надо отменять,
иначе слот держится занятым. Пустой справочник слотов = чекаут работает без
выбора времени, как раньше.

**B2B по счёту** (#557/#559, Wave 1: счёт и резерв живут 24 часа)

Счёт (`B2BInvoice`, статусы `issued/paid/expired/cancelled`) выставляется
автоматически при оформлении B2B-заказа; `valid_until == reserved_until`.
Доставки для юрлиц в Wave 1 нет (#558) — счёт только на товары, самовывоз.
```
Счёт выставлен: invoice=issued  fulfillment=new       payment=pending
Оплата пришла:  invoice=paid    fulfillment=new…ready payment=paid     (резерв списан)
Не оплачен 24ч: invoice=expired fulfillment=cancelled payment=expired  (резерв снят janitor'ом)
```
Оплату отмечает менеджер (админка «Счета B2B» → «Отметить оплаченным»);
истёкший счёт «оживить» нельзя — заказ оформляется заново.

**Возврат после доставки** (история цела)
```
До возврата:    fulfillment=completed payment=paid     sync=exported
После возврата: fulfillment=completed payment=refunded sync=exported
```

**Онлайн-заказ не оплачен вовремя**
```
Оформлен:        fulfillment=new       payment=pending  reservation=held
Резерв истёк:    fulfillment=new       payment=pending  reservation=released  (≤10 мин)
Касса: денег нет fulfillment=cancelled payment=expired  reservation=released  (≤5 мин)
```

**Оплата пришла за уже отменённый заказ** (DRF-2736). Неоплаченный платёж у кассы
погасить нельзя — страница оплаты остаётся рабочей и после отмены заказа, кто бы
его ни отменил: автоматика, покупатель или менеджер.
```
Отменён:         fulfillment=cancelled payment=expired|pending
Деньги пришли:   fulfillment=cancelled payment=paid      + заявка на возврат (сама)
Менеджер вернул: fulfillment=cancelled payment=refunded
```
Заказ не воскресает: товар мог уйти другому покупателю. События `payment_succeeded`
и `order_paid` не издаются — «заказ оплачен, собираем» было бы неправдой. Заказ,
ещё не выгруженный в 1С, туда и не попадёт (отменённые не выгружаются); уже
выгруженный остаётся в 1С, и снять его там нужно вручную — обратного канала
«заказ отменён» в контракте нет.

**Оплата пришла, когда резерв уже снят, а заказ ещё жив** (покупатель был в банке,
пока истёк срок). Товар берётся заново и сразу списывается. Если его уже купили —
заказ оплачен без товара: сотрудникам уходит письмо «оплачен, а товар не списан»,
дальше — замена или отмена заказа (заявка на возврат заведётся сама).

## 6. Что видит человек — производный статус

Клиенту и менеджеру три поля не показывают. `display_status` собирает из трёх осей
один понятный статус по приоритету: терминальные состояния (отменён, возврат)
важнее, затем обработка, оплата — подсказкой.

| Состояние осей | Что видит клиент |
|---|---|
| `payment=expired` | Заказ отменён (не оплачен вовремя) |
| `fulfillment=cancelled`, `payment=paid` или `partially_refunded` | Заказ отменён, оплата получена — вернём деньги |
| `fulfillment=cancelled` | Заказ отменён |
| `payment=refunded` | Возврат оформлен |
| `fulfillment=new`, `payment=pending` | Ожидает оплаты |
| `fulfillment=new`, `payment=paid` | Оплачен, передаётся в обработку |
| `fulfillment=confirmed` | Подтверждён |
| `fulfillment=assembling` | Собирается |
| `fulfillment=ready` (самовывоз) | Готов к выдаче |
| `fulfillment=shipped` | В доставке |
| `fulfillment=completed` | Выполнен |

## 7. Права на переходы (Django permissions)

Нарушение блокируется на уровне прав: роль не может выставить статус не из своей
колонки. Обмен с 1С подчиняется этой же матрице (по оси `fulfillment`).

| Переход | Система | Менеджер | Кладовщик | Админ |
|---|:---:|:---:|:---:|:---:|
| `payment → paid` (онлайн) | ✓ | – | – | – |
| `payment → paid` (B2B/наличные) | – | ✓ | – | ✓ |
| `payment → expired` | ✓ | – | – | – |
| `payment → refunded` | ✓ | ✓ | – | ✓ |
| `fulfillment → confirmed` | – | ✓ | – | ✓ |
| `fulfillment → assembling` | – | ✓ | ✓ | ✓ |
| `fulfillment → ready` | – | ✓ | ✓ | ✓ |
| `fulfillment → shipped` | – | ✓ | – | ✓ |
| `fulfillment → completed` | ✓ | ✓ | – | ✓ |
| `fulfillment → cancelled` | – | ✓ | – | ✓ |
| `sync → exported` | ✓ | – | – | – |

## 8. Уведомления MAX

Реализовано в #514/#515/#516 через `apps.notifications.services.create_notification()`
(intent → preferences → outbox) — не напрямую `send()`. Уведомления привязаны к
**переходам**, а не к одному статусу, и создаются, только если у пользователя
активна привязка MAX (`apps.integration_max.services.resolve_active_chat_id`) и
включена категория `order_updates_enabled` (`UserNotificationPreference`) —
иначе создаётся объяснимый skipped-результат без внешней отправки.

Издатели для оси обработки (`order_status_changed`) — `orders.fulfillment`
(менеджер, покупатель), `sync_1c.use_cases.confirm_orders` (1С),
`orders.invoice_lifecycle` (истёкший счёт) и `payments.expiry` (автоотмена
неоплаченного онлайн-заказа); для оплаты/возврата — `apps.payments.services`
(`order_paid`, `payment_refunded`, ADR-0009); подписчик и typed mapping
переход → MAX-событие/шаблон — `apps.integration_max.receivers`.

Бот отправляет сообщение при смене на:

| Ось | Переходы, которые уведомляют | Переходы, которые НЕ уведомляют |
|---|---|---|
| Обработка | `confirmed`, `ready`, `shipped`, `completed`, `cancelled` | `assembling` (осознанно, MVP); `sync_1c_status` — техническая ось, не уведомляет никогда |
| Оплата | `paid`, `partially_refunded`, `refunded` | `pending`, `expired` |

`ready` учитывает способ получения в тексте (самовывоз vs курьер); `shipped`
добавляет трек-номер только если он есть. Бот не пишет первым — до подписки
через привязку MAX уведомление тихо пропускается (skipped), а не теряется молча
не по причине, а по объяснимой политике.

Идентификатор идемпотентности уведомления — заказ + ось + цель перехода
(`order-status-{id}-{new_status}` для обработки, `order-{created,paid}-{id}`,
`order-refunded-{id}-{refund_id}` для возврата — конкретная операция возврата,
не заказ, т.к. частичных возвратов может быть несколько).
