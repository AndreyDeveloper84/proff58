# Интеграция 1С 7.7 → API сайта «Профессионал». Задание для разработчика 1С

Документ описывает, **как 1С должна отправлять данные на сайт**: формат JSON,
авторизацию, контракты эндпоинтов, форматы значений, интервалы и обработку ошибок.

> Направление обмена: **1С сама вызывает HTTP API сайта** (push). Сайт ничего не
> забирает из 1С напрямую.
>
> Для цен и остатков рекомендуется **дельта-обмен**: 1С сначала забирает снимок
> актуальных позиций сайта (`GET /snapshot/`), сравнивает у себя и шлёт обратно
> **только изменившиеся** строки в `prices/update` / `stocks/update`. Это резко
> снижает объём обмена. Сравнение выполняется на стороне 1С (см. 5.0).

---

## 1. Общие правила

| Параметр | Значение |
|---|---|
| Базовый URL (прод) | `https://proff58.ru/api/1c/` |
| Базовый URL (тест) | `https://dev.proff58.ru/api/1c/` |
| Метод | `POST` (кроме `GET`: `snapshot`, `orders/new`, `sync/<batch_uid>`) |
| Content-Type | `application/json` |
| Кодировка | строго **UTF-8** |
| Тело запроса | конверт `{ "items": [ ... ] }`, массив **не пустой** |
| Числа | строкой или числом; разделитель дробной части — точка `.` **или** запятая `,` (сайт нормализует); разряды можно без пробелов |
| Булево | `true/false`, либо `1/0`, либо `"да"/"нет"` |

Все эндпоинты принимают **пакет строк** (`items`), а не по одной — слать данные
батчами (рекомендация по размеру — в разделе 6).

---

## 2. Авторизация (токен)

Каждый запрос обязан содержать HTTP-заголовок:

```
X-Api-Key: <ТОКЕН>
```

- Токен — общий секрет, выдаётся отдельно (свой для прода и для теста).
- Сверяется на стороне сайта за константное время.
- Нет заголовка / неверный токен → **HTTP 403** (тело: `{"detail": "..."}`), запрос
  не обрабатывается.

Токен передаётся вне этого документа (через защищённый канал). В коде/логах 1С
его хранить как защищённую константу, не светить в открытом виде.

---

## 3. Идентификация товара (ключи связи)

Сайт связывает строку 1С со своим товаром по идентификаторам. В каждой строке
**обязателен минимум один** из:

| Поле в JSON | Что это | Роль |
|---|---|---|
| `external_id` | внутренний код/GUID номенклатуры 1С | **главный** ключ (уникальный) |
| `code_1c` | синоним `external_id` | то же |
| `sku` | артикул товара | запасной ключ |
| `article` | синоним `sku` | то же |

Правила:
- Сопоставление идёт **сначала по `external_id`/`code_1c`**, затем по `sku`/`article`.
- **`external_id` должен быть стабильным и уникальным** на товар (не меняться между
  выгрузками). Это критично — по нему сайт находит товар при каждом обновлении.
- Артикул **не обязан быть уникальным**. Если по артикулу (без кода) подходит
  несколько товаров — строка считается **конфликтом**, ничего не обновляется,
  она уходит в ручной разбор (см. поле `errors` в ответе).
- Рекомендация: **всегда присылать `external_id`** — он снимает неоднозначность.

---

## 4. Что чем управляет (важно!)

Сайт — продающая система, 1С — учётная. Поэтому сайт **берёт из 1С только**:

- цену, остаток;
- базовые поля: исходное название, бренд (если на сайте пусто), штрихкод,
  единицу измерения, активность, исходную группу.

Сайт **никогда не перезаписывает из 1С**: категорию каталога, витринное название,
описание, SEO, фото, опубликованность. Это ведут на сайте вручную.

Практический вывод для 1С: можно смело слать обновления цен/остатков сколько
угодно часто — контент сайта от этого не пострадает.

## 5. Контракты эндпоинтов

### 5.0 `GET /snapshot/` — снимок актуальных позиций (дельта-обмен)

Сайт отдаёт текущее состояние позиций (код 1С + цена + остатки). 1С забирает
снимок **постранично**, сравнивает у себя и шлёт обратно в `prices/update` /
`stocks/update` **только изменившиеся** строки. Сравнение — на стороне 1С.

**Запрос** (заголовок `X-Api-Key`, метод `GET`):

```
GET /api/1c/snapshot/?limit=1000&offset=0
X-Api-Key: <ТОКЕН>
```

Две схемы пагинации (сортировка всегда `code_1c, id`):

| Параметр | По умолчанию | Правила |
|---|---|---|
| `limit` | `ONEC_MAX_ITEMS` (1000) | целое > 0; больше `ONEC_MAX_ITEMS` — **обрезается** до него; `0`/отрицательное/нечисло → `400` |
| `offset` | `0` | **offset-режим** (как было): целое ≥ 0; отрицательное/нечисло → `400` |
| `after_id` | — | **keyset-режим** (рекомендуется для большого каталога): целое ≥ 0; включает курсорную пагинацию; нечисло/отрицательное → `400` |
| `after_code_1c` | `""` | курсор keyset (вместе с `after_id`); для первой страницы — пусто |

> **offset** прост, но дорого на большом каталоге (высокий `offset` медленный +
> `count()`). **keyset** — O(`limit`) независимо от глубины и без `count()`.
> Keyset включается, **только если передан `after_id`**; иначе работает offset
> (контракт не меняется). Первая keyset-страница: `?limit=1000&after_id=0`.

**Ответ `200 OK`:**

```json
{
  "count": 5230,
  "limit": 1000,
  "offset": 0,
  "next_offset": 1000,
  "next_after_code_1c": "1c-000999",
  "next_after_id": 12345,
  "results": [
    {
      "code_1c": "1c-000123",
      "price": "5900.00",
      "currency": "RUB",
      "stock": "7.000",
      "reserved": "2.000",
      "available": "5.000"
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `count` | всего позиций (offset-режим); в keyset-режиме — `null` (не считаем) |
| `next_offset` | `offset` следующей страницы; на последней / в keyset — `null` |
| `next_after_code_1c`, `next_after_id` | курсор следующей keyset-страницы (передать в `after_code_1c`/`after_id`); на последней странице — `null` |
| `code_1c` | код 1С позиции (ключ сравнения) |
| `price` | актуальная цена сайта; `null`, если не задана |
| `currency` | валюта (всегда есть, по умолчанию `RUB`) |
| `stock` | **физический** остаток сайта |
| `reserved` | зарезервировано заказами **сайта** |
| `available` | доступно к продаже (`stock − reserved`) |

Правила:
- Числа отдаются **строками** (`price` может быть `null`).
- В снимок попадают **все позиции с `code_1c`**, включая скрытые на витрине
  (видимость на обмен не влияет). Позиции без `code_1c` (или с пустым кодом) —
  исключены, обмен по ним невозможен.
- **`code_1c` должен быть уникальным** идентификатором позиции — это ключ сравнения.
- Сортировка стабильна (по `code_1c`, затем по внутреннему id) — пагинация
  не теряет и не дублирует строки.

**Что 1С шлёт обратно по итогам сравнения:** только то, что изменилось —
`price` в `prices/update`, **физический** `stock` в `stocks/update`. Поля
`reserved` / `available` ведёт и пересчитывает **сайт** (они зависят от заказов
сайта) — **1С их не присылает**.

**Дельта-флоу целиком:**

```
1С → GET /snapshot/?offset=0     → страница 1 (next_offset=1000)
1С → GET /snapshot/?offset=1000  → страница 2 … пока next_offset≠null
1С: сравнивает снимок со своими данными
1С → POST /prices/update  { только товары с изменившейся ценой }
1С → POST /stocks/update  { только товары с изменившимся остатком }
```

### 5.1 `POST /products/import` — загрузка/обновление номенклатуры

Создаёт новые товары и обновляет существующие. Используется для первичной
выгрузки и периодической полной/частичной синхронизации номенклатуры.

**Поля строки** (обязателен только идентификатор):

| Поле | Тип | Прим. |
|---|---|---|
| `external_id` / `code_1c` | строка | главный ключ |
| `sku` / `article` | строка | артикул |
| `name` | строка | наименование из 1С |
| `brand` | строка | бренд |
| `barcode` | строка | штрихкод |
| `unit` | строка | ед. изм. |
| `source_group` | строка | группа товара в 1С (справочно) |
| `is_active` | булево | активность в 1С |
| `price` | число (2 знака) | цена |
| `old_price` | число (2 знака) | старая цена (для скидки) |
| `currency` | строка | напр. `RUB` |
| `price_type` | строка | тип цены, по умолчанию `retail` |
| `stock` | число (3 знака) | остаток |

**Пример запроса:**

```json
POST /api/1c/products/import
X-Api-Key: <ТОКЕН>
Content-Type: application/json

{
  "items": [
    {
      "external_id": "1c-000123",
      "sku": "BOSCH-GSB13RE",
      "barcode": "4600000000017",
      "name": "Дрель ударная BOSCH GSB 13 RE",
      "brand": "Bosch",
      "unit": "шт",
      "source_group": "Электроинструмент/Дрели",
      "is_active": true,
      "price": "5900.00",
      "old_price": "6500.00",
      "currency": "RUB",
      "price_type": "retail",
      "stock": "7"
    }
  ]
}
```

> **Импорт асинхронный.** Запрос ставится в фоновую обработку, поэтому ответ —
> **`202 Accepted`** + `batch_uid` (см. 5.3). Реального результата (создано/обновлено)
> в этом ответе нет — его нужно **опросить** по `batch_uid`.

### 5.2 `POST /products/update` — обновление существующих

То же тело, что и `products/import`, **но новые товары НЕ создаются**. Если товара
по идентификатору нет — строка попадает в `skipped` (пропущена). Использовать,
когда нужно только обновить уже заведённые товары, не плодя новые.
Тоже **асинхронный**: ответ `202` + `batch_uid`, результат — опросом.

### 5.3 Асинхронный импорт: `202` и опрос статуса `GET /sync/<batch_uid>`

`products/import` и `products/update` обрабатываются в фоне (могут быть большими
и долгими). Поток:

```
1С → POST products/import → 202 { "batch_uid": "...", "status": "accepted", "accepted": N }
1С → GET  /api/1c/sync/<batch_uid>  (опрашивать каждые 5–15 с, пока finished=false)
        → { "status": "ok|partial|error", "finished": true, "created":.., "errors":.., ... }
```

`GET /api/1c/sync/<batch_uid>` (заголовок `X-Api-Key`) — ответ:

```json
{
  "batch_uid": "0f3c1e54-...",
  "status": "running | ok | partial | error",
  "finished": true,
  "rows_total": 100, "rows_ok": 98, "rows_error": 2,
  "created": 30, "updated": 68, "skipped": 0, "uncategorized": 5, "errors": 2,
  "finished_at": "2026-06-16T08:55:00Z",
  "error_details": "1c-000777: Неоднозначный артикул ..."
}
```

- `status=running`, `finished=false` — ещё обрабатывается, опросить позже.
- `finished=true` — готово; `status` = `ok` (без ошибок) / `partial` (часть строк
  не принята) / `error` (прогон упал целиком).
- неизвестный `batch_uid` → `404`.

> `batch_uid` — это ID **прогона на сайте**, который выдаёт сайт. Не путать с
> внутренним кодом товара 1С (`external_id`/`code_1c`) и с возможным кодом
> выгрузки/пакета 1С (его сейчас не принимаем).

### 5.4 `POST /prices/update` — только цены

**Поля строки:**

| Поле | Тип | Прим. |
|---|---|---|
| идентификатор | строка | `external_id`/`code_1c`/`sku`/`article` |
| `price` | число (2 знака) | **обязательно** |
| `old_price` | число (2 знака) | опционально |
| `currency` | строка | по умолч. `RUB` |
| `price_type` | строка | по умолч. `retail`; разные типы (`retail`/`wholesale`/…) живут независимо |

```json
POST /api/1c/prices/update
{
  "items": [
    { "external_id": "1c-000123", "price": "5900.00", "old_price": "6500.00", "currency": "RUB", "price_type": "retail" },
    { "external_id": "1c-000123", "price": "5400.00", "price_type": "wholesale" }
  ]
}
```

> **Семантика `old_price`:** отсутствует или `null` = **не менять** текущую старую цену
> (часто 1С шлёт только `price`). Чтобы убрать зачёркнутую цену/скидку, нужен **явный**
> механизм (отдельная задача) — пустой `old_price` сбросом НЕ считается.
>
> **Идемпотентность:** если присланная `price` (для данного `price_type`/`currency`) и
> `old_price` не отличаются от текущих — строка идёт в **`skipped`** (история цен не
> растёт, лишних событий нет). Это нормально при «полном прайсе без изменений».

### 5.5 `POST /stocks/update` — только остатки

**Поля строки:**

| Поле | Тип | Прим. |
|---|---|---|
| идентификатор | строка | обязателен |
| `stock` | число (3 знака) | физический остаток |
| `reserved` | число (3 знака) | резерв |
| `available_stock` | число (3 знака) | доступно к продаже; если не прислать — считается как `stock − reserved` |
| `warehouse` | строка | код/название склада, по умолч. `main` |

> В строке обязательно **хотя бы одно** из полей остатка (`stock` / `reserved` /
> `available_stock`); строка только с идентификатором → `400`. `stock: "0"` (нулевой
> остаток) — валиден.

```json
POST /api/1c/stocks/update
{
  "items": [
    { "external_id": "1c-000123", "stock": "7", "reserved": "2", "available_stock": "5", "warehouse": "main" }
  ]
}
```

### 5.6 Заказы — модель на 3 осях

| Эндпоинт | Метод | Назначение |
|---|---|---|
| `/orders/new` | `GET` | 1С забирает новые заказы с сайта |
| `/orders/confirm` | `POST` | 1С подтверждает приём/резерв и двигает статус обработки |

> **Эндпоинты реализованы (#50) и работают** — `orders/new` отдаёт `200`,
> `orders/confirm` валидирует конверт и отдаёт per-item-результат. Контракт ниже —
> финальный. Быстрая проверка round-trip без реальной 1С:
> `python manage.py demo_1c_orders` (см. §11).

**Статус заказа на сайте — это три независимых поля-оси** (полная модель:
[`docs/order-lifecycle.md`](order-lifecycle.md)):

| Ось | Поле | Кто двигает |
|---|---|---|
| Обработка | `fulfillment_status` | **1С / менеджер / кладовщик** |
| Оплата | `payment_status` | сайт: вебхук ЮKassa / менеджер — **1С не трогает** |
| Выгрузка в 1С | `sync_1c_status` | сайт (ставит `exported`, когда 1С забрала заказ) |

Поэтому 1С присылает **только** статус обработки (`fulfillment_status`) и результат
резерва. **Оплату 1С не передаёт** — это отдельная ось сайта.

#### `GET /orders/new` — забор новых заказов

Сайт отдаёт заказы со `sync_1c_status = pending` (ещё не выгружены). Сайт **НЕ
меняет** `sync_1c_status` на GET: заказ остаётся `pending` и может быть выдан
повторно, пока 1С не подтвердит приём через `POST /orders/confirm`
(at-least-once delivery). `payment.status` в payload — **информирование** 1С о
факте оплаты (1С его не меняет).

```json
{
  "items": [
    {
      "site_order_id": 123,
      "order_number": "P-2026-000123",
      "created_at": "2026-06-16T10:30:00+03:00",
      "fulfillment_status": "new",
      "payment": { "method": "online", "status": "paid" },
      "customer": { "type": "b2c", "name": "Иван Иванов", "phone": "+79000000000", "email": "client@example.com" },
      "delivery": { "method": "delivery", "address": "Пенза, ул. Московская, 1", "comment": "Позвонить за час", "cost": "0.00" },
      "totals": { "items_total": "5900.00", "delivery_total": "0.00", "total": "5900.00", "currency": "RUB" },
      "items": [
        { "line_id": 1, "external_id": "1c-000123", "sku": "BOSCH-GSB13RE", "name": "Дрель ударная BOSCH GSB 13 RE", "unit": "шт", "quantity": "1.000", "price": "5900.00", "total": "5900.00" }
      ]
    }
  ]
}
```

> **Стоимость доставки пока не передаётся.** Поля `delivery.cost` и
> `totals.delivery_total` сейчас **всегда `"0.00"`**, а `totals.total` равен
> `items_total` (сумме строк). Поле — часть финального контракта и наполнится
> реальной стоимостью, когда на сайте появится расчёт доставки в чекауте; до тех
> пор 1С не должна полагаться на доставку из этого ответа.

1С сохраняет `site_order_id`/`order_number`, чтобы не плодить дубли. Один заказ
может прийти повторно, пока 1С не подтвердила приём — обработка **идемпотентна**.

#### `POST /orders/confirm` — подтверждение и движение по оси обработки

Одним эндпоинтом 1С: (1) подтверждает приём и резерв, (2) двигает
`fulfillment_status`. **Статусы передаются раздельно по осям, а не одним полем.**

`fulfillment_status` — только из набора оси обработки:

| Значение | Смысл |
|---|---|
| `confirmed` | заказ принят и резерв подтверждён (товар закреплён) |
| `assembling` | собирается |
| `ready` | собран (готов к самовывозу/передаче в доставку) |
| `shipped` | передан в доставку (можно добавить трек) |
| `completed` | выдан / доставлен |
| `cancelled` | отменён |

Резерв — **атрибут результата**, не статус. Успех двигает обработку в `confirmed`:

```json
{
  "items": [
    {
      "site_order_id": 123,
      "order_number": "P-2026-000123",
      "onec_order_id": "1c-order-987",
      "onec_order_number": "УТ-000987",
      "fulfillment_status": "confirmed",
      "reserve": { "ok": true, "reserved_until": "2026-06-17T10:30:00+03:00" },
      "comment": "Заказ принят и зарезервирован"
    }
  ]
}
```

Провал резерва — заказ **остаётся** `fulfillment=new`, причина по строкам:

```json
{
  "items": [
    {
      "site_order_id": 123,
      "onec_order_id": "1c-order-987",
      "fulfillment_status": "new",
      "reserve": {
        "ok": false,
        "lines": [
          { "external_id": "1c-000123", "requested": "3.000", "available": "1.000", "error": "Недостаточно остатка" }
        ]
      },
      "comment": "Недостаточно товара на складе"
    }
  ]
}
```

Последующая смена статуса — тем же эндпоинтом, только `fulfillment_status`:

```json
{ "items": [ { "site_order_id": 123, "onec_order_id": "1c-order-987", "fulfillment_status": "shipped", "tracking": "PEK-123456", "comment": "Передан в доставку" } ] }
```

Правила:
- идентификатор заказа — `site_order_id` **или** `order_number` (обязателен один);
- `onec_order_id`/`onec_order_number` — id заказа в 1С, должен быть стабильным;
- повторная отправка того же статуса безопасна (идемпотентность);
- **недопустимые переходы сайт отклоняет** по матрице прав
  ([`order-lifecycle.md`](order-lifecycle.md), разд. 7) — например, нельзя
  `completed` из `new` минуя сборку;
- `sync_1c_status = exported` ставится **только при наличии `onec_order_id`**
  (подтверждение приёма 1С); первичный `confirm` заказа в статусе `pending` без
  `onec_order_id` → ошибка по строке. Оси независимы: ошибка перехода
  `fulfillment` **НЕ откатывает** sync-ack (связка с документом 1С и `exported`
  сохраняются);
- `payment_status` и `sync_1c_status` 1С **не присылает**.

Сайт по факту смены статуса: сохраняет его, пишет историю, шлёт уведомление
клиенту в MAX (если подписан) на переходах `confirmed/ready/shipped/completed`.

**Ответ сайта на `POST /orders/confirm`** — `200 OK`, результат **по каждой строке**
(батч обрабатывается построчно, одна плохая строка не валит остальные):

```json
{
  "items": [
    {
      "site_order_id": 123,
      "order_number": "P-2026-000123",
      "status": "ok",
      "sync_1c_status": "exported",
      "fulfillment_status": "confirmed",
      "detail": ""
    }
  ],
  "batch_uid": "0f3c1e54-9b2a-4f0e-8a1c-7c2d9b1f3a44"
}
```

| Поле строки | Смысл |
|---|---|
| `status` | `ok` — строка принята; `error` — заказ не найден / провал резерва / недопустимый переход |
| `sync_1c_status` | ось выгрузки после обработки (`exported`, если был `onec_order_id`) |
| `fulfillment_status` | ось обработки после применения перехода |
| `detail` | текст ошибки при `status="error"` (иначе пусто) |

Даже при `status="error"` HTTP-код остаётся `200` — это **результат строки**, а не
сбой запроса. Связка с документом 1С (sync-ack) фиксируется независимо от ошибки
перехода обработки (оси независимы). Причины ошибок дублируются в журнал прогона
(`SyncLog`, `batch_uid`).

## 6. Ответы и обработка ошибок

Два режима ответа:

- **Асинхронные** `products/import` и `products/update` → **`202 Accepted`**
  `{ "batch_uid": ..., "status": "accepted", "accepted": N }`. Итог — опросом
  `GET /sync/<batch_uid>` (см. 5.3).
- **Синхронные** `prices/update` и `stocks/update` → **`200 OK`** со сводкой прогона
  сразу (та же структура счётчиков):

```json
{
  "created": 0,
  "updated": 3,
  "skipped": 0,
  "uncategorized": 0,
  "errors": 0,
  "batch_uid": "0f3c1e54-9b2a-4f0e-8a1c-7c2d9b1f3a44"
}
```

| Поле | Значение |
|---|---|
| `created` | создано новых товаров (для `products/import`) |
| `updated` | обновлено существующих / применено цен-остатков |
| `skipped` | пропущено (нет товара при update-only; нет цены/остатка в строке) |
| `uncategorized` | создано без категории (ушли в «Неразобранные» на сайте) |
| `errors` | строк с ошибкой/конфликтом — разобрать по `batch_uid` в админке сайта |
| `batch_uid` | идентификатор прогона; назвать его при разборе проблем |

Те же счётчики для импорта приходят в ответе `GET /sync/<batch_uid>` после `finished=true`.

**Важно:** HTTP 200 с `errors > 0` означает, что часть строк не принята (битый
формат, конфликт артикула и т.п.). Остальные строки при этом обработаны. Причины
каждой ошибки сайт сохраняет у себя (журнал по `batch_uid`).

### Коды ошибок

| Код | Когда | Действие 1С |
|---|---|---|
| `400` | неверный формат тела (нет `items`, пустой массив, нет идентификатора, кривой тип) | исправить payload, не повторять «как есть» |
| `403` | нет/неверный `X-Api-Key` | проверить токен |
| `404` | неизвестный `batch_uid` в `GET /sync/<batch_uid>` | проверить, что используется `batch_uid` из ответа `202` |
| `503` | сайт не смог поставить импорт в очередь (`products/import\|update`) | **повторить позже** с экспоненциальной задержкой |
| `5xx` / таймаут / сеть | временная проблема сайта | **повторить с экспоненциальной задержкой** (см. ниже) |

### Ретраи

- На `5xx`/таймаут/сетевую ошибку — повтор: 2с, 4с, 8с, 16с (до 4–5 попыток).
- Повторная отправка одних и тех же строк **безопасна**: обмен идемпотентен —
  товар матчится по `external_id` и обновляется, дубли не создаются.
- На `400`/`403` ретраить бессмысленно — это ошибка данных/доступа.

## 7. Форматы значений

- **Числа:** `"5900.00"`, `"5900,00"`, `5900` — все валидны. Дробные у цены — 2
  знака, у остатка — 3 знака.
- **Булево:** `true`/`false`, `1`/`0`, `"да"`/`"нет"`.
- **Пустые поля:** можно не присылать вовсе (а не пустой строкой) — так понятнее.
- **Кодировка:** только UTF-8. Если выгрузка формируется в CSV/Windows-1251 на
  стороне 1С — перекодировать в UTF-8 перед отправкой по API (API принимает JSON
  в UTF-8).

## 8. Размеры пакетов и интервалы запросов

### Размер пакета
- Рекомендуемый размер `items` в одном запросе — **до 500–1000 строк**.
- **Жёсткий лимит** — `ONEC_MAX_ITEMS` (по умолчанию 1000): больше строк → ответ
  `400` (запрос не принимается). Большую номенклатуру слать **частями**.

### Рекомендуемые интервалы (push из 1С по расписанию)

| Операция | Частота | Комментарий |
|---|---|---|
| `snapshot` (GET) | перед циклом сверки цен/остатков | забрать снимок постранично, сравнить у себя |
| `prices/update` | каждые **5–15 мин** или по факту изменения | цены — самое «живое» |
| `stocks/update` | каждые **5–15 мин** или по факту изменения | остатки меняются часто |
| `products/update` | **1–4 раза в сутки** | базовые поля меняются редко |
| `products/import` | **раз в сутки (ночью)** + по запросу | полная/большая выгрузка номенклатуры |
| `sync/<batch_uid>` | каждые **5–15 с** после import/update | опрос статуса, пока `finished=false` |
| `orders/new` (GET) | каждые **1–5 мин** | забор новых заказов; подтверждать приём через `orders/confirm` |

Не слать всё одновременно в один момент — разнести по времени, чтобы не создавать
пиковую нагрузку.

## 9. Тестовый контур

- Сначала всё отлаживается на **тесте**: `https://dev.proff58.ru/api/1c/` с
  **тестовым токеном** и тестовыми данными.
- После приёмки на тесте — переключение на прод `https://proff58.ru/api/1c/` с
  боевым токеном.
- Для проверки достаточно отправить 1–2 товара в `products/import`, затем
  `prices/update` и `stocks/update` по тем же `external_id`, и сверить ответы
  (`created`/`updated`) и наличие товара в админке сайта.

## 10. Чек-лист для разработчика 1С

- [ ] Заголовок `X-Api-Key` во всех запросах.
- [ ] Тело — `{"items": [...]}`, UTF-8, непустой массив.
- [ ] У каждой строки стабильный уникальный `external_id`.
- [ ] Числа — с точкой/запятой, цена 2 знака, остаток 3 знака.
- [ ] Дельта по ценам/остаткам: забрать `GET /snapshot/` постранично, сравнить
      у себя и отправить только изменения.
- [ ] Батчи ≤ 500–1000 строк, большие выгрузки — частями.
- [ ] Расписание: цены/остатки часто, номенклатура — реже.
- [ ] Ретраи на `5xx`/таймаут с экспоненциальной задержкой; на `400`/`403` — нет.
- [ ] Разбор `errors`/`batch_uid` при ненулевых ошибках.
- [ ] Сначала тест-контур, потом прод.

## 11. Инструменты проверки на стороне сайта

Для самопроверки контракта (без реальной 1С) в репозитории есть два инструмента:

**Контракт-smoke живого API** — `scripts/smoke_1c.py` (только stdlib, бьёт по HTTP):

```bash
# проверить все эндпоинты (snapshot / products / prices / stocks / sync / orders),
# включая happy-path и ошибки 400/403/404 + сверку счётчиков и снимка
python scripts/smoke_1c.py --base https://dev.proff58.ru --key <ONEC_API_KEY>
```

> Скрипт **пишет** в БД сервера (создаёт тестовый товар `SMOKE-1C-001`) — гонять
> только против тестового контура. Декодирует ответы как настоящая 1С (UTF-8 → CP1251).

**Демо обмена заказами** — management-команда `demo_1c_orders` (полный round-trip
`export → confirm` на реальных моделях, играет роль 1С):

```bash
python manage.py demo_1c_orders                      # принят + резерв (confirmed)
python manage.py demo_1c_orders --scenario reserve-failed   # провал резерва
python manage.py demo_1c_orders --scenario shipped          # new→confirmed→ready→shipped
python manage.py demo_1c_orders --keep               # оставить демо-заказ в БД
```

Команда печатает JSON, который 1С получит из `orders/new` и пришлёт в `orders/confirm`,
а также итоговые статусы заказа по трём осям. Демо-заказ по умолчанию удаляется.
