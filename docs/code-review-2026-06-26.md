# Ревью кодовой базы «Профессионал» — 2026-06-26

Полное ревью критичных зон backend (Django/DRF). Охвачено: `catalog`, `sync_1c`,
`pricing`, `orders`, сквозная безопасность (включая `accounts`-auth, `ai`-слой,
прод docker/nginx). Метод — параллельный fan-out специализированных ревью-агентов,
каждая находка заземлена в конкретной строке кода.

**Не углублялись** (отдельный проход): frontend (Next.js, ~4.3к строк), бизнес-логика
мелких `core`/`ai` (security-агент затронул их по касательной).

## Общая оценка

Код зрелее среднего. Подтверждённые сильные стороны:

- `Decimal` используется в деньгах последовательно; `price_for()` — действительно
  единая точка расчёта цены, цена всегда серверная (мимо тела запроса).
- Доменные события издаются через `transaction.on_commit`.
- `X-Api-Key` сверяется за константное время (`constant_time_compare`), пустой
  серверный ключ закрывает API.
- IDOR на заказах/корзине нет (фильтр по `user`/активной корзине запросившего).
- Эскалация B2C→B2B для аутентифицированного заблокирована (тип берётся из учётки).
- SQL-инъекций, SSRF, command injection, path traversal — не найдено.

Главная опасность — несколько **«тихих» дефектов**: они не падают, а молча
искажают деньги/данные, поэтому труднее всего обнаруживаются в проде.

## 🔴 Критично — чинить до прода

### 1. `apps/sync_1c/normalizers.py:69` — порча цены при запятой-разделителе тысяч
`to_decimal` делает слепой `.replace(",", ".")`.
- `"1.234,50"` → `"1.234.50"` → `InvalidOperation` → `None` → цена молча `skipped`.
- `"1,234"` (1С может означать 1234) → `"1.234"` → `Decimal("1.234")` = **1.234** —
  цена занижена в 1000× и проходит как валидная. Тихая денежная порча.

**Фикс:** различать роль запятой/точки (одна запятая без точки ⇒ дробь; точка+запятая
⇒ точка-тысячи). Тест: `to_decimal(["1 234,50","1.234,50","1,234","1234.50","1234,50"])`.

### 2. `apps/sync_1c/api/views.py:61-83` — задача Celery ставится до коммита `SyncLog`
`new_import_job()` коммитит `SyncLog`, затем `import_products_task.delay(...)` — без
`transaction.on_commit`. При `ATOMIC_REQUESTS=True` (типично для DRF) `SyncLog`
коммитится в конце вью, а `delay()` уходит сразу → воркер очереди `onec` делает
`SyncLog.objects.get(id)` **до** коммита → `DoesNotExist`. Импорт теряется, 1С уже
получил `202 accepted`.

**Фикс:** ставить задачу в `transaction.on_commit`.

### 3. `apps/sync_1c/use_cases.py:683-768` — пустой `onec_order_id` ⇒ вечная пере-выгрузка заказа
`onec_order_id` объявлен `allow_blank=True`, ack применяется только `if onec_order_id:`.
Если 1С прислала подтверждение с `onec_order_id=""`, для PENDING-заказа вернётся ошибка,
заказ останется `pending` и будет выгружаться снова и снова.

**Фикс:** нормализовать пустую строку в «нет идентификатора» явно, не полагаться на
truthy-проверки вперемешку.

### 4. `apps/catalog/management/commands/import_products.py:42-111` — импорт без `transaction.atomic()`
`bulk_create`/`bulk_update` идут батчами по 1000 без внешней транзакции. Сбой на середине
(IntegrityError, обрыв соединения) → первые батчи закоммичены, остальные нет → каталог в
полу-импортированном состоянии (часть цен/остатков новые, часть старые) на витрине.
Команды `enrich_*` транзакцию используют корректно — здесь её забыли.

**Фикс:** обернуть `handle()` в `with transaction.atomic()`.

### 5. `apps/catalog/management/commands/enrich_attributes.py`, `enrich_tool_type.py` — гонка затирания `attrs_cache`
Команда читает `product.attrs_cache` в память (`iterator(chunk_size=2000)`),
модифицирует и в конце делает `bulk_update(..., ["attrs_cache"])`. Между чтением и записью
параллельный 1С-импорт/админ может изменить `attrs_cache` того же товара (сигнал
`rebuild_attrs_cache`). `bulk_update` запишет устаревший словарь целиком, молча откатив
чужие ключи → товар пропадает из соответствующего фасета. `select_for_update` не используется.

**Фикс:** перечитывать `attrs_cache` под `select_for_update` непосредственно перед записью,
либо обновлять точечно (JSONB-патч), а не словарём целиком.

### 6. `apps/orders/services.py:280-284` — двойная продажа остатка
`place_order` блокирует через `select_for_update` только `Cart`, не `Product`. Проверка
`available_quantity` читается без блокировки строки товара и **нигде не списывает/не
резервирует** остаток. Два покупателя (разные корзины) одновременно оформляют последнюю
единицу → оба проходят проверку → продано 2 при остатке 1. Код выглядит как защита, но ею
не является.

**Фикс:** блокировать `Product.objects.select_for_update()` перед проверкой и атомарно
уменьшать остаток, либо явно задокументировать, что контроль остатка — best-effort UX.
Паттерн `select_for_update` на `Product` в проекте уже есть (`apps/pricing/repositories.py:83`).

### 7. `apps/orders/services.py:290-311` — суммирование разных валют как одного числа
`total` накапливается по всем строкам, а `currency` перезаписывается значением последней
строки. Корзина с товарами в RUB и USD (модель `PriceRecord.currency` это допускает) →
`total = 1000 RUB + 50 USD = 1050`, `currency = "USD"`. Денежный итог неверен и необнаружим.
То же в `get_cart_view`.

**Фикс:** проверять единство валюты строк при сборке заказа/корзины, падать при расхождении.

## 🟠 Высокое

### 8. `config/settings/base.py:21` — небезопасный fallback `SECRET_KEY`
`SECRET_KEY = env("DJANGO_SECRET_KEY", default="insecure-change-me-in-prod")`. Если env не
задан/не подхватился — прод поднимется с публично известным ключом → подделка session-cookie
и подписанных токенов (сброс пароля) вплоть до входа за `is_staff`.

**Фикс:** в `prod.py` — `SECRET_KEY = env("DJANGO_SECRET_KEY")` без дефолта (fail-fast) +
assert, что значение ≠ дефолта.

### 9. Весь API — отсутствует throttling/rate-limit
`REST_FRAMEWORK` не задаёт `DEFAULT_THROTTLE_CLASSES`. Следствия: brute-force статического
`X-Api-Key` на неограниченной скорости; флуд заказов/корзин гостем (`AllowAny`), спам в
очередь 1С через `sync_1c_status=pending`; дешёвый DoS на дорогих фасетах (2N+ запросов на хит).

**Фикс:** `AnonRateThrottle`/`ScopedRateThrottle`, жёсткие лимиты на `/api/1c/` и оформление;
на nginx — `limit_req` для `/api/1c/` и `/api/orders`.

### 10. `apps/catalog/signals.py:53-59` — кэш не инвалидируется после пакетного импорта
`bulk_create`/`bulk_update` не шлют `post_save`/`post_delete`, поэтому кэш фасетов
(`FACETS_CACHE_TTL`) и дерева держат старые счётчики `in_stock`/диапазон цен до истечения TTL.
Комментарий в коде про «ловит и 1С-обновления цены/остатка» неверен для bulk-пути, который
`save()` не зовёт.

**Фикс:** явная инвалидация кэшей в конце `import_products.handle()`.

### 11. `apps/catalog/facets.py:481` — бренд-фасет рассинхронен с фильтром по регистру
GROUP BY `brand` без нормализации регистра выдаёт раздельные «Bosch»/«BOSCH», а фильтр —
`brand__iexact` (объединяет). Сумма счётчиков фасета ≠ числу товаров в выдаче. Ломает
инвариант «список = счётчики фасетов».

**Фикс:** нормализация бренда на импорте либо `GROUP BY Lower("brand")`.

## 🟡 Среднее

- **`apps/catalog/facets.py:155`** — MULTISELECT по EAV нереализуем (`unique_together(product,
  attribute)` запрещает >1 строки на атрибут), но тип объявлен и включается в выборку →
  скрыто неверные фасеты при первой multiselect-характеристике.
- **`apps/orders/services.py:61-69`** — lost update в корзине: `item.quantity += qty` без
  `F()`/блокировки, двойной клик теряет инкремент. Фикс: `F("quantity") + qty`.
- **`apps/orders/api/views.py:51-55`** — `get_or_create` корзины под частичным
  uniq-constraint → при гонке первого захода возможен `IntegrityError`/500 (не перехвачен).
- **`apps/orders` (merge)** — гостевая корзина не сливается с пользовательской при логине →
  «корзина пропала» после входа (бьёт по B2B-флоу, они почти всегда залогинены).
- **B2B-гость** (`apps/orders/services.py:247-250`) — гость может прислать `customer_type="B2B"`
  + ИНН: заказ помечен оптовым (реквизиты), а посчитан по рознице. Рассинхрон снимка и расчёта.
  То же для аутентифицированного при `customer_type=B2B`, но `is_b2b=False`.
- **`apps/sync_1c/api/parsers.py:54`** — fallback `errors="replace"` маскирует битую кодировку
  → mojibake кириллицы в `name`/`code_1c` вместо явного 400.
- **`apps/sync_1c/api/parsers.py:34`** — `media_type='*/*'` + `stream.read()` целиком без
  app-лимита размера (только nginx `client_max_body_size 20M`); `ONEC_MAX_ITEMS` проверяется
  уже в задаче, а сырой ввод уходит в Celery до этой проверки.
- **`apps/sync_1c/api/permissions.py`** — статический неротируемый общий ключ 1С без лимита
  попыток и без логирования 403. При утечке ключа — массовая подмена цен/остатков. Рекомендация:
  ротация, IP-allowlist 1С на nginx, лог 403, рассмотреть HMAC-подпись тела.
- **`apps/sync_1c/pricing.py:44`, `stock.py:44`** — для товара без `code_1c` (заматчен по
  `article`) skip-unchanged не работает и историческая запись цены/остатка не пишется → ложные
  `updated` и пробел в истории.
- **`config/settings/prod.py:14`** — при незаданном `DJANGO_ALLOWED_HOSTS` `CSRF_TRUSTED_ORIGINS`
  вычисляется пустым (localhost отфильтрован) → вход в админку по HTTPS молча ломается. Фикс:
  требовать непустой публичный хост (fail-fast), запретить `*` в проде.
- **`apps/orders/api/views.py:138-181`** — анонимное оформление заказа без anti-automation
  (капча/throttle): автосоздание фейковых заказов с чужими телефонами/email.
- **`docker/nginx/default.conf`** — нет security-заголовков (`X-Content-Type-Options`,
  `Referrer-Policy`, CSP, `Permissions-Policy`).

## Проверено и безопасно (чтобы не плодить ложные тревоги)

- IDOR заказов/корзины — нет (`apps/orders/api/views.py:185,203` фильтруют по `user`; строки
  корзины изолированы по активной корзине запросившего).
- Манипуляция ценой через тело запроса — нет (`serializers.py:154-176` игнорирует price-поля,
  цена всегда из `price_for`).
- Timing-attack на `X-Api-Key` — нет (`constant_time_compare`, пустой ключ закрывает API).
- SQL-инъекции — нет (фасеты на ORM с guarded `Cast`; единственный `cursor.execute("SELECT 1")`
  — в healthcheck).
- SSRF / command injection / path traversal — AI-слой детерминированный без исходящих HTTP;
  нет `subprocess`/`os.system`/`requests`/`urlopen`; загрузки файлов через публичный API нет.
