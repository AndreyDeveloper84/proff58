### 6.2. Что показала выборка целиком (49 наших перфораторов 4 брендов)

Формат `article` у наших товаров:

| Бренд | всего | `article` пуст | `РСВ-…` (мусор) | `NN/N/N` (код производителя) | обозначение модели | код в названии |

- **`РСВ-…` — не артикул, а внутренний код поставщика и он НЕ уникален.** В каталоге
  2817 товаров с таким `article`; 577 групп дубликатов. `РСВ-140807` висит одновременно
  на «Перф. П-900к-в ВИХРЬ», «Перф. П-1200к-м ВИХРЬ» и «Перф. П-26/800ЭР Интерскол»;
  `РСВ-` (пустой хвост) — на 31 товаре от радиатора до швабры. **Матчить по нему нельзя
  ни при каких условиях.**
- **`75/3/2` и `72/3/2` — это один и тот же порядковый код у разных брендов**

### 6.4. Архитектурный вывод для Phase 4

1. **Ключ матчинга — `(бренд, нормализованная модель)`.** Модель извлекается из `name`
   (у 1С она всегда в названии), нормализация — транслит + удаление разделителей.
2. **`article` — не ключ, а подтверждение.** Правило: если `article` матчится форматом
   бренда (`^\d+/\d+/\d+$` для Ресанты/ВИХРЯ, обозначение модели для ЗУБРа) и совпал с
   `sku`/«Артикул» карточки — считать матч подтверждённым (confidence high). Если
   `article` начинается на `РСВ-` — **игнорировать поле целиком**, не понижая матч.
3. **`code_1c` в матчинге не участвует** — это наш внутренний идентификатор, у
   производителя его нет по определению. Он остаётся ключом записи в нашу БД.
4. **Строгая нормализация обязательна, подстрочный матч запрещён.** Проверено на живом
   примере: `ЗП-2680` является подстрокой ключа `ЗП-26-800` — наивный `in` даёт ложное
   склеивание двух разных моделей. Сравнивать только полное равенство нормализованных
   ключей, иначе — в отчёт как «неоднозначно».
5. **Дубли на нашей стороне разбирать вручную.** `П-800к` (44514) и `П-800к-в` (44504),
   `П-900к` (44505) и `П-900к-в` (44515) ведут на одну карточку источника; у Интерскола
   `П-26/800ЭР` заведён дважды (44510, 44511), `П-30/900ЭР` — дважды (44512, 44513).
   Импортёр должен позволять матч «многие к одному» и писать это в отчёт.

**Итог для Phase 3 — чего не хватает и как закрывать:**

1. **`power` у Ресанты** — единственный носитель — краткая сводка `dl--product__cart--summary`
   / `itemprop=description` (`«SDS-Plus, 900 Вт, 4,3 Дж, …»`) и обозначение модели
   (`П-30-900К` → 900 Вт). Парсер обязан уметь читать сводку; у нас та же мощность уже
   извлекается регуляркой из **нашего** названия (Phase 0.5) — источник тут не нужен.
2. **`motor_type`** — есть только у Интерскола. Для Ресанты/ВИХРЯ/ЗУБРа не выводится
   из карточки вообще: либо оставлять пустым, либо доопределять по правилу
   «бесщёточный упомянут в названии/описании → brushless, иначе не заполнять».
3. **`power_source`** — ни один источник не даёт явно; выводится детерминированно
   (есть `Напряжение питания 220-230 В` → `mains`; модель в разделе «Аккумуляторный
   инструмент» → `battery`). Правило, а не парсинг.
4. **`voltage` у Интерскола** — отсутствует; для сетевых моделей подставлять 220 В
   правилом, не выдумывать из карточки.
5. **`battery_capacity` / `battery_included`** — по перфораторам источники этого
   не отдают структурно; аккумуляторные модели проверять отдельно на Phase 3.
6. **Нормализация значений обязательна перед записью в EAV:**
   - `no_load_speed` (`decimal`) ← источники дают диапазон `0-1100`, `0-1240` → брать
     верхнюю границу;
   - `voltage` (`decimal`) ← `220-230В, ~50 Гц` / `230/50` → извлекать первое число;
   - `chuck` (`select`) ← `SDS-PLUS` / `SDS Plus` / `sds-plus` → одна опция `sds-plus`
     (в БД уже есть `sds-plus`, `sds-max`);
   - `motor_type` (`select`) ← `щеточный` → `brushed` (опции `brushed`/`brushless` есть);
   - `power_source` (`select`) ← опции `mains`/`battery` есть.
   Новых `Attribute` и `AttributeOption` создавать не требуется.
7. **Вес брать нельзя как есть:** у Ресанты/ВИХРЯ `Вес, кг` = брутто с кейсом (4.926 кг
   при нетто 2.7 кг), у ЗУБРа поля разделены (`Масса изделия` / `Масса в упаковке`),
   у Интерскола `Вес, кг` = нетто. Атрибута веса у нас всё равно нет — просто не берём.
