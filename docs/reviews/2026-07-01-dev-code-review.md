## Blocker

### 1. Присвоение гостевых заказов по непроверенному телефону

`RegisterView` разрешает создать аккаунт с произвольным номером и сразу вызывает `claim_guest_orders()`. Сервис привязывает к аккаунту все гостевые заказы с совпадающим `customer_phone`. Злоумышленник может зарегистрировать ещё не занятый номер жертвы и получить состав заказов, контактные данные и B2B-реквизиты.

Затронуто:

- `apps/accounts/api/views.py:55`
- `apps/orders/services.py:346`

Требуется:

- привязывать заказы только после подтверждения владения телефоном через OTP;
- нормализовать телефон до поиска;
- выполнять привязку транзакционно и оставлять аудит;
- добавить негативный тест: регистрация без подтверждения не получает гостевые заказы.

### 2. Webhook ЮKassa доверяет типу события из публичного payload

Платёж повторно запрашивается через API ЮKassa, но ветка обработки по-прежнему выбирается по исходному `payload["event"]`. При наличии ID платежа можно отправить `payment.canceled`, даже если проверенный объект имеет статус `succeeded`, и нарушить локальную платёжную state machine.

Затронуто:

- `apps/payments/services.py:128`

Требуется:

- определять переход только по статусу проверенного объекта ЮKassa;
- сверять ID, `paid`, сумму, валюту, metadata заказа и допустимость перехода;
- запретить регресс терминальных состояний;
- оставить `PAYMENTS_ENABLED=False` до исправления и прохождения тестов webhook state machine.

## Major

### 3. Удаление аккаунта не удаляет все персональные данные

Обезличиваются `User` и снимки заказов, но в `Profile` остаются название организации, ИНН, КПП, юридический адрес и данные согласия.

- `apps/accounts/api/views.py:189`
- `apps/accounts/models.py:69`

Нужно определить retention-политику и транзакционно очистить либо удалить профиль и связанные персональные данные.

### 4. Первый GET избранного может завершиться ошибкой 500

`WishlistItem` объявлен в `apps/accounts/wishlist.py`, который Django не импортирует при загрузке приложения. Тест маскирует проблему: сначала выполняется POST, где модуль импортируется вручную, и только затем GET.

- `apps/accounts/wishlist.py:11`
- `apps/accounts/api/views.py:98`

Модель следует перенести в `models.py` либо гарантированно зарегистрировать при старте. Нужен тест пустого GET сразу после запуска приложения.

### 5. SessionAuthentication не состыкован с CSRF на frontend

Frontend не получает и не передаёт CSRF-токен для защищённых POST/PATCH/DELETE. Logout не ожидается перед навигацией и его ошибка игнорируется: интерфейс может показать выход, хотя сессия останется активной.

- `frontend/lib/auth.ts:32`
- `frontend/app/account/profile/page.tsx:47`
- `config/settings/base.py:169`

Нужны единый API-клиент с `X-CSRFToken`, явная CSRF-инициализация и обработка ошибок мутаций.

### 6. Доставка не интегрирована в checkout

Checkout принимает произвольные `delivery_method` и `delivery_address`. Сервер не проверяет зону, не рассчитывает стоимость и не включает доставку в итог заказа. СДЭК отсутствует. Data-миграция создаёт неподтверждённый адрес и пороги 5 000/10 000 ₽ вместо согласованного порога 7 000 ₽.

- `apps/orders/api/serializers.py:173`
- `apps/orders/services.py:270`
- `apps/delivery/migrations/0002_default_zones.py:7`

Стоимость и способ доставки должны рассчитываться сервером и сохраняться снимком в заказе. Временные адреса нельзя создавать production-миграцией.

### 7. Sourcing может потерять найденные данные

`ExternalCall` переводится в `ok` до сохранения findings. При сбое между этими действиями повторный запуск увидит `ok`, пропустит вызов и не восстановит находки. Кроме того, worker, не владеющий `running/unknown` попыткой, считает её успешной и может преждевременно завершить run как `ok`.

- `apps/ai/services.py:369`
- `apps/ai/services.py:381`

Финализация вызова и идемпотентное сохранение результата должны образовывать согласованный протокол. Чужой `running` нельзя трактовать как успех.

### 8. Бюджет sourcing некорректен на границе суток

Резерв создаётся для дня начала, но снимается со строки дня завершения. При переходе через полночь старый резерв зависнет, а новый может стать отрицательным. Фактическая стоимость не ограничена зарезервированным потолком; `provider_idempotency_key` не сохраняется.

- `apps/ai/services.py:313`
- `apps/ai/services.py:392`
- `apps/ai/services.py:426`

Вызов должен хранить ссылку на конкретную бюджетную строку/дату. Стоимость необходимо валидировать до reconciliation.

### 9. Провенанс можно повысить через недоверенный ответ источника

Guardrail не ограничивает `source_name`. Внешняя находка может объявить источник `manual` и получить максимальный приоритет. Источник должен назначаться доверенным адаптером, а не содержимым ответа.

- `apps/ai/sourcing/guardrails.py:15`
- `apps/ai/services.py:450`

Дополнительно применение `select/multiselect` записывает строку в `value_text`, хотя доменная модель читает такие атрибуты из `value_option`.

- `apps/catalog/provenance.py:66`

### 10. Аналитика не получает событие успешной оплаты

Аналитика подписана на `order_paid`, а платежный сервис отправляет `payment_succeeded`. В результате `PAYMENT_SUCCESS` не записывается.

- `apps/analytics/receivers.py:9`
- `apps/payments/services.py:176`

Следует оставить один канонический доменный event и контрактный тест «успешный webhook → одно событие аналитики».

### 11. Недостаточная защита auth-endpoints

Для login/register/OTP отсутствует throttling. Регистрация проверяет только длину пароля, не используя Django password validators. Смена телефона не подтверждает владение новым номером.

- `apps/accounts/api/serializers.py:18`
- `apps/accounts/api/views.py:220`
- `config/settings/base.py:169`

### 12. Частичный возврат помечает весь платёж возвращённым

При передаче частичной суммы весь `Payment` и заказ получают статус `REFUNDED`. Нет проверки `0 < amount <= payment.amount`; один idempotency key исключает несколько частичных возвратов.

- `apps/payments/services.py:207`

Нужна отдельная модель/история возвратов и вычисляемый агрегатный статус платежа.
