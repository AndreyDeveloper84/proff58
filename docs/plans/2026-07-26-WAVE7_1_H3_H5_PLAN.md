## 4. H3 — default v2 CI replay + release manifest

**Проблема.** Gate 2.0 существует, но запускается руками. Ничто не мешает изменить
ruleset или манифест и не заметить, что точность упала или что артефакты
рассинхронизировались.

**Задачи.**

1. **CI job `catalog-rules-gate`** в `.github/workflows/tests.yml` (или отдельным
   workflow): прогон `catalog_rules_gate_validate` на замороженном sample
   (`apps/catalog/tests/fixtures/phase7d-gate-sample-official.json` + `phase7d-labels.json`)
   против **default** ruleset. Exit code команды = статус job (0 → pass; 1/2/3 → fail).
   Джоба обязана падать при любом дрейфе ruleset/manifest/matcher.
2. **Release manifest** — единый артефакт версии контура, связывающий:
   `ruleset_path` + `ruleset_hash`, `corpus` + hash, `taxonomy_identity_hash` +
   `manifest_semantic_hash`, `matcher_version`, `gate_version`, метрики последнего
   пройденного gate (rows, precision, Wilson 95%), `artifact_sha256` всех входов.
   Детерминированный, byte-stable (без `generated_at` в canonical-части).
3. **Команда генерации/проверки** release manifest (`--check` в CI: расхождение
   пересчитанного и зафиксированного → fail).
4. Документ `docs/catalog/rules-release-manifest.md`.

**Критерии приёмки.**

- CI зелёный на текущем `dev`; искусственная порча ruleset в ветке-пробе роняет job
  с exit 1 или 2 (доказать в протоколе);
- release manifest воспроизводится двумя прогонами байт-в-байт;
- catalog suite и полный regression — на baseline (`2 failed` окружения, не больше);
- протокол `scratchpad/wave7/wave7-h3-report.md` в формате H1/H2.

**Зависимость:** снята — коммиты H2 в `origin/dev` с 2026-07-26, CI видит и
`rules_gate.py`, и команду.

## 5. H4 — re-gate на canonical taxonomy + clean-taxonomy check

**Проблема.** Замороженный 7D sample несёт **legacy** `taxonomy_hash` (`b357be60…`),
поэтому gate проходит только с поблажкой `--allow-legacy-taxonomy-hash`. Пока
поблажка нужна, «зелёный gate» не является полным доказательством.

**Задачи.**

1. **Re-gate:** перевыпустить gate-sample с canonical `taxonomy_hash`
   (`fc13be78…`), перепривязать существующую разметку (`phase7d-labels.json`,
   103 строки, 102 correct) без переразметки смысла — только смена binding, с
   доказательством, что множество строк и ground truth не изменились.
2. Добиться `gate_passed=true` **без** legacy-флага; порог precision ≥ 0.99,
   rows ≥ 100 (recomputed, Wilson 95% в отчёте).
3. **Clean-taxonomy check:** довести манифест до состояния без «серых» записей —
   разобрать 15 `pending_business_review` (11 legacy_unknown + 4 unused) и 4 unused
   опции. Порядок работы: готовится таблица «тип → сколько товаров → откуда пришёл →
   предлагаемое решение (оставить / слить в X / удалить)», владелец утверждает пачкой.
   **Самостоятельные слияния и сплиты типов запрещены** — это продуктовое решение.
4. Staging: read-only `catalog_taxonomy_reconcile` (ожидание blocking drift = 0),
   затем no-op `load_tool_types` — **по отдельному GO**, с pg_dump по
   `docs/catalog/operations/pgdump-policy.md`.
5. Решить судьбу legacy-флага: оставить как исторический механизм (для replay старых
   артефактов) или вывести из употребления после re-gate.
6. **Снять поблажку из CI (H3).** Джоба `catalog-rules-gate` содержит
   `env.LEGACY_TAXONOMY_HASH` и передаёт `--allow-legacy-taxonomy-hash` в оба шага.
   Пока переменная там, зелёный CI — неполное доказательство. Убрать вместе с
   re-gate, тем же коммитом.
7. **Перевыпустить release manifest тем же коммитом**, что и новый sample: evidence
   манифеста ссылается на `apps/catalog/tests/fixtures/`, расхождение уронит
   `--check` (процедура — `docs/catalog/rules-release-manifest.md`).

**Критерии приёмки.**

- gate проходит на canonical binding без `--allow-legacy-taxonomy-hash`;
- `catalog_taxonomy_reconcile --fail-on blocking` на staging = 0 blocking;
- `pending_business_review` = 0 либо каждая оставшаяся запись имеет письменное
  решение владельца в протоколе;
- негативная матрица H2 (tamper-тесты) остаётся зелёной на новом sample;
- протокол `scratchpad/wave7/wave7-h4-report.md`.

**Риск:** самая тяжёлая стадия — требует продуктовых решений и работы со staging.
Планировать отдельное окно, при необходимости — два.

## 6. H5 — reverse migration hardening

> **Трактовка подтверждена владельцем 2026-07-26.** В исходной строке H5 был назван
> «reverse migration hardening» без расшифровки; принятое ниже определение — рабочее
> ТЗ стадии.

**Определение стадии.** Обратимость изменений словаря и применённых
предложений: если манифест эволюционировал (переименование/слияние/удаление опции)
или предложения были применены к товарам, должна существовать проверенная процедура
отката, а не только форвардный путь.

**Задачи.**

1. Reverse-map изменений манифеста: переход `manifest_version N → N-1`, что
   происходит с товарами, у которых стоит исчезнувшая опция; fail-closed при
   невозможности однозначного отката.
2. Процедура отката применённых `tool_type` (снимок «до» → откат → post-audit),
   согласованная с `docs/catalog/operations/rollback.md`.
3. Тесты: откат идемпотентен; частичный сбой не оставляет полуприменённого
   состояния; попытка отката поверх изменившегося baseline → conflict, не молчаливая
   перезапись.
4. Связка с `future_evolution.immutable_option_identity` (`option_uid`) из H1 —
   решить, вводим ли стабильный идентификатор опции сейчас или фиксируем как долг.

**Критерии приёмки.** Документированная и покрытая тестами процедура отката;
негативные сценарии fail-closed; протокол `scratchpad/wave7/wave7-h5-report.md`.
