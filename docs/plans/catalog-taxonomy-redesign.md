# Редизайн таксономии каталога «Профессионал»

> Статус: **черновик плана (Фаза 2, на утверждение владельцем)**. Фаза 1 (аудит)
> выполнена — см. `docs/reports/catalog-taxonomy-*.md`. Код данных/дерева **не
> менялся**; этот документ — проект решения.

## 1. Цель

Спроектировать стабильную публичную иерархию каталога как основу для навигации,
SEO, фильтров/фасетов, импорта из 1С, карточек, хлебных крошек, посадочных
страниц и B2B/B2C — без дублей и двусмысленностей, безопасно для существующих
URL/PLP/фильтров/импорта.

Ключевой принцип (ADR-0001): не путать **категорию** (узел дерева) с **tool_type**
(вторая ось навигации / SEO-фасет), **характеристикой** (EAV), **брендом**
(`Product.brand`), **сценарием** и **SEO-посадочной**.

## 2. Текущие проблемы (из аудита, на реальном дампе 47 224 товара)

Маппинг здоров: 94.4% on_site, 5.6% намеренно скрыто (грязь 1С), 0 сирот.
Проблема — **форма дерева**, не покрытие. Находки (`catalog-taxonomy-audit.md`):

| Код | Проблема | Масштаб |
|---|---|---|
| F1 | Электроинструмент разбит по **питанию** (Сетевой 1971 / Аккумуляторный 694), а не по типу товара | high |
| F2 | Корни-листья без структуры: Хозтовары 4642, Электрика 2523, Измерительный 1660 | high |
| F4 | Узлы-бренды в дереве: «Запчасти Hitachi», «ЗУБР», «ЭХО», «Оснастка Hitachi» | high |
| F3 | Мусорные листья: «Прочая оснастка» 2141, «Прочее» | medium |
| F5 | Дубль оси: 19 листьев-категорий совпадают со значением `tool_type` (вся ветка «Оснастка»: Буры/Свёрла/Коронки/Биты…) | medium |
| F6 | 15 крупных одиночных листьев — кандидаты на навигацию через TypePanel | medium |
| F7 | `recategorize`-цели без раздела-приёмника (Сварка, Связь/Радио…) | low |

## 3. Принципы новой иерархии

1. Категория отвечает на «**что это за товар?**». Питание/размер/патрон/бренд/сценарий — не категории.
2. **Один товар — одна основная публичная категория** (уже гарантировано: `Product.category` — один FK, M2M нет).
3. Категория не дублирует фасет. Бренд → `Product.brand`. Характеристика → EAV.
4. SEO-посадочная (`category + facet`/`category + tool_type`) ≠ узел дерева. Дерево не должно блокировать будущие SEO-роуты (#25).
5. Широкий раздел навигируется **второй осью** (`tool_type` / TypePanel), а не десятками узлов.
6. Публичное дерево ≠ дерево 1С; связь — через `external_id` в `group_mapping.json`. Грязь 1С — под скрытым корнем (`on_site:false`, ADR-0002).
7. Бизнес-логика — на `slug`/`code`/`id`, **не** на русском label.

## 5. Целевое дерево — приоритетный раздел (Электроинструмент)

Узлы = типы товара (уже описаны как `tool_type` в `data/tool_type_rules.json`,
покрытие подтверждено в Фазе A — 96%). Питание становится фасетом, а не веткой.

```text
Электроинструмент            (electroinstrument)
├── Перфораторы              (perforatory)
├── Отбойные молотки         (otboynye-molotki)
├── Дрели и шуруповёрты      (dreli-shurupoverty)
├── Болгарки (УШМ)           (ushm)
├── Шлифовальные машины      (shlifmashiny)
├── Лобзики                  (lobziki)
├── Пилы                     (pily)
├── Фрезеры                  (frezery)
├── Электрорубанки           (rubanki)
├── Строительные миксеры     (miksery)
├── Строительные пылесосы    (pylesosy-str)
├── Краскораспылители        (kraskoraspyliteli)
├── Фены строительные        (feny)
└── … (прочие типы из tool_type_rules)

Аккумуляторы и зарядные → выносим из «инструмента» в раздел
«Аккумуляторы и ЗУ» как товары-комплектующие (akkumulyatory-zu),
а НЕ как ось питания инструмента.
```

Фасеты для PLP (контекстные, см. §8):
- базовые: Наличие, Бренд, Цена, **Питание (power_source)**;
- технические (зависят от типа): Мощность, Энергия удала, Тип патрона, Диаметр диска, Напряжение, Ёмкость АКБ и т.д. (уже в `attribute_rules.json`).

> Полное целевое дерево остальных разделов (Оснастка, Ручной, Сварка, …) —
> отдельные итерации Фазы 2 после утверждения подхода на Электроинструменте.

## 6. Что есть категория / фасет / SEO-посадочная (примеры)

| Сущность | Роль | Где живёт |
|---|---|---|
| Перфораторы, УШМ, Свёрла, Коронки | категория **или** tool_type (по разделу) | `Category` / `tool_type` |
| Bosch, Hitachi | бренд | `Product.brand` |
| SDS-Plus, 125 мм, Аккумуляторный | характеристика/опция | EAV (`chuck_type`, `disc_diameter`, `power_source`) |
| «Для бетона», «до 10 000 ₽» | сценарий / ценовой пресет | фасет / подборка, не дерево |
| «Перфораторы SDS-Plus», «УШМ 125 мм» | SEO-посадочная | `category + facet` route (#25, отложено) |

**Решение по «Оснастке» (F5):** в разделе с `inherit_1c_subgroup` под-типы
(Буры/Свёрла/Коронки) сейчас дублируются как категория-лист **и** как `tool_type`.
Целевое: оставить их **категориями-листьями** (так приходят из 1С-подгрупп и
стабильны), а `tool_type` в этом разделе не дублировать — освободить вторую ось
под под-типы внутри листа (например, «Свёрла по металлу/бетону/дереву»).

## 7. URL-стратегия, slug, canonical, redirects

- **Категорийные URL:** `/catalog/<slug>` (плоский resolve по последнему slug — как сейчас).
- **Фасетные:** `/catalog/<slug>?brand=…&attr_<slug>=…&power_source=…` (уже поддержано).
- **Будущие SEO-фасеты:** `/catalog/<slug>/<facet>` — закладываем совместимость, не реализуем без отдельного решения.
- **Slug:** латиница, стабильный, человекочитаемый, из канонической карты (не из имени 1С). Переход кириллица→латиница через карту `old_slug → new_slug`.
- **Redirects:** нужна модель/конфиг 301 (сейчас её нет — смена slug = 404). Заводим в Фазе 5.
- **Canonical:** один canonical на категорию; фасетные комбинации — `canonical` на базовую категорию (кроме разрешённых SEO-посадочных).
- **Окно безопасности:** сейчас `robots.txt = Disallow: /`, sitemap нет, индексации нет → redirect-долг минимален. Перестройку делать **до go-live**.

## 8. Совместимость с PLP-фильтрами

Механика уже есть (`facets.build_facets`, `queries._category_filter_attributes` —
наследование фильтров вверх по дереву, `range_filter_attributes`, `tool_type_facets`).
Для каждой целевой категории определяем:
- `basic_filters`: Наличие, Бренд, Цена, Питание;
- `technical_filters`: атрибуты из `attribute_rules.json` (через `CategoryAttribute.is_filter`);
- `navigation_facets`: `tool_type` (для широких разделов, TypePanel);
- `scenario_chips`: коммерческие/SEO-сценарии (позже).

Риск к исправлению: привязка атрибутов к категории по **русскому имени**
(`attribute_rules.tool_types[].category`) — перевести на slug/code (принцип §3.7).

## 10. Definition of Done

- Каждый узел отвечает «что это за товар»; нет узлов-брендов/характеристик/мусора; нет дублей между осями «категория» и «tool_type».
- Один валидный публичный путь на товар; нерасклассифицированное — по политике (скрытый корень).
- Маппинг `1С(external_id) → public_category` полный, идемпотентный; импорт и контент не сломаны.
- PLP/фасеты/breadcrumbs/поиск работают; `attrs_cache` пересобран; counts верны.
- Slug стабильны и латиничны; на каждый изменённый slug есть 301; canonical определён; SEO-дублей нет.
- Бизнес-логика на slug/code; миграции с dry-run + тестами; изменения обратимы.
- Документы в `docs/plans/` и `docs/reports/` актуальны.
