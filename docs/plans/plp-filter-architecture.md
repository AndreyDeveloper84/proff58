# Архитектура фильтров PLP — source of truth

Электроинструмент + оснастка.

Статус: на ревью. Workflow: архитектурный план → ревью → GitHub Issues → реализация.
Issues не создаём до утверждения этого документа.

## 1. Цель
Превратить левый фильтр PLP из «простыни всех атрибутов из базы» в управляемый подбор товара.
Покупатель должен сначала выбрать направление:

- перфораторы;
- дрели;
- шуруповёрты;
- УШМ;
- пилы;
- коронки;
- буры;
- сверла;
- диски;
- оснастка.

И только потом уточнять технические параметры: мощность; энергия удара; тип патрона; диаметр; длина;
посадка; материал; назначение; тип питания; обороты; крутящий момент.

Главная UX-цель: пользователь не должен видеть технический параметр рядом с товарами, к которым этот
параметр не относится. Если пользователь применил фильтр «Диаметр», в выдаче не должны оставаться товары
без диаметра.

## 2. Главный принцип
Фильтр каталога делится на два уровня.

### 2.1. Навигация
Навигация отвечает на вопрос: **что именно ищет пользователь?** Примеры: Перфораторы; УШМ; Шуруповёрты;
Дрели; Коронки; Буры; Сверла; Биты; Диски.

`tool_type` — это навигация, а не обычный фильтр в левом сайдбаре.

### 2.2. Фильтрация
Фильтрация отвечает на вопрос: **какой именно товар внутри выбранного типа нужен?** Примеры: бренд; цена;
наличие; мощность; тип патрона; диаметр; длина; посадка; энергия удара.

## 3. Принятые UX-решения

### 3.1. `tool_type` — панель типов над выдачей
`tool_type` выносится в отдельную панель кнопок над выдачей. Пример:

```text
[Перфораторы] [Дрели] [Шуруповёрты] [УШМ] [Пилы] [Шлифмашины]
```

Для оснастки:

```text
[Буры] [Сверла] [Коронки] [Диски] [Биты] [Пилки] [Насадки]
```

В левом сайдбаре `tool_type` не показываем как обычный чекбокс-фасет.

### 3.2. URL: параметр сейчас, SEO потом
На текущем этапе тип инструмента выводится через URL-параметр:

```text
/catalog/electroinstrument?tool_type=perforatory
/catalog/electroinstrument?tool_type=ushm
/catalog/osnastka-i-rashodniki?tool_type=koronki
```

SEO-роуты вида:

```text
/catalog/perforatory
/catalog/ushm
/catalog/koronki
```

не делаем сейчас. Это отдельная фаза после стабилизации UX, фильтров, данных и аналитики.

### 3.3. На широкой категории технические фильтры скрыты
Для широкой категории без выбранного типа показываем только базовые фильтры: Наличие; Бренд; Цена; Тип
питания, если применим к категории. Технические фильтры появляются только после выбора `tool_type`.

### 3.4. Контекстность
```text
Широкая категория, тип не выбран → только базовые фильтры
Выбран tool_type → базовые + технические фильтры этого типа
Листовая категория → полный релевантный набор, если категория действительно однородная
```

**Технический критерий «широкой категории»** (чтобы реализация не гадала по depth/детям/флагу):

```text
Широкая категория — категория, где:
1. есть несколько значимых tool_type;
2. товары внутри неоднородны по техническим атрибутам;
3. технические фильтры применимы только к части товаров;
4. TypePanel содержит более одного значения с count > 0.
```

Источник режима — явное поле `category_filter_mode = broad | typed | leaf`; на старте допускается авто-определение:
`broad` ⇔ `count(tool_type options с count > 0) > 1`.

## 4. Архитектурный факт
`tool_type` уже существует как EAV-атрибут SELECT. Он не является узлом дерева категорий. Опции `tool_type`
имеют slug:

```text
perforatory
ushm
koronki
sverla
bity
```

Это позволяет быстро сделать TypePanel без миграции модели каталога. Текущий подход:

- `tool_type` остаётся атрибутом;
- TypePanel работает поверх `tool_type`;
- SEO-роуты откладываются;
- дерево категорий не ломаем.

## 5. URL-контракт
Состояние PLP полностью хранится в URL и восстанавливается после перезагрузки.

### 5.1. Тип инструмента
```text
?tool_type=perforatory
```
Это верхнеуровневый параметр, не `attr_tool_type`. Конфликт двух источников разрешаем жёстко:

```text
Если одновременно пришли tool_type и attr_tool_type:
- canonical input = tool_type;
- attr_tool_type для типа инструмента игнорируется/нормализуется;
- frontend не сериализует attr_tool_type для tool_type.
```
(Иначе `?tool_type=perforatory&attr_tool_type=koronki` — неоднозначность «перфораторы или коронки».)

### 5.2. Обычные чекбоксы
```text
?brand=bosch,makita
?stock=in_stock
?attr_chuck=sds-plus
```

### 5.3. Диапазоны
```text
?price_min=5000&price_max=20000
?attr_diameter_min=10.5&attr_diameter_max=20
?attr_length_min=600&attr_length_max=1100
```

### 5.4. UI-state
```text
?sort=price_asc
?view=grid
?page=2
?per_page=24
```
Дефолтные значения не сериализуем.

### 5.5. Reset
`reset all` сбрасывает: `tool_type`; brand; stock; price; attr-фильтры; ranges; page.
При смене любого фильтра `page` сбрасывается на `1`.

## 6. Поведение широкой категории
Пример:

```text
/catalog/electroinstrument
/catalog/osnastka-i-rashodniki
```

### 6.1. Над выдачей
Показываем TypePanel:

```text
[Перфораторы] [Дрели] [Шуруповёрты] [УШМ] [Пилы]
```
или:
```text
[Буры] [Сверла] [Коронки] [Диски] [Биты]
```

### 6.2. В левом фильтре
Показываем только базовые фильтры: Наличие; Бренд; Цена; Тип питания, если применим.

### 6.3. Технические фильтры
Не показываем: энергия удара; тип патрона; диаметр диска; посадка; длина; крутящий момент; напряжение;
диаметр; материал — пока пользователь не выбрал тип товара.

## 7. Поведение выбранного `tool_type`
Пример:

```text
/catalog/electroinstrument?tool_type=perforatory
```

### 7.1. TypePanel
Кнопка «Перфораторы» подсвечена. Повторный клик снимает `tool_type`.

### 7.2. Выдача
Товары отфильтрованы по выбранному типу.

### 7.3. Сайдбар
Показываются базовые фильтры + технические фильтры для выбранного типа.

- **Перфораторы:** Энергия удара; Мощность; Тип патрона; Режимы работы; Вес.
- **УШМ:** Диаметр диска; Мощность; Регулировка оборотов; Посадочный диаметр; Тип питания.
- **Шуруповёрты:** Напряжение аккумулятора; Крутящий момент; Тип патрона; Ёмкость аккумулятора; Наличие АКБ в комплекте.
- **Коронки:** Диаметр; Длина; Посадка; Материал; Назначение.

## 8. Поведение прямой ссылки
Если пользователь открыл `/catalog/electroinstrument?tool_type=perforatory`, система должна сразу восстановить
состояние:

- TypePanel подсвечивает «Перфораторы»;
- товары отфильтрованы;
- счётчик «Найдено N» пересчитан;
- левый фильтр показывает базовые + технические фильтры перфораторов;
- applied chip показывает «Тип: Перфораторы»;
- reset all возвращает широкую категорию.

## 9. Applied chips
Все активные фильтры должны быть видны над выдачей. Примеры:

```text
Тип: Перфораторы ×
Бренд: Bosch ×
Диаметр: от 10,5 до 20 мм ×
Цена: до 20 000 ₽ ×
В наличии ×
Сбросить всё
```

### 9.1. Чип `tool_type`
Для MVP показываем чип типа всегда (`Тип: Перфораторы ×`), даже если TypePanel видна. Чип должен быть спокойным
визуально, чтобы не дублировать панель слишком агрессивно.

### 9.2. Range-чипы
Диапазоны показываем по-русски:

```text
Диаметр: от 10,5 до 20 мм
Длина: от 600 до 1100 мм
Цена: от 5 000 до 20 000 ₽
```

### 9.3. Индивидуальный сброс
Каждый чип можно снять отдельно.

## 10. Приоритеты показа фасетов
Фасет не должен попадать в интерфейс просто потому, что у него есть значения в базе. Порядок принятия решения:

### 10.1. Placement gate
Сначала определяем место показа: `tool_type` → TypePanel; базовые фильтры → sidebar; технические фильтры →
sidebar после выбора типа; сценарии → ScenarioChips; SEO-фасеты → отдельная будущая логика.

Важно: **SEO-фасет ≠ навигационный UI-фасет.** Сегодня `tool_type` рендерим как TypePanel, но завтра
SEO-фасетом может стать «SDS-Plus», «Bosch», «125 мм», «До 10 000 ₽» — и не всё это должно попадать в верхнюю
панель типов. На текущем этапе допускается использовать `CategoryAttribute.is_seo_facet=True` для `tool_type`
как временный источник `is_nav=true`, но долгосрочно нужен отдельный UI-признак:

```text
ui_placement = sidebar | type_panel | scenario_chip
```
или отдельные флаги:
```text
is_navigation_facet
is_scenario_facet
is_sidebar_filter
```

Иначе через несколько итераций `is_seo_facet` начнёт отвечать сразу за SEO, UX и placement — это приведёт к
путанице. Placement определяется UI-признаком, а не SEO-флагом.

### 10.2. Category/tool_type gate
Фасет может попасть в sidebar только если он разрешён для текущей категории или выбранного `tool_type`. Источник:
`CategoryAttribute.is_filter`; наследование от категории/предков; кураторская настройка для типа товара.

### 10.3. Drill-down gate
Из разрешённых фасетов показываем только те, у которых есть значения в текущем контексте. Drill-down не заменяет
настройку релевантности. Он только очищает разрешённые фасеты от пустых значений.

### 10.4. Coverage gate
Если атрибут заполнен у слишком малой доли товаров, он не должен попадать в основные фильтры.

```text
низкое покрытие → скрыть или отправить в “Дополнительные”
coverage < 5% → скрыть или Дополнительные
```

Одного процента мало (20 товаров × 10% = 2 шт — бессмысленно; 10 000 × 4% = 400 шт — возможно в «Дополнительные»).
Coverage gate учитывает **процент + абсолютное количество + бизнес-важность**:

```text
Основной фильтр:  coverage >= 30%  ИЛИ атрибут закреплён куратором.
Дополнительный:   coverage 5–30%.
Скрыть:           coverage < 5%  И нет кураторского закрепления.
```
Финальные числа — ориентиры, уточняются после анализа данных.

## 11. Базовые фильтры
Базовые фильтры не являются жёстким списком для всех категорий.

### 11.1. Почти всегда
Наличие; Бренд; Цена.

### 11.2. Условно
`Тип питания` показываем только там, где он применим к значимой доле товаров. Для электроинструмента — да;
для оснастки и расходников — обычно нет.

## 12. Числовые фильтры

### 12.1. UX
Числовой фильтр отображается одной дорожкой с двумя бегунками. Пример:

```text
Диаметр, мм

●════════════●

[10,5] — [20]
```

Правила: одна дорожка; два бегунка; активный сегмент между бегунками; поля «от/до» остаются; `min=max` разрешён;
запрос не отправляется на каждый пиксель движения; применение происходит на отпускании бегунка, blur или Enter.

### 12.2. Товары без атрибута
Если применён числовой фильтр, товары без этого атрибута исключаются. Пример:

```text
?attr_diameter_min=10.5&attr_diameter_max=10.5
```

В выдаче остаются только товары, у которых есть атрибут `diameter` и значение входит в диапазон.

### 12.3. UX-пояснение
Так как исключение товаров без атрибута может резко уменьшить выдачу, UI должен объяснять это. В подсказке:

```text
Показаны товары, у которых указан диаметр.
Товары без диаметра скрыты фильтром.
```

Для empty-state:

```text
По диаметру 10,5 мм товаров нет.

Часть товаров без указанного диаметра скрыта фильтром.

[Сбросить Диаметр]
[Сбросить все фильтры]
```

Не смешивать обратно товары без атрибута в отфильтрованную выдачу. Если пользователь хочет увидеть их, он должен
явно сбросить фильтр.

## 13. TypePanel counts
Счётчики в TypePanel считаются по принципу own-axis exclude: учитываем категорию, бренд, наличие, цену,
технические фильтры; не учитываем текущий выбранный `tool_type`. Пример:

```text
Выбран brand=Bosch

TypePanel:
Перфораторы 120
Дрели 35
УШМ 48
Шуруповёрты 62
```

Если выбран `tool_type=perforatory`, панель всё равно должна показывать альтернативные типы с их счётчиками,
чтобы пользователь мог переключиться.

## 14. TypePanel order
Порядок типов должен быть стабильным. Приоритет:

1. `sort_order` из `AttributeOption` / `CategoryAttribute`, если есть;
2. иначе count desc;
3. активный тип не перемещаем наверх;
4. нулевые типы — см. правило ниже;
5. если типов больше 10–12, используем горизонтальный scroll или «Ещё».

**Нулевые counts после фильтрации** (чтобы панель не «прыгала» и пользователь не терял выбранный тип):

```text
До применения фильтров: типы с count=0 не показываем.
После применения фильтров:
- активный тип показываем ВСЕГДА, даже если count стал 0;
- остальные типы с 0 — можно скрывать или показывать disabled, но порядок панели не должен резко прыгать.
```

Особенно для empty-state: если выбран `tool_type=perforatory`, а другие фильтры дали 0 товаров, активный тип
остаётся видимым.

## 15. Subcategories vs TypePanel
`subcategories` и `TypePanel` — разные сущности: `subcategories` — дерево каталога; `tool_type` — EAV-навигация.
Если они дублируют друг друга по смыслу, не показывать две одинаковые панели одновременно.

```text
Если TypePanel и subcategories показывают одно и то же, приоритет у TypePanel
на страницах, где tool_type выбран как основной механизм навигации.
```

## 16. Листовая категория
Листовая категория — это не просто категория без детей. Она считается пригодной для полного технического набора, если:

1. у неё нет дочерних категорий;
2. или она явно связана с одним доминирующим `tool_type`;
3. и технические фильтры применимы к значимой доле товаров.

Если категория формально листовая, но товары внутри смешанные, применяется поведение широкой категории:
TypePanel; базовые фильтры; технические фильтры после выбора типа.

## 17. Data quality risk
Контекстные фильтры зависят от заполненности EAV-атрибутов. Если `tool_type`, диаметр, энергия удара, тип
патрона, посадка, материал и др. заполнены плохо, код может быть корректным, но фильтры на витрине будут пустыми
или бесполезными. Перед включением технических фильтров для `tool_type` нужен coverage-отчёт.

### 17.1. Метрика покрытия
```text
coverage(attribute, tool_type) =
товаров выбранного типа с заполненным атрибутом / всего товаров выбранного типа
```

Пример:

```text
Перфораторы:
energy_impact — 78%
chuck — 91%
power — 64%

Коронки:
diameter — 42%
material — 18%
purpose — 25%
```

### 17.2. Правило включения
Высокий coverage → основной фильтр; средний → дополнительный; низкий → скрыть до обогащения.

### 17.3. Риск
Фаза 2 контекстных фильтров зависит не только от кода, но и от качества данных. Если данных нет, сначала нужен
enrichment/backfill, иначе пользователь увидит пустой интерфейс.

## 18. Performance constraints
Facets endpoint — критичный по нагрузке. На больших категориях вроде «Оснастка» drill-down, JSONB range, group-by
и пересчёт счётчиков могут быть дорогими.

### 18.1. Бюджет
Бюджет разделён по уровням (где измеряем):

```text
- backend facets API p95 < 500–800 мс на staging для крупных категорий;
- product list API p95 — отдельно;
- frontend perceived update после клика по фильтру — без full-page spinner, с skeleton/transition.
```

В PR-комментарии фиксируем (чтобы performance-review не был субъективным):

```text
SQL count | total DB time | API response time | category size | active filters
```
Финальный бюджет уточнить после замеров на staging.

### 18.2. Правила реализации
- counts не считать отдельным запросом на каждое значение;
- для brand/stock использовать group-by;
- range-фасеты считать аккуратно;
- проверять SQL count/time на больших категориях;
- не делать N+1;
- не пересчитывать одинаковые базы без необходимости.

### 18.3. Возможные оптимизации
Если facets endpoint станет тяжёлым: кэш facets по ключу `category + tool_type + filters`; GIN-индекс по
`attrs_cache`; переход numeric ranges на relational `value_decimal`; предрасчёт популярных фасетов; отдельная
таблица поискового/фасетного индекса.

## 19. Pricing consistency
Цена в карточке, ценовой фильтр и сортировка по цене должны использовать один и тот же источник цены. Если цена
зависит от роли пользователя, нужно учитывать: B2C; B2B; оптовую цену; авторизованность; доступность цены;
будущий `pricing.price_for`.

```text
Displayed price = price filter = price sort
```

Если сейчас price-фасет считается по `Product.price`, а карточка показывает другую цену, это known limitation и
должно быть явно отмечено.

```text
До role-based pricing: price facet / price sort работают по Product.price
После внедрения pricing: price facet / price sort / card price переходят на единый price_for / effective price contract
```

**Текущая temporary inconsistency (явно).** Сортировка по цене уже переведена на `effective_price` для B2B
(см. реализацию B2B-сортировки), а price facet/filter пока на `Product.price` (retail). Инвариант
`Displayed price = price filter = price sort` — целевой, НЕ текущий:

```text
До завершения role-aware price facets:
- card price может быть B2B/effective;
- sort может быть effective;
- price filter/facet временно остаётся retail;
- это known limitation и должно быть видно в issue/PR.
```

## 28. Риски

coverage-отчётом; обогащением данных; скрытием фильтров с низким покрытием.

### 28.2. Производительность фасетов
Drill-down и JSONB ranges могут быть тяжёлыми. Митигировать: измерениями; group-by; кэшем; индексами; eventual
relational facet index.

### 28.3. SEO-дубли
`?tool_type=`, sort, page, filters создают много URL. Митигировать: canonical; noindex/follow для части
фильтрованных URL; будущими SEO-роутами.

### 28.4. Pricing inconsistency
B2B/B2C цена может расходиться между карточкой, фильтром и сортировкой. Митигировать: единым price contract;
тестами; follow-up на role-aware price facets.

## 30. Release checkpoints (выкатка на dev)
Правило: деплой на dev — после каждого «вертикального среза» (эпика), **backend раньше frontend**, каждый
деплой = чек-поинт с фиксированным чек-листом проверки. Гранулярность = эпик/срез, а не каждый коммит.

### Порядок внутри фазы
1. **Backend-PR → dev → verify (API).** Бэкенд-контракт, как правило, обратно-совместим (добавляет поля/
   параметры) — фронт его игнорирует, ничего не ломая. Поэтому выкатывается и проверяется первым, по API.
2. **Frontend-PR → dev → verify (UI).** Деплоить **только после** того, как backend уже на dev (фронт
   потребляет контракт; выкат раньше = битый/пустой UI). Это и есть видимая пользователю веха.

→ Два деплоя на срез, но одна UX-веха (фича видна только после frontend; backend между ними — тихая
проверка контракта).

### Пример: Фаза 1 (A1 → A2)
- **A1 (#223, backend)** мержим в `dev` при зелёном CI (`pytest apps/catalog apps/pricing`, ruff/black).
  Чек-поинт на dev (через API, без UI):
  - `GET /api/catalog/categories/<slug>/facets/` → `tool_type` с `is_nav:true`, прочие `is_nav:false`;
  - `?tool_type=<slug>` сужает список (`/products/`) и фасеты (`total_products`) **одинаково**;
  - own-axis: панель типов показывает все типы при выбранном;
  - регрессия: brand/stock/price/`attr_*` (+ range #219) работают;
  - перф: время ответа фасетов на крупной категории приемлемо.
- **A2 (#224, frontend)** мержим **после** A1-на-dev; `tsc --noEmit` + eslint чисто. Чек-поинт на
  dev.proff58.ru (UI, §26): TypePanel над выдачей; клик меняет URL и выдачу; активный подсвечен; `tool_type`
  нет в сайдбаре; RU-чипы с единицами; skeleton при смене фильтра; «Найдено N» меняется; empty-state с
  точечным сбросом; восстановление из прямой ссылки.

### Общие правила
- Внутри каждой фазы (B, D, E, F) — тот же порядок: backend-PR → dev → verify → frontend-PR → dev → verify.
- Время суток: backend-срез — в любой момент (невидим); видимый UI-срез — когда есть 15–20 мин спокойно
  прогнать ручной чек-лист, не во время демо/просмотра dev.
- Проверять на 1–2 «тяжёлых» категориях (Электроинструмент, Оснастка) — там и перф, и разнообразие типов.
- План отката: обратно-совместимый backend откатывается легко; для видимого frontend-среза держать быстрый
  revert-PR.
- Чек-лист каждого чек-поинта = DoD соответствующего эпика (§26) + регрессия.
