# Архитектура фильтров PLP

Source of truth для каталога электроинструмента, оснастки и смежных категорий.

Статус: на ревью. Workflow: архитектурный план → ревью → GitHub Issues → реализация.

## 1. Цель
Цель — превратить фильтр каталога из «простыни всех атрибутов из базы» в управляемый подбор товара.
Покупатель должен сначала выбрать направление поиска:

- перфораторы;
- дрели;
- шуруповёрты;
- УШМ;
- пилы;
- коронки;
- буры;
- сверла;
- диски;
- оснастку и т.д.

И только после этого видеть технические уточнения, релевантные выбранному типу товара.

Главный принцип:
> Тип инструмента — это навигация, а не обычный фильтр в левом сайдбаре.
> Левый сайдбар должен уточнять выбор, а не заменять структуру каталога.

## 2. Ключевые UX-решения

### 2.1. `tool_type` выносится в отдельную панель
`tool_type` не должен отображаться как обычный фасет в левом фильтре. Вместо этого он выводится отдельной
панелью над выдачей:

```text
[Перфораторы] [Дрели] [Шуруповёрты] [УШМ] [Пилы] [Шлифмашины]
```

Для оснастки:

```text
[Буры] [Сверла] [Коронки] [Диски] [Биты] [Пилки] [Насадки]
```

Панель типов — это навигация внутри широкой категории.

### 2.2. URL: параметр сейчас, SEO-роуты потом
На текущем этапе выбранный тип инструмента выводится в URL как параметр:

```text
/catalog/electroinstrument?tool_type=perforatory
/catalog/electroinstrument?tool_type=ushm
/catalog/osnastka-i-rashodniki?tool_type=koronki
```

SEO-роуты вида:

```text
/catalog/perforatory
/catalog/ushm
/catalog/koronki
```

не делаем сейчас. Это отдельная фаза после стабилизации UX, фильтров, данных и аналитики.

### 2.3. Широкая категория показывает только базовые фильтры
Для широкой категории без выбранного типа товара показываем только базовые фильтры:

- наличие;
- бренд;
- цена;
- тип питания, если применим.

Технические фильтры скрыты до выбора типа товара. Пример:

```text
Электроинструмент

Панель типов:
[Перфораторы] [Дрели] [Шуруповёрты] [УШМ]

Фильтры:
Наличие
Бренд
Цена
Тип питания
```

### 2.4. После выбора типа появляются контекстные фильтры
Если выбран тип `tool_type=perforatory`, сайдбар показывает базовые фильтры + технические для перфораторов:

```text
Наличие
Бренд
Цена
Тип питания
Энергия удара
Мощность
Тип патрона
Режимы работы
Вес
```

Если выбран `tool_type=ushm`, сайдбар показывает:

```text
Наличие
Бренд
Цена
Тип питания
Диаметр диска
Мощность
Регулировка оборотов
Посадочный диаметр
```

## 3. URL-контракт
Состояние PLP полностью живёт в URL и восстанавливается после перезагрузки.

### 3.1. Тип инструмента
```text
?tool_type=perforatory
```
`tool_type` — верхнеуровневый параметр, не `attr_tool_type`.

### 3.2. Обычные чекбоксы
```text
?brand=bosch,makita
?stock=in
?attr_chuck=sds-plus
```

### 3.3. Диапазоны
```text
?price_min=1000&price_max=10000
?attr_diameter_min=10.5&attr_diameter_max=20
?attr_length_min=600&attr_length_max=1100
```
Контракт диапазона: `code_min / code_max`.

### 3.4. UI-состояния
```text
?sort=price_asc
?view=grid
?page=2
?per_page=24
```
Дефолты не сериализуются.

### 3.5. Reset all
`reset all` сбрасывает: `tool_type`, brand, stock, price, attr-фильтры, range-фильтры, page.
При изменении любого фильтра `page` сбрасывается на `1`.

## 4. Поведение широкой категории
Широкая категория — это категория, где находится много разных типов товаров. Примеры:

```text
Электроинструмент
Оснастка и расходники
Садовая техника
```

На широкой категории без выбранного `tool_type`:

- сверху показывается TypePanel;
- слева показываются только базовые фильтры;
- технические фильтры скрыты;
- H1 и intro остаются общими;
- товары показываются по всей широкой категории.

## 5. Поведение выбранного `tool_type`
Если пользователь выбрал тип `?tool_type=perforatory`, то:

- TypePanel подсвечивает «Перфораторы»;
- выдача сужается;
- счётчик «Найдено N» пересчитывается;
- сайдбар показывает базовые + технические фильтры выбранного типа;
- чип типа отображается как «Тип: Перфораторы»;
- повторный клик по активной кнопке или крестик в чипе снимает тип;
- `reset all` сбрасывает тип и возвращает широкую категорию.

## 6. Листовая категория
Листовая категория — это категория, в которой:

1. нет дочерних категорий;
2. или категория явно соответствует одному доминирующему `tool_type`;
3. или технические фильтры применимы к значимой доле товаров.

Если категория технически листовая, но по товарам остаётся смешанной, применяется логика широкой категории:

```text
сначала TypePanel + базовые фильтры,
затем технические фильтры после выбора типа.
```

## 7. Приоритет показа фасетов
Фасет не должен попадать в UI только потому, что у него есть значения в базе. Порядок принятия решения:

### 7.1. Placement gate
Сначала определяем, где фасет должен отображаться. Например:

```text
tool_type → TypePanel
brand → sidebar
price → sidebar
diameter → sidebar, если релевантен текущему типу
```

Важно: SEO-фасет и UI-навигационный фасет — не одно и то же. На текущем этапе можно временно использовать
`CategoryAttribute.is_seo_facet=True` для `tool_type`, чтобы отдать `is_nav=true`. Но долгосрочно лучше
иметь отдельный признак:

```text
ui_placement = sidebar | type_panel | scenario_chip
```
или `is_navigation_facet`.

### 7.2. Category/tool_type gate
Фасет может попасть в сайдбар только если он разрешён для текущей категории или выбранного `tool_type`.
Источник:

```text
CategoryAttribute.is_filter
CategoryAttribute.sort_order
CategoryAttribute inheritance
```

### 7.3. Drill-down gate
После category/tool_type gate из разрешённых фасетов показываются только те, у которых есть значения в
текущем контексте. Drill-down не решает, какие фильтры «уместны». Он только убирает пустые значения из уже
разрешённого набора.

### 7.4. Coverage gate
Если атрибут заполнен у слишком малой доли товаров, он не должен попадать в основные фильтры. Пример:

```text
2425 товаров
атрибут заполнен у 12 товаров
```

Такой фильтр лучше: скрыть; или отправить в «Дополнительные»; или не включать до обогащения данных.
Рекомендуемый стартовый ориентир:

```text
coverage < 5% → скрыть или Дополнительные
```

## 8. Базовые фильтры
Базовые фильтры не должны быть жёстко захардкоженным списком. Правило:

- **Наличие** — почти всегда базовый фильтр.
- **Бренд** — показывать, если бренд заполнен у значимой доли товаров.
- **Цена** — показывать, если есть min/max и товары с ценой.
- **Тип питания** — показывать только там, где применим к большинству товаров. Например:

```text
Электроинструмент → да
Оснастка → нет
Ручной инструмент → нет
```

## 9. Технические фильтры по типам
**Перфораторы:** энергия удара; мощность; тип патрона; режимы работы; максимальный диаметр бурения; вес; тип питания.

**Шуруповёрты:** тип питания; напряжение аккумулятора; крутящий момент; тип патрона; ёмкость аккумулятора; количество скоростей; аккумулятор в комплекте.

**УШМ:** диаметр диска; мощность; регулировка оборотов; плавный пуск; посадочный диаметр; тип питания.

**Дрели:** тип дрели; мощность; тип патрона; ударный режим; обороты; реверс.

**Оснастка** (после выбора типа товара): диаметр; длина; посадка; материал; назначение; совместимость.

## 10. Числовые фильтры
Числовые фильтры работают через одну дорожку с двумя бегунками.

**Правила UX:** одна дорожка; два бегунка; активный сегмент между бегунками; поля «от» и «до» сохраняются;
`min = max` разрешён; запрос не отправляется на каждый пиксель; фильтр применяется после отпускания бегунка,
blur или Enter.

**Правила выдачи.** Если применён числовой фильтр `Диаметр: 10,5–20 мм`, то в выдаче остаются только товары:
у которых есть атрибут «Диаметр» и значение попадает в диапазон. Товары без этого атрибута исключаются.

**UX-пояснение для скрытых товаров.** Если числовой фильтр исключил товары без атрибута, UI должен объяснять это:

```text
Показаны товары, где указан диаметр. Товары без диаметра скрыты.
```

В empty-state:

```text
По диаметру 10,5 мм товаров нет.
Товары без указанного диаметра скрыты фильтром.

[Сбросить Диаметр]
[Сбросить все фильтры]
```

Не нужно «подмешивать» товары без атрибута в отфильтрованную выдачу. Правильное действие — сбросить конкретный фильтр.

## 11. Applied chips
Все активные фильтры должны быть видны чипами. Примеры:

```text
Тип: Перфораторы ×
Bosch ×
В наличии ×
Диаметр: от 10,5 до 20 мм ×
Цена: до 10 000 ₽ ×
```

Для MVP рекомендуется всегда показывать чип типа `Тип: Перфораторы ×`, даже если TypePanel видна. Это уменьшает
риск непонимания при прямой ссылке или скролле.

## 12. TypePanel
TypePanel — панель выбора типа инструмента или товара.

**Правила отображения:** находится над toolbar и выдачей; работает как навигационный слой; активный тип выделен;
клик по неактивному типу применяет `?tool_type=<slug>`; повторный клик по активному типу снимает его; counts
показываются рядом с названием; скрытые/нулевые типы не показываются.

**Порядок типов:**

1. `sort_order` из `AttributeOption` / `CategoryAttribute`, если есть;
2. иначе по count desc;
3. активный тип не перемещается наверх, чтобы панель не прыгала;
4. если типов больше 10–12, использовать горизонтальный scroll или «Ещё».

**Counts в TypePanel** считаются по own-axis exclude: учитывают текущую категорию, brand, stock, price,
attr-фильтры; не учитывают текущий выбранный `tool_type`. Это нужно, чтобы пользователь мог переключаться
между типами. Пример:

```text
Выбран tool_type=perforatory
Выбран brand=Bosch

TypePanel:
Перфораторы 120 selected
Дрели 35
УШМ 48
Шуруповёрты 62
```

## 13. TypePanel и subcategories
`subcategories` и `tool_type` — разные сущности: `subcategories` — дерево каталога; `tool_type` — EAV-навигация.
Если они дублируют друг друга визуально, не нужно показывать две одинаковые панели. Правило:

```text
Если subcategories и TypePanel совпадают по смыслу, приоритет у TypePanel на тех категориях,
где tool_type выбран как основной навигационный механизм.
```

## 14. Empty-state
Плохой empty-state:

```text
Товаров не найдено
```

Хороший empty-state:

```text
По этим фильтрам товаров нет.

Попробуйте:
— расширить диапазон диаметра;
— снять бренд Bosch;
— посмотреть товары под заказ.

[Сбросить Диаметр]
[Снять бренд]
[Сбросить всё]
```

Для числовых фильтров важно объяснять, если товары без атрибута скрыты.

## 15. Loading-state
При смене фильтра: не показывать большой полностраничный спиннер; сохранять стабильную сетку; показывать
skeleton карточек; рядом со счётчиком можно показать «Обновляем…»; range применяется после отпускания бегунка,
blur или Enter.

## 16. Mobile UX
На мобильном фильтры открываются в bottom-sheet. Кнопки:

```text
[Фильтры] [Сортировка]
```

Внутри sheet:

```text
Фильтры
Найдено 214 товаров

Наличие
Бренд
Цена
...

[Сбросить] [Показать 214 товаров]
```

Если доля мобильного трафика больше 40%, мобильный bottom-sheet нужно поднять в более раннюю фазу, сразу после
TypePanel и базовой контекстности.

## 17. Производительность фасетов
Facets endpoint — критичная по нагрузке часть PLP. Обязательные требования:

1. Счётчики не считать отдельным запросом на каждую опцию.
2. Brand/stock/type counts считать group-by.
3. Проверять SQL count/time на больших категориях.
4. Держать бюджет ответа facets endpoint.
5. Для тяжёлых категорий допускается кэш facets по ключу:
   ```text
   category + tool_type + brand + stock + price + attr_filters
   ```
6. Для тяжёлых numeric range по `attrs_cache` рассмотреть переход на индексируемый relational path через `value_decimal`.

Ориентир:

```text
facets endpoint p95 < 500–800 мс на категории до 10–12 тыс. товаров
```

## 18. Риск качества данных
Контекстные фильтры зависят от заполненности EAV-атрибутов. Если `tool_type`, диаметр, энергия удара, тип
патрона, посадка и другие атрибуты заполнены плохо, фильтры могут быть технически правильными, но пустыми или
бесполезными на витрине. Перед включением технических фильтров нужен coverage-отчёт:

```text
coverage(attribute, tool_type) = товары с атрибутом / товары выбранного типа
```

Пример:

```text
Перфораторы:
tool_type заполнен у 92%
energy_impact заполнен у 78%
chuck заполнен у 91%
power заполнен у 64%

Коронки:
diameter заполнен у 42%
material заполнен у 18%
landing заполнен у 35%
```

Если coverage низкий, фильтр не должен попадать в основные. Сначала нужно обогащение данных.

## 19. Price / pricing / B2B
Цена в карточке, price-фасет и сортировка по цене должны использовать один и тот же источник. Если карточка
показывает B2B-цену, а price-фильтр считает retail-цену, пользователь получит рассинхрон. Правило:

```text
displayed price, price facet, price filter, price sort должны быть консистентны по роли пользователя.
```

Если сейчас price-фасет считается по `Product.price`, это нужно считать known limitation до завершения
`pricing.price_for`.

## 20. Canonical и SEO для параметрических URL
SEO-роуты типов отложены, но canonical-дисциплину нужно заложить раньше. Минимальные правила:

- sort/view/page не должны создавать самостоятельные canonical-страницы;
- параметрические URL не должны бесконтрольно индексироваться;
- canonical должен указывать на базовую категорию или будущий canonical type URL;
- SEO-роуты `/catalog/<тип>` делаются отдельной фазой.

## 21. Analytics
TypePanel и фильтры должны давать данные для бизнеса. События:

```text
type_panel_view
tool_type_select
tool_type_reset
filter_apply
filter_reset_one
filter_reset_all
range_filter_commit
empty_state_view
empty_state_reset_click
mobile_filter_open
mobile_filter_apply
```

Основные связки:

```text
tool_type_select → product_card_click
tool_type_select → add_to_cart
empty_state_view rate
filter_reset rate
```

Эти данные помогут понять: какие типы товаров ищут чаще; какие типы первыми делать SEO-страницами; какие
атрибуты обогащать в первую очередь; какие фильтры мешают выбору.

## 22. Требования к данным
Для каждой широкой категории нужно проверить: какой атрибут является navigation facet; какие фильтры базовые;
какие технические атрибуты относятся к каждому `tool_type`; `sort_order` фасетов; labels; units; coverage;
какие фасеты скрывать при низком покрытии.

Без data governance фильтры снова превратятся в отражение грязной базы.

## 23. Backend-изменения

### 23.1. Навигационный фасет
В `build_facets` отдавать признак для фасета `tool_type`:

```text
is_nav: true
```

На текущем этапе можно использовать `CategoryAttribute.is_seo_facet=True`, но долгосрочно лучше отделить
UI placement от SEO.

### 23.2. `tool_type` как drill-down измерение
`CategoryFacetsView` и `build_facets` должны принимать:

```text
tool_type=<slug>
```

Список товаров и фасеты должны сужаться одинаково.

### 23.3. `CategoryAttribute.is_filter`
`queries._category_filter_attributes` должен учитывать `CategoryAttribute.is_filter`, а не только глобальный
`Attribute.is_filterable`.
