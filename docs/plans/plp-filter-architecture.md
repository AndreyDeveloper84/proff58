# Архитектура фильтров PLP — source of truth (электроинструмент + оснастка)

> Статус: на ревью. Реализацию начинаем после утверждения этого документа.
> Workflow: **архитектурный план → ревью → GitHub Issues → реализация.** Issues пока НЕ создаём.

## 1. Цель
Превратить левый фильтр из «простыни всех атрибутов из базы» в **управляемый подбор товара**:
сначала навигация (тип инструмента), затем контекстные технические уточнения. Покупатель не должен
видеть параметр (напр. «Диаметр») рядом с товарами, у которых его нет, и не должен ощущать фильтр
сломанным. Документ — единый источник правды по продуктовой логике фильтров PLP.

## 2. Принятые UX-решения
1. **Тип инструмента — это навигация, а не обычный фасет.** `tool_type` выносится в **отдельную панель
   кнопок над выдачей**, убирается из левого сайдбара.
2. **URL: «параметр сейчас, SEO потом».** Тип — параметр `?tool_type=<slug>` на текущей категории
   (`/catalog/electroinstrument?tool_type=perforatory`, `/catalog/osnastka-i-rashodniki?tool_type=koronki`).
   Отдельные SEO-роуты `/catalog/<тип>` — следующая задача после стабилизации UX (см. §10, §9-Эпик G).
3. **Широкая категория: прятать технические фильтры до выбора типа.** Показываем базовые фильтры +
   панель типов; тех. параметры появляются контекстно после выбора типа (не скрываем навсегда).
4. **Контекстность:** широкая категория → только базовые; выбран тип → базовые + тех. фильтры этого типа;
   листовая категория → полный релевантный набор.
5. Range применяется по отпусканию/blur/Enter (не на каждый пиксель); `min=max` разрешён; применённый
   числовой фильтр исключает товары без атрибута (готово, PR #219).
6. `tool_type` работает как обычный фильтр выдачи; активный тип — подсвеченная кнопка в панели; чип типа
   либо не дублируем панель, либо аккуратно «Тип: Перфораторы»; `reset all` сбрасывает и тип, и фильтры.

### Ключевой архитектурный факт (почему это дёшево)
`tool_type` уже существует как **EAV-атрибут SELECT** (ADR-0001), НЕ узел дерева. Опции
(«Перфораторы», «УШМ», …) имеют готовые slug (`perforatory`, `ushm`) и счётчики через drill-down; есть
`ProductFilter.filter_tool_type` для `?tool_type=<slug>`. ⇒ панель типов и контекстность строятся **без
миграции модели**; контекстность частично поддержана `CategoryAttribute` + наследованием в
`queries._category_filter_attributes`.

## 3. URL-контракт
Состояние PLP целиком в URL (восстанавливается после перезагрузки). Источник — `frontend/lib/url-state.ts`.
- Тип инструмента: `?tool_type=perforatory` (новый верхнеуровневый параметр, НЕ `attr_`).
- Чекбоксы: `?brand=bosch,makita`, `?stock=in`, `?attr_<slug>=v1,v2`.
- Диапазоны: `?attr_diameter_min=10.5&attr_diameter_max=20`, `?price_min/price_max` (контракт `code_min/code_max`).
- UI-state: `?sort=&view=&page=&per_page=` (дефолты не сериализуются).
- `reset all` сбрасывает и `tool_type`, и все фильтры. Смена любого фильтра → `page=1`.

## 4. Поведение широкой категории (тип не выбран)
- Над выдачей — **панель типов** (кнопки/плитки с count из навигационного фасета).
- Левый фильтр — **только базовые**: Наличие, Бренд, Цена, Тип питания (если применим).
- Технические `attr_*` скрыты (не показываем нерелевантные большинству товаров параметры).
- H1/intro — общий для категории.

## 5. Поведение выбранного `tool_type`
- URL: `?tool_type=<slug>`; активная кнопка в панели подсвечена.
- Выдача и счётчики (фасеты, «Найдено N») пересчитываются под выбранный тип (drill-down).
- Левый фильтр: **базовые + технические фильтры, релевантные типу** (см. §6).
- Applied-chip типа — аккуратно «Тип: Перфораторы» (или не дублировать панель); × / повторный клик снимает тип.
- H1/intro можно уточнить подзаголовком («Перфораторы»). Левые фильтры **уточняют** тип, не заменяют навигацию.

## 6. Правила показа технических фильтров
```
Широкая категория, тип не выбран → только базовые (Наличие, Бренд, Цена, Тип питания)
Выбран tool_type               → базовые + технические фильтры этого типа
Листовая категория             → полный релевантный набор (как на «выбран тип»)
```
- Релевантность определяется: (а) `CategoryAttribute.is_filter` для категории/предков (наследование),
  (б) drill-down автоматически отсекает фасеты с пустыми значениями после сужения по типу.
- Ожидаемые наборы: Перфораторы → энергия удара, мощность, тип патрона, режимы, вес;
  УШМ → диаметр диска, мощность, регулировка оборотов, посадочный диаметр; Шуруповёрты → напряжение,
  крутящий момент, АКБ; Коронки → диаметр, длина, посадка, материал, назначение.
- Цель: не показывать параметры, неприменимые к большинству товаров текущей выдачи.

## 7. Backend-изменения (`apps/catalog`)
- **Навигационный фасет:** помечать атрибут с `CategoryAttribute.is_seo_facet=True` как `is_nav: true` в
  ответе `build_facets` (это `tool_type` на depth=1) — фронт рендерит панелью, не в сайдбаре.
- **`tool_type` как drill-down-измерение:** `CategoryFacetsView` + `build_facets` принимают `tool_type=<slug>`;
  счётчики прочих фасетов учитывают тип, сам tool_type — own-axis exclude. Согласовать с существующим
  `ProductFilter.filter_tool_type` (один механизм для списка и фасетов).
- **Учитывать `CategoryAttribute.is_filter`** в `queries._category_filter_attributes` (сейчас читается лишь
  глобальный `Attribute.is_filterable` — расхождение с `range_filter_attributes`).
- **Группы фильтров (фаза 2):** поле/производное `CategoryAttribute.group` (Базовые/Основные/Доп.) → `group` в фасете.
- **Сценарии (фаза 4):** отдать `scenarios` на категорию (config/фикстура), не смешивая с `subcategories`.
- Затрагиваемые: `apps/catalog/facets.py`, `queries.py`, `api/views.py`, `filters.py`.

## 10. Что не делаем сейчас
- НЕ делаем SEO-роуты `/catalog/perforatory|ushm|koronki` (mapping slug→категория/фасет, canonical,
  breadcrumbs, sitemap, redirects, дубли, meta) — отдельная фаза 4/Эпик G после стабилизации UX.
- НЕ вводим модель Brand; НЕ делаем `tool_type` узлом дерева (он атрибут — ADR-0001).
- НЕ подключаем тяжёлую UI-библиотеку ради bottom-sheet (нативный + CSS, как в проекте).
- НЕ ломаем URL-контракт диапазонов (`code_min/code_max`) и принцип «список и фасеты из одного источника».
- НЕ создаём GitHub Issues до утверждения этого документа.

### Инварианты (держать во всех фазах)
1. URL — единственный источник состояния, полностью восстановим.
2. Чекбоксы — сразу; range — по отпусканию/blur/Enter; `min=max` разрешён.
3. Применён числовой фильтр ⇒ товары без атрибута исключаются (готово в #219).
4. Все активные фильтры видны чипами с индивидуальным сбросом.
5. «Найдено N» меняется заметно; список и счётчики — из одного источника (`attrs_cache`).
6. Тип инструмента — навигация (панель), а не фасет сайдбара.
