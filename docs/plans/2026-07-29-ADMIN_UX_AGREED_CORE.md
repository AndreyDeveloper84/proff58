## 1. Согласовано — совпало в обоих документах, считаем закрытым

1. Проблема **организационная, а не визуальная**. Смена темы задачу не решает.
2. **Два контура:** рабочий и системный. Системные сущности из рабочего меню
   убираются.
3. **Цена и остаток из 1С — только для чтения**, с подписью-объяснением в форме.
4. **Статусы заказа меняются только бизнес-действиями.** Ручная правка статуса,
   снимков и сумм запрещена.
5. **Стартовый экран «Сегодня»** со счётчиками, каждый ведёт в готовую очередь.
6. **Готовые очереди вместо конструктора фильтров** — для товаров и для заказов.
7. **Индикатор готовности товара** со списком, чего не хватает для публикации.
8. **Постепенное раскрытие сложности:** основные поля сразу, SEO / 1С /
   служебное — по раскрытию.
9. **Развести две сущности «Акции»** — промо-страница и скидочная механика.
10. **Не делать универсальный конструктор главной** — фиксированный набор блоков.

**С уточнением:** скрыть slug, внутренние ID, JSON-снимки, хэши, ключи
идемпотентности, source/confidence — да. Но `code_1c`, артикул, причину
непубликации и статус выгрузки в 1С **скрывать нельзя** — по ним человек
сверяется с 1С и понимает, почему товара нет на сайте.

**Добавляю к п. 9:** дубль не один. «Категории» (`Category`) и «Категории
(сайт)» (`SiteCategory`, прокси на `is_site_v2=True`) стоят рядом в одном
разделе — `apps/catalog/models.py:103` и `:391`. Нужно решить, какое дерево
остаётся в рабочем меню.

## 3. Стартует немедленно: спринт 0 — существующие дефекты

Ни один документ этого не описывал, а это не UX, а поломки. ~1.5 дня.

1. **Матрица переходов заказа в админке не применяется.**
   `apps/orders/transitions.py` существует, но `can_transition` вызывается
   только из `apps/sync_1c/use_cases.py:819` и
   `apps/orders/invoice_lifecycle.py:125`. Из админки статус переводится
   куда угодно: «Выполнен» → «Новый», «Отменён» → «В доставке».
2. **Снимки заказа редактируемы.** `readonly_fields` в `OrderAdmin` — три поля;
   `total`, `vat_amount`, `customer_*`, `promo_snapshot` правятся руками без
   пересчёта строк.
3. **Три экрана рендерят `<select>` на всю таблицу:** `CartItemInline.product`
   (`apps/orders/admin.py:81`), `ProductAttributeValueInline.value_option`
   (`apps/catalog/admin.py:426`), `OrderAdmin.user`. Это и есть жалоба
   «админка виснет».
4. **`brand` в `list_filter`** (`apps/catalog/admin.py:536`) — `CharField`,
   в сайдбаре рендерятся все бренды каталога.
5. **Нет `get_absolute_url`** — а «Предпросмотр» требуется в пяти местах §7.
6. **Нет `save_on_top`** при семи блоках и пяти инлайнах в карточке товара.

## 8. Итог обсуждения — 2026-07-29

Ответы по §2 получены, **Y1–Y4 приняты все четыре**. Техническое обсуждение
закрыто, предмета спора между ревьюерами не осталось.

Зафиксировано к исполнению:

- **v1 — один интерфейс универсала**, без ролевой матрицы;
- **расширяем существующий Django admin**, вторая UI-система не создаётся;
- **наблюдение за работой** — короткое, без выделения в этап;
- **спринт 0 — первый**, начинается по прямому подтверждению заказчика.

Две оговорки из ответов приняты без возражений:

1. **Скрытие пунктов меню — не ограничение доступа.** `hide_models` убирает
   пункт из сайдбара, но URL остаётся рабочим. Значит защита опасных полей и
   действий — только серверная: `readonly_fields`, `has_*_permission`,
   валидация формы. Именно так и устроен спринт 0 — пп. 1–2 §3 закрываются
   на сервере, а не сокрытием в интерфейсе.
2. **Документ не является разрешением на разработку.** Пересылка согласованного
   текста не запускает изменение кода — нужен явный старт от заказчика.

Открытым остаётся только §4 — три решения заказчика (C1 предпросмотр,
C2 порядок сценариев, C3 доступ к живой админке). Ни одно из них не блокирует
спринт 0.
