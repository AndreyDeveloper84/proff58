# DRF-2293 — MAX-уведомления покупателю: протокол проверки перед включением

Дата: 2026-09-22. Ветка `feature/max-launch-check` (поверх DRF-2296).
Что закрыто кодом и тестами — §1; что нужно пройти живьём на стенде — §2 (заполняет
тот, у кого есть доступ к стенду и боту); решение владельца — §3.

## 1. Что проверено кодом и тестами

| Пункт приёмки | Где |
|---|---|
| События создания, оплаты, смены статуса (подтверждён/собран/в доставке/доставлен/отменён), полного и частичного возврата → шаблоны | `apps/integration_max/test_order_receivers.py` |
| Настройки пользователя: выключенный канал или категория гасят отправку с записанной причиной, не молча | `test_order_updates_disabled_preference_skips_without_send`, `notifications/test_notification_domain.py` |
| Повтор одного события не создаёт второй постановки (ключ идемпотентности + ограничение в БД) | `test_duplicate_*`, `test_notification_idempotency_key_db_constraint` |
| Неопределённый результат (`unknown`, зависшая отправка) не ретраится вслепую | `notifications/test_retry_policy.py`, `reconcile_stuck_notifications` |
| Гостевое отслеживание: чужой заказ по подмене номера/токена или с другим телефоном не раскрывается и не привязывается | `apps/integration_max/test_track_order.py` |
| В сообщениях нет ПДн и токенов, только публичный номер и статус | `test_payload_contains_only_safe_public_fields` |
| Недоступность очереди после коммита заказа не ломает оформление: строка помечается `failed/retryable`, доступен повтор из админки | `notifications/test_enqueue_failure.py` (эта ветка) |
| Включение флага не переотправляет старые «пропущенные» уведомления | `notifications/test_admin_retry.py::test_retry_action_ignores_skipped` (эта ветка) |
| Сбой самого MAX API: временные ошибки ретраятся с backoff, постоянные — нет, ручной повтор из админки | `notifications/test_retry_policy.py`, `test_error_classification.py`, `test_admin_retry.py` |

Известный пробел вне объёма (для отдельной задачи): путь остатков от 1С
(`stocks/update` → fan-out «товар в наличии») ставит задачу в очередь напрямую; с этой
ветки сбой очереди там логируется, но строк для повтора не создаёт — подписчики
поступления в этот момент уведомление не получат.

Покупатель **без MAX** уведомлений не получает нигде: статусы он смотрит в личном
кабинете (вход по e-mail) или на странице «Спасибо за заказ» по ссылке из адресной
строки после оформления. Писем и SMS о статусах нет — это не обещается ни в
интерфейсе, ни в руководстве.

### 2.1 Конфигурация (только чтение)

- [ ] Эффективный флаг: `SiteSettings.max_chat_enabled` = ____ ; override `FEATURES["max_chat"]`
      в env отсутствует / = ____ (приоритет у override, см. `apps/core/features.py`).

- [ ] В контейнере web заданы `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_BOT_USERNAME`,

- [ ] `GET /subscriptions` у бота показывает webhook `https://proff58.ru/api/max/webhook/`

- [ ] **На воркере, а не только в web:** отправку выполняет контейнер `celery`; в нём

      is_enabled; print(bool(settings.MAX_BOT_TOKEN), is_enabled('max_chat'))"` даёт `True True`.
      Иначе web пишет строки в очередь, а воркер отвечает «MAX_BOT_TOKEN not configured» —
      всё уходит в `failed/permanent`.
- [ ] В `.env` нет `FEATURE_MAX_CHAT`: env-override перекрывает галочку в «Настройках сайта».
- [ ] Воркер `celery` и `celery-beat` запущены; в расписании beat есть
      `reconcile_stuck_notifications` и очистка журналов (`config/celery.py`).
- [ ] Владелец бота (кто держит доступ к dev.max.ru): ________.

### 2.2 Привязка и отслеживание

- [ ] Зарегистрированный покупатель (тестовый аккаунт ________) привязал MAX через
      «Уведомления в MAX» в кабинете → в чат пришло «Вы будете получать уведомления…».
- [ ] Гость оформил заказ → на странице «Спасибо» нажал «Отслеживать заказ в MAX»,
      подтвердил контакт с **тем же** телефоном, что в заказе → пришло «Отслеживание
      заказа №… подключено».
      Затем сменить статус заказа кнопкой → сообщение пришло в тот же чат (кодом покрыт
      только отказ, полный путь «/thanks → грант → снимок → следующее событие» — здесь).

### 2.4 Сбои и повтор

- [ ] Временно подменить `MAX_BOT_TOKEN` на неверный **на воркере** → событие → строка
      `failed` (`permanent`, HTTP 401) в «Лог уведомлений»; заказ при этом оформился и
      оплатился. Для permanent повтор из админки недоступен — так и должно быть.
- [ ] Остановить воркер (или Redis) на минуту → оформить заказ → заказ создан, ответ
      витрины без ошибки, строка `failed/retryable` «Очередь недоступна». Поднять →
      «Повторить отправку» → `sent`, сообщение пришло **один раз**. Заметить: при лежащем
      брокере оформление отвечает на несколько секунд дольше (publish-retry kombu).
- [ ] Повторно подтвердить тот же статус из 1С (или повторный webhook кассы) → второй
      строки нет.

### 2.5 Включение

- [ ] Перед включением `max_chat_enabled` снять числа:
      `select status, count(*) from notifications_notificationlog group by status;` и
      `select count(*) from notifications_notification where policy_skip_reason <> '';`
      → skipped ____, sent ____, failed ____. Через 10 минут после включения — те же
      запросы: `sent` не вырос на число skipped, skipped не уменьшилось (старые
      уведомления не рассылаются).
- [ ] **Откат:** выключить галочку «MAX-чат» → оформить заказ → заказ создан, строка
      `skipped` («MAX канал недоступен или отключён»), покупателю ничего не приходит.
- [ ] **ПДн:** тестовые аккаунты — служебные номера, не реальные покупатели. После
      прогона в логах воркера нет chat_id и токена: `docker logs <celery> | grep -c` по
      chat_id и по первым символам токена → 0.
- [ ] Инструкция включения/отключения: `docs/max-bot-setup.md`, runbook §7.
