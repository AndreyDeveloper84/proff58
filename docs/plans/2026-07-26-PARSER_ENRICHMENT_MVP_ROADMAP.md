# Roadmap: MVP-обогащение категории контентом с сайта-источника

**Статус:** Draft, требует утверждения владельцем
**Дата:** 2026-07-26
**Цель:** максимально быстро получить **одну полностью расставленную категорию** —
у товаров есть фотографии и характеристики, лежащие в наших EAV-полях, а не в
свалке raw-JSON. Работают фасеты и фильтры.

> Переписан относительно `Все-Инструменты-VSEINSTRUMENTI_PARSER_MVP_ROADMAP.md`
> под фактическую архитектуру proff58. Главное отличие: **мы не создаём товары,
> а обогащаем свои**; характеристики раскладываются по `ProductAttributeValue`,
> а не складываются в `attributes_raw`.

---

## 1. Что именно делаем

```text
URL категории источника
    ↓  парсер (вне Django)
JSON-выгрузка карточек
    ↓  импортёр (management command)
матчинг карточка → НАШ товар (бренд + модель; артикул только как подтверждение)
    ↓
фото → ProductImage (через ImagePipeline)
характеристики → ProductAttributeValue (source=marketplace)
    ↓
категория на сайте: карточки с фото, характеристики, работающие фильтры
```

Товары у нас уже есть — они приходят из 1С. Больно другое: у них нет фотографий и
характеристик. Парсер — **донор контента**, а не источник ассортимента.

## 2. Жёсткие границы (нарушение = стоп)

Импортёр **никогда** не трогает:

| Что | Почему |
|---|---|
| цену и остаток | 1С — источник истины (ADR-0006, `apps/pricing`) |
| `code_1c`, `article` | идентичность товара из 1С |
| дерево категорий, привязку товара к категории | сайт мастерит дерево вручную (ADR-0007) |
| `tool_type` | только rules-engine из canonical manifest (CLAUDE.md §7) |
| `name` | название — контент сайта, уже выправлено |
| значения с `source="manual"` | руками расставленное не затирается автоматикой |

Не создаёт: товары, категории, бренды, `Attribute`, `AttributeOption`.
Всё, что не удалось сопоставить с существующими сущностями, идёт **в отчёт**, а не
в базу.

## 3. Что уже есть в проекте — переиспользуем, не пишем заново

Это главный источник экономии времени:

| Готовое | Где | Что даёт |
|---|---|---|
| `ImagePipeline` | `apps/catalog/image_pipeline.py` | скачивание с SSRF-защитой (резолв IP + пиннинг, запрет redirects), лимит 10 МБ, защита от decompression bomb, ресайз до 1200×1200 |
| `ProductImage` | `models.py:779` | `is_main`, `sort_order` |
| `ProductAttributeValue` | `models.py:797` | типизированные `value_text/integer/decimal/boolean/option` + провенанс |
| `Source.MARKETPLACE` | `models.py:41` | **готовый источник для наших значений** |
| `source_priority` | `data/attribute_rules.json` | политика перезаписи: `manual` не затирается |
| pg_trgm по `name`/`article`/`brand` | `models.py:569` | нечёткий матчинг прямо в БД |
| `rebuild_attrs_cache` | management command | синхронизация кэша фасетов после записи |
| gate-цикл | `docs/catalog/operations/README.md` | read-only → preflight → dry-run → pg_dump → write → post-audit |

Писать с нуля нужно только парсер и маппинг-слой.

## 4. Архитектура

```text
parser/                          # автономный, вне Django
├── main.py                      # CLI-оркестратор
├── category.py                  # сбор URL товаров + пагинация
├── product.py                   # парсинг карточки
├── client.py                    # httpx: таймаут, retry, 2-3 параллельных запроса
├── schemas.py                   # pydantic-контракт выгрузки
├── output/{products,errors}.json
└── tests/fixtures/              # сохранённый HTML — тесты без сети

apps/catalog/management/commands/
└── catalog_import_scraped.py    # матчинг + запись, с --dry-run

data/catalog_processing_rules/
└── scraped_attr_map.<категория>.json   # карта «характеристика источника → наш Attribute»
```

Стек парсера: Python 3.12, `httpx`, `beautifulsoup4`, `lxml`, `pydantic`.
Playwright — только если данных нет в HTTP-ответе, с обоснованием в отчёте.
Ни Scrapy, ни Celery, ни отдельной БД.

## 5. Контракт выгрузки

```json
{
  "schema_version": "1.0",
  "source": "vseinstrumenti",
  "created_at": "2026-07-26T12:00:00Z",
  "category": {"name": "Перфораторы", "source_url": "https://..."},
  "products": [
    {
      "source_url": "https://...",
      "source_id": "1234567",
      "name": "Перфоратор Example SDS-plus 780 Вт",
      "brand": "Example",
      "manufacturer_sku": "MODEL-001",
      "image_urls": ["https://.../main.jpg"],
      "attributes": {"Мощность": "780 Вт", "Тип патрона": "SDS-plus"}
    }
  ]
}
```

Цены в контракте **нет** — она не нужна и не должна попадать в базу даже случайно.

# 6. Фазы

## Phase 0 — выбор цели ✅ ВЫПОЛНЕНО 2026-07-27

Цель пилота — **перфораторы**: `tool_type` = «Перфораторы» (`AttributeOption id=1`),
**188 товаров**, все опубликованы, у **всех** нет фото и нет ни одной характеристики
кроме самого типа, `content_locked=0`, `article` непустой у 161 (86%).

Полные цифры, бренды и находки — `docs/parser-mvp/input-category.md`.

Три факта из разведки, которые определили остальные фазы:

1. **Отдельной категории «Перфораторы» нет** — все 188 лежат в плоском `cat=3`
   «Электроинструмент». Выборка идёт по `tool_type`, не по категории; «расставленная
   категория» на витрине = раздел, отфильтрованный по типу.
2. **Поле `brand` пустое у всех 188**, но бренд есть в названии («Перф. **Bosch**
   GBH 2-26DFR») → извлекаем через `apps/catalog/brand_slugs.py`.
3. **Артикулы — настоящие номера производителя** (`0611254768`, с префиксом
   поставщика `BSH-0611240008`) → матчинг по артикулу реален, нужна нормализация
   префикса.

Схема характеристик уже настроена: у `cat=3` есть `power`, `chuck`, `energy_impact`,
`no_load_speed`, `voltage` и др. Новые `Attribute` не создаём.

Остаётся выбрать URL категории перфораторов у источника — на Phase 1.

## Phase 0.5 — «бесплатный» слой характеристик из названий (1 день) ⚡

**Делать первым.** Названия из 1С уже содержат ядро характеристик перфоратора:

```
Перф. Bosch GBH 2-26DFR; 800Вт, SDS+, 3Дж, 3реж, 0-900об/мин
              ↑ бренд    ↑power ↑chuck ↑energy_impact ↑no_load_speed
```

Это извлекается регулярками из наших собственных данных — **без внешнего сайта, без
парсера и без правовых вопросов**, существующей командой `enrich_attributes`
(правила — `data/attribute_rules.json`, источник значения `source="regex"`).

- [ ] Составить regex-правила для перфораторов: мощность (`Вт`), энергия удара
      (`Дж`, десятичная запятая), тип патрона (`SDS+` / `SDS-Max` / `SDS-plus`),
      обороты (`об/мин`), число режимов.
- [ ] Прогон `enrich_attributes` в dry-run по выборке 188, глазами проверить 10 штук.
- [ ] Замерить покрытие: сколько товаров получило каждый атрибут.
- [ ] Применить по гейт-циклу (pg_dump → запись → post-audit → `rebuild_attrs_cache`).

**Готово когда:** значимая доля из 188 перфораторов имеет мощность, тип патрона и
энергию удара, а фасеты по ним стали рабочими фильтрами.

Это самостоятельный результат: если дальше по правовым или техническим причинам
парсер не поедет, категория всё равно перестанет быть пустой. Парсер затем
**дополняет** то, чего нет в названиях: фото, габариты, вес, комплектацию.

## Phase 1 — разведка источников (0.5 дня) ◐ ЧАСТИЧНО ВЫПОЛНЕНО 2026-07-27

> **Смена источника, решение владельца 2026-07-27.** Вместо агрегатора-магазина —
> **сайты производителей**. Фотографии **не берём**, только характеристики.
> Полный протокол замера: `docs/parser-mvp/source-recon.md`.

### Почему сменили источник

Замер показал, что агрегаторы закрыты антибот-защитой и обычным HTTP-клиентом
не читаются вовсе:

| Источник | robots.txt | Страницы | Вывод |
|---|---|---|---|
| `vseinstrumenti.ru` | **403** | **403** | отказ и с браузерным UA; защита уровня Cloudflare |
| `dns-shop.ru` | 200, **разрешает** `/product/characteristics/*` | **401** | формально можно, технически закрыто → кандидат на официальный запрос доступа |
| `hikoki`, `dewalt.ru`, `metabo.com/ru` | — | 403 / таймаут / обрыв | закрыты |
| `makita.ru` | — | домена нет | искать дистрибьютора |

Работающий автопарсер по ним означал бы эмуляцию браузера со стелс-обвязкой — это
обход намеренного технического отказа и постоянно ломающаяся конструкция. Решение:
идти к производителям, которые публикуют характеристики сами.

### Источники, принятые в работу

| Источник | robots | sitemap | Карточка | Статус |
|---|---|---|---|---|
| `resanta.ru` | полного запрета нет | `sitemap-shop.xml`, 874 URL | **JSON-LD + 97 microdata + таблица**, артикул производителя есть (`75/3/2`) | ✅ структура подтверждена |
| `vihr.su` | полного запрета нет | `sitemap-shop.xml`, 1177 URL | прямые URL моделей | ✅ sitemap подтверждён |
| `interskol.ru` | полного запрета нет | `sitemap.xml`, 2070 URL, разделы SDS-plus/SDS-max | не проверялась | ◐ нужен заход |
| `zubr.ru` | полного запрета нет | **сломан** — ведёт на тестовый домен `zubr.itech-test.ru` | не проверялась | ◐ навигация по каталогу |

**Критический вопрос закрыт: артикул производителя в карточке есть.** Матчинг
строится на нём, а не на догадках по названию. Проверить на Phase 4 остаётся одно —
совпадает ли артикул производителя с нашим `article` из 1С; если нет, резерв —
модель из названия (для этих брендов она в URL: `perforator-p-30-900k-resanta`).

### Покрытие — честная оценка

Открытые источники покрывают **российские бренды**: ВИХРЬ (7 товаров), Интерскол (6),
Ресанта (4), ЗУБР (2–3) — суммарно ~20 перфораторов из 188. Это ровно те, у которых
мощность зашита в маркировку и правилами не извлекается.

Остальные ~168 (Bosch, Makita, DeWALT, Metabo, HiKoki) требуют другого пути:
Icecat (доступен, покрытие по электроинструменту не проверено), ETIM как эталон
набора характеристик, прайсы поставщиков с привязкой к артикулам, официальный доступ
к DNS или ВсеИнструментам. **Это отдельная задача, не блокирующая MVP.**

### Что осталось сделать в Phase 1

- [ ] Разобрать `JSON-LD` и `microdata` карточки: какие поля отдаются структурно,

не более 1 запроса в 2–3 секунды на домен, честный `User-Agent` с контактом,
кэширование скачанного, отсутствие параллельных потоков на один хост. Мы гость на
чужом сайте, а не нагрузочный тест.

## Phase 2 — парсер (2 дня)

Объединяет клиент, схемы, карточку и категорию — они мелкие и тестируются вместе.

### Два режима добычи (решение владельца 2026-07-28)

Источники разделены на две группы, клиент поддерживает оба режима за общим интерфейсом.

| | Режим A — HTTP | Режим B — браузер |
|---|---|---|
| Источники | `resanta.ru`, `vihr.su`, `interskol.ru`, `zubr.ru` | `vseinstrumenti.ru`, `dns-shop.ru` |
| Основание | отдают всё обычным HTTP: 24 запроса на Phase 1, ни одного отказа | на обычный запрос отвечают 403 / 401 |
| Включение | по умолчанию | только явным флагом `--mode browser` |
| Темп | ≤ 1 запрос в 2–3 с на хост | 5–10 с между карточками, лимит за прогон |
| Назначение | основной сбор | **добор недостающих карточек**, а не первичный обход каталога |

**Режим B — замещение ручного труда контент-менеджера, поэтому профиль соответствующий:**

- Playwright, persistent context + `storage_state`; за образец — отлаженный клиент
  `wb_p/monitoring/browser/client.py` (сохранение профиля и куки между запусками);
- **разовый headed-bootstrap**: первый запуск в видимом окне, челлендж при появлении
  проходит **человек**, сессия сохраняется; далее headless на ней;
- **автоматическое решение капчи не делается** — ни своими силами, ни внешними сервисами;
- **при 403 / 429 / челлендже — остановка и доклад владельцу**, а не цикл ретраев:
  срабатывание защиты означает неверный профиль работы, и это решение владельца.
  Логику ожидания `retry_after` из `wb_p` сюда не переносить — там своя площадка;
- никакого параллелизма; фотографии не берём и в этом режиме.

**Порядок:** сначала производители (режим A) — они покрывают ~40 товаров из выборки
Phase 1; закрытые источники (режим B) — только то, чего у производителей нет.

### Модули

- [ ] `client.py`: общий интерфейс обоих режимов. **A:** таймаут 20 с,
      последовательные запросы, до 3 ретраев с возрастающей задержкой, обработка 429
      и 5xx, без ретраев на 4xx. **B:** Playwright по правилам выше.
- [ ] `schemas.py`: pydantic-схемы карточки и выгрузки, валидация URL, очистка строк.
- [ ] `product.py`: сначала JSON-LD, HTML-селекторы только для недостающего.
      Обязательные поля — `source_url`, `name`; товар без них отклоняется.
- [ ] `category.py`: `collect_product_urls(source, limit)` — **из sitemap**, а не
      обходом пагинации: у `resanta.ru` и `vihr.su` есть `sitemap-shop.xml`, у
      `interskol.ru` — `sitemap.xml`; фильтр по маске URL категории, дедуп, сохранение
      порядка, потолок. Обход пагинации остаётся резервом для `zubr.ru`, где sitemap
      сломан (ведёт на тестовый домен).
- [ ] Клиент обязан быть «вежливым»: `robots.txt`, ≤1 запрос в 2–3 с на домен,
      честный `User-Agent` с контактом, кэш скачанного, без параллельных потоков
      на один хост.
- [ ] `main.py`: CLI (`--source`, `--mode {http,browser}`, `--category-url`, `--limit`,
      `--output`, `--errors-output`), атомарная запись через `.tmp` + rename, ошибки
      отдельным файлом, статистика. `--mode` по умолчанию `http`.
- [ ] Тесты на fixtures — без сети.

**Готово когда:** одна команда даёт валидный JSON минимум по 20 карточкам.

## Phase 3 — карта характеристик (1 день) ⬅ ядро «расстановки»

Это и есть то, ради чего всё затевается. Файл
`data/catalog_processing_rules/scraped_attr_map.<категория>.json`:

```json
{
  "schema_version": 1,
  "category": "perforatory",
  "attributes": {
    "Мощность": {"attribute": "power_w", "unit": "Вт", "type": "integer"},
    "Тип патрона": {"attribute": "chuck_type", "type": "option",
                    "values": {"SDS-plus": "sds-plus", "SDS-max": "sds-max"}},
    "Вес": {"attribute": "weight_kg", "unit": "кг", "type": "decimal"}
  },
  "ignore": ["Гарантия", "Страна производства"]
}
```

- [ ] Выгрузить топ-30 характеристик источника по частоте в выбранной категории.
- [ ] Сопоставить с существующими `Attribute` и `CategoryAttribute` категории.
- [ ] Для `option`-атрибутов сопоставить значения **только с существующими**
      `AttributeOption` (по slug). Новых опций не создаём.
- [ ] Нормализация значений: число + единица («780 Вт» → `780`), десятичная
      запятая, диапазоны — в отчёт, не в базу.
- [ ] Всё несопоставленное — в `ignore` или в отчёт `unmapped`.

**Готово когда:** карта покрывает ≥ 80% характеристик источника по частоте, и
каждая запись указывает на реально существующий `Attribute`.

## Phase 4 — импортёр: матчинг и запись (2 дня)

Команда `catalog_import_scraped <json> --category <slug> [--dry-run] [--limit N]`.

**Матчинг карточки к нашему товару — ключ `(бренд, нормализованная модель)`.**

> **Переписано 2026-07-28 по результатам Phase 1.** Исходный план строил матчинг на
> артикуле — замер показал, что это невозможно. Протокол: `docs/parser-mvp/source-structure.md`.

**Почему не артикул.** `article` в нашей БД не идентифицирует товар:

- **не уникален**: `РСВ-140807` висит одновременно на `Перф. П-1200к-м ВИХРЬ`,
  `Перф. П-900к-в ВИХРЬ` и `Перф. П-26/800ЭР Интерскол`. По каталогу целиком дубли
  массовые — один артикул на 7–9 товаров (костюмы и обувь разных размеров);
- **часто пустой**: 13 226 товаров вообще без артикула;
- **у разных брендов совпадает**: `75/3/2` — Ресанта П-30-900К, `72/3/2` — ВИХРЬ
  П-900К. Артикул применим **только в паре с брендом**;
- у Интерскола 7 из 8 артикулов — коды поставщика `РСВ-…`, к производителю отношения
  не имеющие (0/8 совпадений с сайтом).

**Порядок матчинга** по убыванию надёжности:

1. `(бренд, модель)` — точное совпадение нормализованных значений. Бренд извлекается
   из названия (`brand_slugs.py`), модель — из названия и из URL источника
   (`perforator-p-30-900k-resanta`). Даёт **40/49 = 82%** на замере Phase 1:
   Ресанта 6/6, ВИХРЬ 9/9, Интерскол 7/8, ЗУБР 18/26;
2. `(бренд, модель)` через pg_trgm с порогом схожести — для остатка;
3. `article` — **только как подтверждение** уже найденного совпадения, никогда как
   первичный ключ. Достоверен у Ресанты (6/6) и ЗУБРа (26/26 — там артикул и есть
   обозначение модели), у ВИХРЯ 3/9, у Интерскола 0/8.

**Нормализация модели — критично.** Подстрочное сравнение **запрещено**: `ЗП-2680`
является подстрокой `ЗП-26-800`, наивный матч склеит разные модели. Сравнение только
после приведения к канону (регистр, дефисы, пробелы, разделители) и **целиком**, а не
вхождением.

Правила: одна карточка → максимум один товар; **неоднозначное совпадение пропускается
и уходит в отчёт** — это касается и матчей «многие к одному» (`П-800к` / `П-800к-в`,
дубли URL Интерскола); товар вне указанной категории не трогается. `code_1c` в
матчинге не участвует.

**Запись:**

- [ ] Характеристики → `ProductAttributeValue` с `source="marketplace"`,
      `confidence` из карты; перезапись решает `source_priority` — `manual`
      и `import_1c` не затираются.
- ~~Фото → `ImagePipeline`~~ — **фотографии не берём** (решение владельца 2026-07-27):
      источник — сайты производителей, работаем только с характеристиками.
- [ ] Транзакция на товар, а не на весь прогон.
- [ ] `--dry-run` печатает полный план: сколько совпало, сколько PAV создастся,
      сколько перезапишется, сколько фото скачается — **без единой записи**.
- [ ] Итоговая статистика + JSON-отчёт: `matched`, `ambiguous`, `not_found`,
      `unmapped_attributes`, `image_errors`.
- [ ] `rebuild_attrs_cache` по затронутым товарам после записи.
- [ ] Интеграционные тесты: матчинг, идемпотентность, защита `manual`.

# 7. Критический путь

```text
Phase 0 ✅ → Phase 0.5 (результат уже здесь) → 1 → 2 → 3 → 4 → 5 → 6 → 7
```

Phase 0.5 не зависит от парсера и даёт первую расставленную выборку сама по себе —
поэтому идёт вперёд всего остального.

Phase 3 (карта характеристик) можно готовить параллельно с Phase 2 — как только
Phase 1 дала список характеристик источника. Это единственное разумное
распараллеливание; остальное строго последовательно.

**Оценка:** 7–8 рабочих дней до расставленной категории. Самая недооценённая
часть — Phase 3 и разбор `ambiguous` в Phase 5: там ручная работа, которую нельзя
пропустить, не получив мусор в каталоге.

# 8. Риски

**R1. Матчинг не сходится.** С нашей стороны риск снят разведкой: артикулы —
номера производителя, непустые у 161 из 188. Остаётся сторона источника:
публикует ли он артикул производителя в карточке. *Действие:* проверяется на
Phase 1. Если не публикует — матчить по бренду + модели из названия, начав с
Bosch и Makita, где модельные обозначения предсказуемы (`GBH 2-26DFR`, `HR2470`).

**R2. Характеристики не ложатся в нашу схему.** У источника своя гранулярность.
*Действие:* карта Phase 3 покрывает то, что покрывается; остальное честно
уходит в `unmapped`. Не изобретать новые `Attribute` ради покрытия — это
отдельное решение по `operations/new-tool-type.md`.

**R3. Антибот.** 403/429/CAPTCHA. *Действие:* снизить частоту, зафиксировать
ответы. Агрессивный обход защиты в MVP не делаем; если данные без него
недоступны — стоп и отдельное решение.

**R4. Перезапись руками расставленного.** *Действие:* `source_priority` уже
защищает `manual`; в приёмку добавлена явная проверка запросом.

**R5. Правовое.** Фотографии и описания с чужого сайта — охраняемый контент,
и риск возникает **в момент публикации у нас**, а не при сборе. Характеристики
как факты (мощность, тип патрона) — существенно менее рискованны, чем фото и
авторские описания. Решение о публикации фотографий принимает владелец
осознанно, до Phase 5. Технически roadmap позволяет запустить всё
**только с характеристиками**, отключив фото одним флагом — если правовой
вопрос не закрыт, начинать стоит именно так.
