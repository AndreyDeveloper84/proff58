**Связанный документ:** [2026-07-29-ADMIN_UX_STAGE_A.md](2026-07-29-ADMIN_UX_STAGE_A.md)

## 0. Резюме позиции

С диагнозом согласен полностью: проблема организационная, а не визуальная.
С целевой картиной (§5, §7) согласен почти во всём — это хорошо продуманный
разбор, и большинство пунктов я готов принять как техзадание.

Возражений два, оба принципиальные:

1. **Ролей спроектировано шесть — пользователь один.** Заказчик подтвердил:
   в админке работает один человек-универсал. Шесть ролей — это матрица прав,
   которую некому применять, и шесть вариантов каждого экрана.
2. **Вариант B оценён как «низкий риск» — это неверно.** Собственные
   task-based views означают заново реализовать списки, фильтры, поиск,
   формсеты, валидацию, права, массовые действия. При этом **12 из 15
   требований §7 достижимы штатным Django admin** — таблица в §3 ниже.

Плюс документ не называет уже существующих дефектов: часть «неудобно» — это
не UX, а поломки, которые чинятся за полтора дня (§6).

Встречное предложение: **Вариант A+** — Django admin с кастомными шаблонами,
виджетами и вьюхами внутри самого admin. Итог v1 — около 2–2.5 недель вместо
2–4 месяцев по этапности §11, причём админка остаётся рабочей после каждого
спринта.

## 1. Где согласие полное

Не переформулирую, просто фиксирую как принятое:

- диагноз §3.1 — навигация отражает устройство системы, а не задачи;
- §3.3 — заказ представлен как запись БД, нужен один человекочитаемый статус;
- §3.4 — карточка товара смешивает контексты;
- §5.4 — предотвращение ошибки важнее сообщения об ошибке;
- §5.6 — постепенное раскрытие сложности;
- §7.1 — дашборд направляет к работе, а не показывает графики;
- §7.2 — готовые очереди вместо конструктора фильтров;
- §7.5 — индикатор готовности товара со списком, чего не хватает;
- §9 — скрыть slug, внутренние ID, JSON-снимки, хэши, ключи идемпотентности,
  source/confidence;
- §12 — не делать универсальный конструктор страниц, не менять только тему,
  не разрешать ручную правку статусов/цены/остатков;
- §16 — формат фиксации общего решения принимаю, заполненный вариант в §9.

Отдельно отмечу §7.8: сравнение «сейчас / предложено» вместо таблицы находок —
это лучшее место документа. Модель `CatalogChange` уже хранит `before_value`,
`proposed_value`, `after_value` (`apps/catalog/models.py:1160`), то есть данные
для такого экрана есть, нужен только шаблон.

## 2. Расхождение №1: шесть ролей на одного человека

**Факт:** заказчик на прямой вопрос ответил — «всё сразу, один человек».
Универсал без разделения: он же разбирает каталог, он же обрабатывает заказы,
он же ведёт контент.

Матрица §4 (Менеджер / Контент-менеджер / Кладовщик / Маркетолог /
Администратор / Разработчик) проектирует организацию, которой пока нет. Цена
ошибки здесь не теоретическая: каждый экран нужно продумать в шести вариантах
видимости, завести группы и права, и потом поддерживать это при каждом
изменении.

**Предлагаю:**

- Два контура — **да**, но контур «Система» это скрытие пунктов из меню
  (`hide_models`), а не отдельная площадка с собственными правами.
- Шесть ролей — **нет для v1**. Одна учётка, разделение визуальное.
- Группы прав вводить в тот момент, когда появится второй человек. Это
  примерно полдня работы в любой момент — откладывание ничего не удорожает.

Ответ на **D2**: не «менеджер и контент-менеджер», а «ролей в v1 нет,
пользователь один; разделение Работа / Система — визуальное».

## 3. Расхождение №2: Вариант B дороже, чем описано

Формулировка «переиспользуем Django auth, permissions, модели и сервисы,
низкий риск» верна про **backend** и неверна про **UI**. Собственные
task-based views придётся снабдить: списками с пагинацией и сортировкой,
фильтрами, поиском, инлайн-формсетами, валидацией форм, CSRF, проверками
прав, хлебными крошками, массовыми действиями, автокомплитами. Всё это в
Django admin уже написано и оттестировано. Отказ от него — это не
«переиспользование», это вторая UI-система на поддержке навсегда.

Проверяемый контраргумент — что из §7 реально требует выхода за admin:

| Требование | В Django admin? | Чем делается |
|---|---|---|
| 7.1 Дашборд «Сегодня» | **Да** | `templates/admin/index.html` + вьюха со счётчиками |
| 7.2 Один статус + следующее действие | **Да** | `list_display` + `format_html`; кнопки через `ModelAdmin.get_urls()` |
| 7.2 Готовые очереди | **Да** | `SimpleListFilter` + `custom_links` |
| 7.3 Карточка заказа, переход кнопкой | **Да** | свой `change_form.html` + admin-view, вызывающая доменный сервис |
| 7.4 Список товаров с фото и проблемами | **Да** | миниатюра в `list_display`; колонка «Причина в очереди» уже есть |
| 7.5 Вкладки карточки | **Да** | jazzmin `changeform_format` (совместимость с 3.0.4 проверить) |
| 7.5 Индикатор готовности «75%» | **Да** | readonly-поле; `publication_errors()` уже написан |
| 7.6 Фото: миниатюры, «сделать главной» | **Да** | `is_main` и `sort_order` уже в модели (`apps/catalog/models.py:786-787`) |
| 7.6 Загрузка и сортировка перетаскиванием | **Частично** | свой виджет или пакет; ~день работы, стек менять не нужно |
| 7.7 Только характеристики своей категории | **Да** | `formfield_for_foreignkey` + фильтр по `CategoryAttribute` |
| 7.8 Сравнение «сейчас / предложено» | **Да** | свой `change_form` для `CatalogChange`; данные в модели есть |
| 7.9 Управление блоками главной | **Нет — и не про стек** | нужна модель блоков главной; после неё — обычный admin |
| 7.10 Редактор баннера | **Да** | форма + свой шаблон |
| §8 Глобальный поиск | **Да** | расширить `search_model` в `JAZZMIN_SETTINGS` |
| §8 Сохранённые пользователем фильтры | **Нет** | нужна модель + UI; при одном пользователе избыточно |
| §8 История изменений | **Да** | `LogEntry` уже пишется Django, нужен только экран |
| §8 Откат к версии контента | **Нет** | нужна модель версий; предлагаю не в v1 |

**Двенадцать из пятнадцати** — это Django admin с кастомными шаблонами.
Три исключения не требуют смены стека: drag-n-drop — виджет, блоки главной —
новая модель, откат версий — новая модель.

**Предлагаю переименовать вариант:**

> **Вариант A+** — Django admin как единственная площадка, поверх неё —
> собственные шаблоны, виджеты, admin-views и дашборд. От Варианта A
> отличается тем, что мы не ограничиваемся настройками. От Варианта B — тем,
> что не создаём вторую навигацию, вторую систему прав и второй набор форм.

Ответ на **D5**: внутри Django — да, но **внутри admin**, а не рядом с ним.

## 4. Пропущенная в документе задача: предпросмотр — это фронт

«Предпросмотр» стоит в 7.4, 7.5, 7.6, 7.10 и в §8 как обязательное свойство,
и в §13 как критерий готовности (пункты 5 и 6). При этом:

- витринное API отдаёт **только опубликованное** — `visible_products()`,
  `apps/catalog/api/views.py:141`;
- в Next.js нет draft-режима (по коду `frontend/` ничего похожего нет);
- значит «посмотреть результат до публикации» сегодня технически невозможно.

Чтобы это заработало, нужен отдельный трек: draft-режим в Next.js + endpoint,
отдающий черновики по подписанному токену + закрытие от индексации. Это
несколько дней фронтовой работы, и ни в один из этапов §11 они не заложены.

**Предлагаю решить явно:** либо включаем фронтовый трек в план и признаём
сдвиг сроков, либо в v1 ограничиваемся кнопкой «Смотреть на сайте» для уже
опубликованного (`get_absolute_url` сейчас тоже не определён — это полчаса
работы), а полноценный предпросмотр переносим.

## 5. Этап 0: согласен по сути, не согласен по форме

## 6. Чего в документе нет: существующие дефекты

Документ описывает целевое состояние, но не называет того, что сломано уже
сейчас. Это важно, потому что часть жалобы «неудобно» — это не UX, а баги, и
чинятся они несопоставимо дешевле редизайна.

1. **Матрица переходов заказа в админке не применяется.**
   `apps/orders/transitions.py` существует, но `can_transition` вызывается
   только в `apps/sync_1c/use_cases.py:819` и
   `apps/orders/invoice_lifecycle.py:125`. `Order.save()` не валидирует.
   Из админки статус переводится куда угодно: «Выполнен» → «Новый»,
   «Отменён» → «В доставке». Принцип §5.4 в документе заявлен — но как цель,
   а не как «вот конкретный существующий дефект».
2. **Снимки заказа редактируемы.** `readonly_fields` в `OrderAdmin` — три
   поля; `total`, `vat_amount`, `order_number`, `customer_*`,
   `promo_snapshot`, `delivery_snapshot` правятся руками без пересчёта строк.
3. **Три экрана рендерят `<select>` на всю таблицу:** `CartItemInline.product`
   (`apps/orders/admin.py:81`), `ProductAttributeValueInline.value_option`
   (`apps/catalog/admin.py:426`), `OrderAdmin.user`. Это буквально «админка
   виснет» — и чинится за вечер тремя строками.
4. **`brand` в `list_filter`** (`apps/catalog/admin.py:536`) — это `CharField`,
   в сайдбаре рендерятся все бренды каталога.
5. **Два дерева категорий.** В документе назван дубль «Акции» — верно, но
   есть и второй: «Категории» (`Category`) и «Категории (сайт)»
   (`SiteCategory`, прокси на `is_site_v2=True`) стоят рядом в одном разделе.
6. **Нет `get_absolute_url`** — а «Предпросмотр» требуется в пяти местах §7.
7. **Нет `save_on_top`** при семи блоках и пяти инлайнах в карточке товара.

**Предлагаю выделить это в «спринт 0»** — полтора дня до любого редизайна.
Он закрывает и денежный риск (пп. 1–2), и главную причину ощущения
«тормозит» (пп. 3–4).

## 8. Ответы на вопросы §15

1. **Согласен ли с диагнозом?** Да, полностью. Добавлю: часть проблемы — не
   организация, а конкретные дефекты (§6), и их надо отделить от редизайна.
2. **Есть ли причина сразу выбирать SPA?** Нет. Более того, я считаю
   преждевременным и Вариант B — Django admin не исчерпан даже наполовину
   (§3).
3. **Три сценария с наибольшей ценностью?** (1) разобрать и опубликовать
   товар — ежедневная ручная работа наибольшего объёма; (2) обработать заказ
   от нового до выданного; (3) заменить баннер или выложить статью.
4. **Что опасно скрывать?** `code_1c` и артикул — по ним человек сверяется
   с 1С и с поставщиком, их надо оставить видимыми (только для чтения).
   Причину непубликации и статус выгрузки в 1С скрывать нельзя — без них
   человек не поймёт, почему товара нет на сайте. Остальное из §9 —
   согласен скрыть.
5. **Что не учтено в экране заказа?** Резерв и его срок (`reserved_until`,
   `reservation_status`) — заказ может «протухнуть»; слот доставки и его
   занятость; счёт B2B отдельной сущностью со своим жизненным циклом
   (`apps/orders/invoice_lifecycle.py`); гостевой доступ по `access_token`.
6. **Достаточно ли разделения ролей?** Вопрос преждевременный — см. §2.
7. **Что требует подтверждения?** Отмена заказа, отметка счёта оплаченным,
   массовая публикация товаров, массовая перепривязка категории, удаление
   чего угодно. Двухэтапного согласования при одном человеке — ничего.
8. **Минимум версий и аудита для контента?** Аудит — `LogEntry` (уже есть,
   нужен экран). Версии — не в v1. Черновик/публикация — уже в моделях.
9. **Чем подтвердим, что стало удобнее?** Не замерами времени, а прямой
   проверкой: даём человеку, не работавшему в админке, десять сценариев из
   §13 и смотрим, где он застревает. Плюс объективное: сколько товаров он
   разбирает за час до и после.
10. **Что избыточно для v1?** Шесть ролей; сохранённые пользователем фильтры;
    версионирование с откатом; Этап 0 как отдельный этап с замерами;
    универсальный конструктор главной (согласен с §12 — берём фиксированный
    набор блоков).

## 9. Сведённое предложение к утверждению

Заполняю форму из §16 документа v0.1 — как предложение, не как факт.

```text
Согласовано (предлагается):
- два контура: Работа и Система, разделение визуальное (hide_models);
- реализация — внутри Django admin (Вариант A+), без второй площадки;
- ролей в v1 нет: один пользователь-универсал;
- все переходы заказа — только через доменные сервисы и матрицу transitions;
- цена и остатки 1С — только для чтения, с подписью-объяснением;
- первым редизайном идёт каталог, вторым — заказы;
- существующие дефекты выносятся в спринт 0 до любого редизайна.

Изменено после обсуждения:
- Вариант B → Вариант A+ (admin + свои шаблоны/виджеты/вьюхи);
- шесть ролей → ноль ролей в v1;
- Этап 0 (наблюдение с замерами) → час наблюдения без отдельного этапа;
- D3: первый сценарий — каталог, а не заказы.

Отклонено для v1:
- сохранённые пользователем фильтры;
- версионирование контента с откатом;
- отдельное рабочее пространство рядом с admin;
- универсальный конструктор страниц.

Открытые вопросы:
- предпросмотр черновиков: включаем фронтовый трек или переносим (§4);
- два дерева категорий: какое оставить в меню (§6.5);
- вкладки в карточке товара: проверить jazzmin 3.0.4 на совместимость
  с пятью инлайнами;
- нужен доступ к dev-админке под реальной учёткой — оба аудита сделаны
  по коду, живой интерфейс никто из нас не видел.
```

| **4. Контент** | Баннеры, блоки главной (новая модель), разведение скидок и промо-страниц | 3 дня |
| **фронт, параллельно** | Draft-режим для предпросмотра — если решим включать (§4) | 2–3 дня |

Итого **~2–2.5 недели** против 2–4 месяцев по этапности §11. После каждого
спринта админка в рабочем состоянии, откатывать нечего.
