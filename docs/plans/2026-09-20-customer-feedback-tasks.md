## Основание и границы анализа

Проанализированы текущие файлы рабочего дерева, включая уже существующие незакоммиченные изменения. Код приложения не изменялся. Проверки выполнялись чтением frontend/backend и существующих тестов; поведение опубликованного сайта, реальные данные каталога и задержка у пользователя не воспроизводились. Приоритеты рекомендованные: P1 — мешает выбору или покупке, P2 — улучшение интерфейса. Создание в Linear требует подключения интеграции; на момент подготовки задачи там не созданы.

Рабочие трактовки неоднозначных пожеланий:

- «Чуть светлее/темнее фона» — карточки должны отчётливо отделяться от страницы; предлагаем светлые карточки на слегка сером фоне и различимые поверхности в тёмной теме.
- «Предпросмотр как на ВБ» — быстрый просмотр товара поверх списка по нажатию на фото/название, с сохранением позиции списка. Это предлагаемое поведение, а не утверждение о текущем интерфейсе Wildberries.
- «Бренд ведёт в категорию» — отдельная каталожная выдача товаров выбранного бренда с возможностью выбрать товарную категорию. Metabo не следует автоматически привязывать к одной произвольной категории.
- «Шрифт, окошки везде крупнее» — увеличить основной текст, поля, кнопки, выпадающие меню и диалоги на всех основных покупательских экранах. Предлагаемые размеры ниже — стартовые критерии реализации.

**Приоритет:** P1. **Область:** корзина и пересчёт заказа.

**Проблема и подтверждение.** В `CartItemRow.tsx` между кнопками «−» и «+» находится `<span>{line.quantity}</span>`. Ввод невозможен. На приложенном пользователем скриншоте ожидается редактирование числа непосредственно между кнопками.

**Что сделать.** Заменить span полем ввода с числовой клавиатурой на мобильном. Разрешить выделить и целиком заменить число, вставить значение. Хранить промежуточный ввод локально; применять по Enter или потере фокуса, не отправляя запрос на каждый символ. Escape отменяет редактирование. Сохранить кнопки ± и существующий API. Enter с последующим blur не должен отправлять два одинаковых запроса.

**Критерии приёмки:**

- Можно заменить 1 на 15 или 159, если это допускает сервер; после ответа верно пересчитываются строка, общий итог и счётчик корзины.

- Быстрые нажатия, Enter+blur и переход к ± после ввода не вызывают двойных изменений и отката к устаревшему ответу.
- Поле вмещает многозначное число, подписано для screen reader, доступно клавиатурой на desktop/mobile.

**Точки изменения:** `CartItemRow.tsx`, `CartItemRow.test.tsx`, при необходимости `CartProvider.tsx`, `frontend/app/cart/page.tsx`. Проверить существующие API-тесты корзины; backend менять только при обнаруженном пробеле контракта.

## PERF-01. Диагностировать и устранить «бренды не нажимаются несколько минут»

**Приоритет:** P1. **Тип:** исследование с исправлением подтверждённой причины.

**Сообщение пользователя.** При первом тестировании бренды казались ненажимаемыми, спустя несколько минут заработали. Устройство, браузер, URL, время события и сеть неизвестны. Это наблюдение пользователя, а не воспроизведённый дефект.

**Что подтверждено кодом.** Популярные бренды — `next/link`, без собственной блокировки или таймера. Текущий путь ведёт в `SearchPage`, которая ожидает `searchProducts`. В `fetchSearchFromApi` используется `cache: "no-store"` без явно заданного timeout/AbortSignal; неуспешный HTTP-ответ превращается в пустой список и выглядит как «ничего не найдено». Отдельной loading-границы у поиска не найдено. Корневой layout дополнительно ожидает theme, info pages и категории. Это направления расследования, а не доказанная причина задержки. Отсутствие собственного timeout не означает буквально бесконечное ожидание: могут действовать ограничения платформы.

**Что сделать:**

1. Воспроизвести первый и повторный переход в production-сборке: чистый профиль, холодный/тёплый кэш, desktop/mobile, обычная и замедленная сеть. Проверить отдельно первый вход и повторную навигацию.
2. Записать Console, Network/HAR и серверные длительности: дошёл ли click, есть ли перекрывающий элемент, когда начался запрос, где задержка между браузером, Next, Django и БД. Проверить ошибки JS/гидрации и prefetch, не считать их причиной без данных.
3. Если тормозит поиск/фильтр — исследовать запрос и план выполнения на репрезентативном объёме данных. Если проблема только в dev — документировать прогрев/компиляцию отдельно и перепроверить production.
4. Исправить обнаруженную причину. Для запросов добавить ограниченное ожидание, видимую загрузку и различимые состояния «ошибка»/«нет товаров»; стартовые ориентиры — реакция интерфейса до 200 мс и сообщение об ошибке зависшего API не позднее 10 секунд. Это предлагаемые бюджеты, не текущие замеры.

**Критерии приёмки:** приложены условия и запись воспроизведения либо честный результат «не воспроизведено» с охватом проверок; при установленной причине есть замеры до/после. В 20 последовательных проверках холодных/тёплых переходов нет потерянных нажатий и ожидания без индикации. Обычная загрузка выдачи на согласованном стенде укладывается в согласованный бюджет (стартовый ориентир до 3 секунд). Искусственно зависший/ошибочный API даёт понятную ошибку с повтором в установленный срок. Не закрывать расследование только на основании добавления спиннера. После UX-07 повторить проверки брендовой выдачи; старый дефект поиска не считать исправленным только из-за смены ссылки.

## DATA-01. Переработать подбор и отображение характеристик товаров

**Приоритет:** P1. **Область:** каталог, страница товара, API и качество данных.

**Проблема и подтверждение.** `ProductSpecs.tsx` объединяет только значения через «·» в одну обрезаемую строку; домашний вариант `ProductCard.tsx` отдельно берёт первые три значения и выводит их размером 10 px. Названия теряются. В `ProductListSerializer.get_attributes` выбираются фильтруемые/сравниваемые характеристики, сортируются по имени и ограничиваются лимитом: первые характеристики не обязательно наиболее важные для данного типа товара. На странице товара уже есть пары название/значение и блок первых шести характеристик, поэтому требуется улучшить существующую структуру, а не считать таблицу отсутствующей. Detail API отдаёт все характеристики; адаптер уже форматирует числа, boolean и единицы. Реальная полнота и корректность данных в БД не проверялась.

**Что сделать.** Определить ключевые характеристики и порядок по типам товаров. Для компактной карточки показывать 2–3 осмысленные пары «Название: значение», на странице товара — основные параметры рядом с покупкой и полную таблицу, при необходимости по группам. Согласовать этот порядок с быстрым просмотром. Проверить источник и нормализацию данных: пустые и дублирующиеся значения, технические названия, единицы и их повторы, неверные типы. Не заполнять отсутствующие технические параметры предположениями; отдельным списком зафиксировать товары, которым нужен контент.

**Примеры порядка, подлежащие сверке с каталогом:** для перфоратора — энергия удара, мощность, патрон; для аккумуляторного инструмента — напряжение, крутящий момент, комплектация аккумулятором; для крепежа — размеры, материал, покрытие. Это схема выбора параметров, не данные конкретных товаров.

**Критерии приёмки:**

- По характеристике понятно, что означает число; нет строк из нескольких безымянных значений.
- Названия, значения и единицы единообразны; ноль и «Нет» не исчезают как ложные значения, пустые параметры не создают пустых строк.
- Ключевые параметры выбираются по типу товара, а не случайному порядку/алфавиту; порядок стабилен между карточкой, предпросмотром и полной страницей.
- Длинные значения переносятся, таблица читается на 320–375 px; кнопка «Все характеристики» ведёт к полной информации.
- Для отсутствующих характеристик используется аккуратное пустое состояние; не выводятся выдуманные значения.
- Проверена выборка минимум из 10 реальных товаров разных категорий, включая товар без характеристик, с длинными значениями и с неполным набором данных; приложены примеры API и скриншоты до/после.
- При выявлении проблем импорта/контента приложен конкретный список товаров и правил исправления. Представление считается готовым отдельно от наполнения, пока все данные не проверены.

**Точки изменения:** `frontend/components/product/ProductSpecs.tsx`, `ProductCard.tsx`, `frontend/app/product/[slug]/page.tsx`, `frontend/lib/adapters.ts`, `apps/catalog/api/serializers.py`; нормализацию/импорт затрагивать по результатам аудита данных.
