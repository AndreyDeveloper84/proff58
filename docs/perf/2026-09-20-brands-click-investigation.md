# PERF-01: «бренды не нажимаются несколько минут» — расследование

Дата замеров: 20.09.2026. Сырые данные и скрипты — в `docs/perf/2026-09-20-brands-click/`.

## Вывод

Жалоба воспроизведена частично. Клик по плитке бренда доходит всегда, перекрывающих
элементов и ошибок JavaScript нет. Но после клика сайт **от 2 до 10 секунд не показывал
ничего**: ни индикатора, ни скелетона, ни смены адреса. Для покупателя это выглядит как
«плитка не нажимается».

Задержка в «несколько минут» не воспроизведена. Устройство, браузер, сеть и время события
неизвестны, поэтому этот случай не подтверждён и не опровергнут. Правдоподобное
объяснение — холодный старт стенда после выкладки: `deploy.yml` пересоздаёт контейнеры,
и до прогрева запросы к каталогу висят. Раньше у таких запросов не было таймаута.
Проверить можно, сверив время жалобы с запусками `deploy.yml` и с `upstream_response_time`
в логах nginx. Доступа к серверу в этой работе не было.

## Причина

1. У страницы поиска не было `loading.tsx`. Плитки вели на `/search?q=<бренд>`, а это
   динамическая страница. Next 16 не подгружает такие страницы заранее и при переходе
   держит прежний экран, пока сервер не отрендерит новый
   (`node_modules/next/dist/docs/01-app/02-guides/prefetching.md`).
2. Поиск — самый медленный запрос каталога. Страница ждала сразу два таких запроса.
3. У запросов листинга, поиска и товара не было таймаута. Зависший каталог держал переход
   без ограничения по времени.
4. Сбой поиска не имел своего экрана ошибки.

## Замеры «до» (proff58.ru)

Сервер, запросы `curl` с рабочего места. Сетевой минимум до сервера — около 0,9 с
(`/healthz/`, `robots.txt`).

| Запрос | Время ответа |
|---|---|
| `/healthz/`, статика | 0,9–1,0 с |
| `products/?brand=<бренд>` (точный фильтр) | 1,2–1,3 с |
| `products/?search=<бренд>` | 1,3–2,7 с |
| `search/facets/?search=<бренд>` | 2,1–2,2 с |
| страница `/search?q=<бренд>`, первый байт | 2,6–4,4 с |
| страница `/search?q=<бренд>`, целиком | 3,6–7,1 с |
| страница категории, первый байт | 0,95 с |

За вычетом сети: поиск в Django занимает 0,4–1,8 с, фасеты поиска — около 1,2 с, точный
фильтр бренда — 0,3–0,4 с. Страница категории отдаёт первый байт сразу, потому что
стримит скелетон; страница поиска этого не делала.

Браузер (headless Chrome, настоящие события ввода, половина прогонов с очищенным кэшем):

| Сценарий | Прогонов | До первого отклика | До контента | Потерянных кликов |
|---|---|---|---|---|
| desktop 1440, обычная сеть | 10 | 2,1–5,7 с | 2,1–5,7 с | 0 |
| mobile 375, медленная сеть (300 мс, 200 КБ/с) | 10 | 4,0–10,4 с | 4,0–10,4 с | 0 |

«До первого отклика» равно «до контента»: промежуточной индикации не было вовсе.
Перекрытий плитки — 0, ошибок консоли — 0. Гидратация на холодном входе — до 8,2 с;
до неё клик работает обычным переходом по ссылке.

## Что сделано

- Плитки ведут на `/brands/<slug>` (UX-07). Там точный фильтр бренда вместо поиска: он
  быстрее в 3–5 раз.
- Плитка сразу показывает, что переход начался (`useLinkStatus`).
- `/search` получил `loading.tsx` (скелетон по клику) и `error.tsx` с «Повторить».
- Шапка бренда и список товаров запрашиваются параллельно; счётчик для подсказки
  «ещё N товаров» считается в отдельной границе и страницу не задерживает.
- Товар и его совместимость запрашиваются параллельно, а не подряд.
- Таймаут 8 с на запросы листинга, поиска, бренда и товара. Сбой и таймаут дают экран
  ошибки, а не «ничего не найдено».
- Удалён неиспользуемый `fetchSearchFromApi`, который превращал ошибку API в пустой список.

## Замеры «после»

Локальная production-сборка. Перед Django стоит прокси, который задерживает каждый ответ
каталога на 2 с — это медленнее, чем бой. Абсолютные цифры с боевыми не сравниваются:
сеть и объём данных другие. Сравнивается время до первого отклика.

| Сценарий | Прогонов | До первого отклика | До контента | Потерянных кликов |
|---|---|---|---|---|
| плитка бренда, desktop | 10 | 13–79 мс | 2,1–2,3 с | 0 |
| плитка бренда, mobile | 10 | 14–106 мс | 2,1–2,3 с | 0 |
| поиск из шапки, desktop | 5 | 60–69 мс | 2,1 с | 0 |
| API не отвечает вовсе | 4 | 12–51 мс | экран ошибки через 8,1–8,4 с | 0 |
| API отвечает 500 | 4 | 12–40 мс | экран ошибки через 0,1 с | 0 |

Бюджеты из постановки: отклик до 200 мс — выполнен; ошибка зависшего API не позднее
10 с — выполнена; 20 последовательных переходов без потерянных кликов и без ожидания
вслепую — выполнено.

## Что осталось

- Бюджет «обычная выдача до 3 секунд» на боевом стенде проверяется после выкладки. Скрипт
  `click-test.mjs` запускается против любого адреса (`BASE=https://…`).
- Поиск по каталогу остаётся медленным (до 1,8 с в Django плюс 1,2 с фасеты). Это отдельная
  задача: `EXPLAIN ANALYZE` для `filters.search_match` на боевом объёме данных.
- Гидратация главной на холодном входе занимает до 8 с. На кликабельность ссылок это не
  влияет, но задерживает корзину и избранное.
