# Настройка MAX-бота

Инструкция по регистрации бота, получению токена и настройке webhook
для интеграции магазина «Профессионал» с мессенджером MAX.

> Связанные документы: [ARCHITECTURE.md](ARCHITECTURE.md) (раздел `integration_max`),
> issue #47 (реализация webhook handler).

---

## 1. Регистрация бота

### 1.1 Подготовка

1. Зайти на [dev.max.ru](https://dev.max.ru) → раздел «Для партнёров»
2. Создать и верифицировать профиль организации (ИП или самозанятый)
3. Пройти модерацию

### 1.2 Создание бота

1. В панели партнёра создать нового бота
2. Указать название: `Профессионал` (или `Профессионал Dev` для staging)
3. Получить **токен бота** (access token)
4. Сохранить токен в `.env` (см. раздел 3)

> **Два бота:** для staging и production нужны отдельные боты с отдельными
> токенами, чтобы webhook-и не пересекались.

## 2. MAX Bot API — ключевые сведения

### 2.1 Базовый URL

```
https://platform-api.max.ru
```

### 2.2 Авторизация

Токен передаётся в заголовке:

```
Authorization: <BOT_TOKEN>
```

### 2.3 Лимиты

- Максимум **30 запросов/сек** на `platform-api.max.ru`
- Webhook: только **HTTPS** с сертификатом от доверенного CA

### 2.4 Основные методы

| Метод | Описание |
|-------|----------|
| `GET /me` | Информация о боте |
| `POST /subscriptions` | Подписка на webhook |
| `GET /subscriptions` | Текущие подписки |
| `DELETE /subscriptions` | Отписка |
| `POST /messages` | Отправка сообщения |
| `POST /answers` | Ответ на callback-кнопку |
| `GET /updates` | Long polling (только для dev) |

Добавить в `.env` окружения:

```env
# MAX Bot

MAX_WEBHOOK_SECRET=<случайный секрет для подписи, 32+ символов>

```

Переменные для staging и production **разные** (разные боты, разные токены).

## 4. Настройка webhook

### 4.1 Production / Staging

Webhook URL для подписки:

```
https://proff58.ru/api/max/webhook/         # production
https://dev.proff58.ru/api/max/webhook/      # staging
```

Подписаться через API:

```bash
curl -X POST https://platform-api.max.ru/subscriptions \
  -H "Authorization: $MAX_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{
    \"url\": \"https://proff58.ru/api/max/webhook/\",
    \"secret\": \"$MAX_WEBHOOK_SECRET\",
    \"update_types\": [\"bot_started\", \"message_created\", \"message_callback\"]
  }"
```

Поле `secret` обязательно. MAX передаёт его при каждом webhook-запросе в
заголовке `X-Max-Bot-Api-Secret`; обработчик сравнивает его с
`MAX_WEBHOOK_SECRET`.

### 4.2 Локальная разработка (ngrok)

```bash
# 1. Поднять dev-сервер
docker compose up -d

# 2. Запустить ngrok
ngrok http 8000

# 3. Подписаться на webhook с ngrok URL
curl -X POST https://platform-api.max.ru/subscriptions \
  -H "Authorization: $MAX_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{
    \"url\": \"https://<xxxx>.ngrok.io/api/max/webhook/\",
    \"secret\": \"$MAX_WEBHOOK_SECRET\",
    \"update_types\": [\"bot_started\", \"message_created\", \"message_callback\"]
  }"
```

### 4.3 Проверка подписки

```bash
curl -s https://platform-api.max.ru/subscriptions \
  -H "Authorization: $MAX_BOT_TOKEN" | python3 -m json.tool
```

### 4.4 Удаление подписки

```bash
curl -X DELETE "https://platform-api.max.ru/subscriptions?url=https://proff58.ru/api/max/webhook/" \
  -H "Authorization: $MAX_BOT_TOKEN"
```

## 5. Формат входящих событий (webhook payload)

MAX отправляет POST-запросы с JSON-телом на зарегистрированный URL.

### 5.1 bot_started — пользователь запустил бота

```json
{
  "update_type": "bot_started",
  "timestamp": 1718880000000,
  "chat_id": 12345678,
  "user": {
    "user_id": 87654321,
    "name": "Иван Иванов",
    "username": "ivan_ivanov"
  }
}
```

**Обработка:** сохранить `chat_id` для отправки уведомлений пользователю.

### 5.2 message_created — входящее сообщение

```json
{
  "update_type": "message_created",
  "timestamp": 1718880001000,
  "message": {
    "sender": {
      "user_id": 87654321,
      "name": "Иван Иванов"
    },
    "recipient": {
      "chat_id": 12345678,
      "chat_type": "dialog"
    },
    "body": {
      "mid": "mid.001",
      "seq": 1,
      "text": "Привет"
    }
  }
}
```

### 5.3 message_created с contact (после request_contact)

```json
{
  "update_type": "message_created",
  "timestamp": 1718880002000,
  "message": {
    "sender": {
      "user_id": 87654321,
      "name": "Иван Иванов"
    },
    "recipient": {
      "chat_id": 12345678,
      "chat_type": "dialog"
    },
    "body": {
      "mid": "mid.002",
      "seq": 2,
      "attachments": [
        {
          "type": "contact",
          "payload": {
            "vcf_info": "BEGIN:VCARD\r\nVERSION:3.0\r\nTEL;TYPE=cell:79001234567\r\nFN:Иван Иванов\r\nEND:VCARD\r\n",
            "max_info": {
              "user_id": 87654321
            },
            "hash": "a1b2c3d4e5f6..."
          }
        }
      ]
    }
  }
}
```

**Верификация контакта (HMAC-SHA256):**

```python
import hmac
import hashlib

def verify_contact(token: str, vcf_info: str, received_hash: str) -> bool:
    """Проверить подлинность контакта от MAX.
    
    vcf_info приходит с \\r\\n — перед хешированием
    заменить экранированные последовательности на реальные переносы.
    """
    vcf_bytes = vcf_info.replace("\\r\\n", "\r\n").encode("utf-8")
    expected = hmac.new(
        token.encode("utf-8"), vcf_bytes, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, received_hash)
```

### 5.4 message_callback — нажатие inline-кнопки

## 9. Авторизация через MAX (deeplink + one-time attempt, #492)

Вход, регистрация и привязка идут по модели **одноразовой попытки**: сайт создаёт
попытку → пользователь открывает бота по диплинку (нажимает «Начать», при первом
входе — делится номером) → бот проверяет данные и присылает **шестизначный код** →
покупатель вводит код на той же странице сайта → сайт завершает попытку
(`POST …/confirm/`) и поднимает сессию.

Почему код (DRF-2740). Раньше попытку завершал бот, а сессию поднимал опрос статуса
в браузере, создавшем попытку. Ссылку же можно переслать кому угодно: мошенник
создавал попытку у себя, слал ссылку покупателю — и одно нажатие «Начать» (если
MAX уже привязан) впускало мошенника в его кабинет. Теперь пересланная ссылка даёт
только код в чате покупателя; чтобы код сработал в чужом браузере, покупатель должен
его продиктовать — как код из SMS. Бот прямо пишет: никому не сообщать. Телефон и
профиль из контакта до ввода кода лежат в кэше под id попытки (TTL попытки), в БД не
попадают; сам код — нигде, только HMAC-хэш на попытке. Отслеживание гостевого заказа
(#520) идёт без кода — там завершает бот: чужая ссылка даёт лишь уведомления о чужом
заказе при совпадении номера.

Другого пути нет. Старый поток привязки по коду («Старт» в боте → номер → код)
удалён (DRF-2735): бот по номеру находил аккаунт и «подтверждал» номер кодом,
который сам же показывал, — чужой номер, вписанный в профиль, так подтверждался
первым же владельцем номера. Без живой попытки с сайта бот по номеру никого не
ищет: на «Старт» и на любой текст отвечает подсказкой, на номер — «ссылка уже не
действует».

### 9.1. Переменные окружения

| Переменная | Назначение |
|------------|------------|
| `MAX_BOT_USERNAME` | Имя бота для диплинка `https://max.ru/<username>?start=<token>` |
| `MAX_AUTH_ATTEMPT_TTL_MINUTES` | Срок жизни попытки (по умолчанию 5) |

`MAX_BOT_TOKEN` / `MAX_WEBHOOK_SECRET` — те же, что и для webhook. **Токен бота
хранится только на backend** и никогда не попадает во frontend (§11.7).

### 9.2. Диплинк

Кнопка «Войти через MAX» вызывает `POST /api/auth/max/start/`, backend возвращает
диплинк вида `https://max.ru/<MAX_BOT_USERNAME>?start=<public_id>.<secret>`.
В диплинке — **только случайный one-time токен**, без телефона/ID/e-mail (§11.1).
При открытии бот получает `start`-payload в событии `bot_started` (поле `payload`).

### 9.3. Эндпоинты

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/api/auth/max/start/` | создать попытку входа/регистрации |
| GET | `/api/auth/max/<id>/status/` | опрос статуса (только из создавшей сессии; сессию НЕ поднимает) |
| POST | `/api/auth/max/<id>/confirm/` | ввод кода из бота `{code}` — завершает вход/привязку/подтверждение; только из создавшей сессии; 400 `wrong_code` + `attempts_left`, 409 `code_not_issued` / `already_authenticated` |
| POST | `/api/auth/max/<id>/cancel/` | отмена попытки |
| POST | `/api/account/max/link/` | старт привязки MAX (авторизованный) |
| POST | `/api/account/max/unlink/` | отключить MAX (авторизованный) |
| GET | `/api/account/max/status/` | привязан ли MAX |
| POST | `/api/max/webhook/` | приём событий MAX (см. раздел 4) |

Статусы попытки: `pending` → `confirmation_required` (код выдан) → `completed`
(код введён) | `cancelled` | `expired` | `failed`. Frontend опрашивает статус раз в
2–3 с (по `confirmation_required` подсказывает ввести код), а завершает вход
ответом `confirm`. Правила кода (`apps/integration_max/confirm.py`): 6 цифр, 5
неверных вводов → `failed` (`code_attempts_exceeded`), повторное «Начать» тем же
MAX перевыпускает код (не больше 3 раз), другой MAX по той же ссылке получает «ссылка
уже использована», попытка живёт 5 минут с выдачи кода и не дольше 15 минут от
создания. Новый старт отменяет прежние незавершённые попытки той же сессии (и
стирает их отложенный телефон из кэша). Отслеживание заказа кода не использует
вовсе: бот сверяет номер с заказом сам, даже если у гостя MAX привязан к аккаунту.

Отказы самого контура кода (`failure_reason`): `code_attempts_exceeded` — 5
неверных вводов; `code_reissue_limit` — четвёртое «Начать»; `pending_lost` — кэш с
отложенным телефоном потерян (рестарт Redis, истёк TTL) — начать заново; `race` —
параллельное исполнение той же попытки; `no_max_user` — MAX не передал id
пользователя; `foreign_contact` — поделились контактом другого человека из
записной книжки (личность — всегда отправитель сообщения, `sender`, а не владелец
контакта из `max_info`); `inactive_account` — аккаунт заблокирован.

До выдачи кода ответы `status`/`confirm` для входа **не раскрывают** причину
отказа, по которой чужой браузер узнал бы, есть ли у номера аккаунт и какой
(`phone_unverified`, `password_account`, `user_has_other_max`,
`inactive_account`): сайт отдаёт `declined_in_max`, а честную причину человек
читает в чате бота; в БД и аналитике причина настоящая. После ввода кода причина
отдаётся как есть. После успешного входа бот присылает в чат «Выполнен вход на
сайт…» (событие уведомлений `max_login`, для подтверждения из кабинета —
`max_reauth`): если код выманили, владелец увидит чужой вход и отключит MAX.

### 9.4. Правила аккаунта (§10)

- MAX уже привязан → вход (повторно номер не запрашивается);
- телефон не найден → **создаётся аккаунт без пароля**, телефон подтверждён;
- телефон найден у аккаунта без привязки MAX → вход **только если** номер у
  аккаунта подтверждён и у аккаунта нет пароля (человек пришёл через MAX, отвязал
  его и входит снова). Иначе отказ, аккаунт не меняется (DRF-2735):
  - `phone_unverified` — номер вписан в профиль без проверки;
  - `password_account` — у аккаунта есть пароль или это сотрудник;
- конфликты (MAX у другого аккаунта / у аккаунта уже другой MAX / несовпадение
  телефона при привязке / в профиле нет телефона — `no_phone`) → **без
  автоматического объединения**, сообщение об ошибке.

Решение принимается без записи (`services.decide`) дважды: ботом — чтобы отказать
сразу или выдать код, и при вводе кода — уже под блокировкой, по свежему состоянию
(между шагами MAX могли отвязать, номер — сменить). Пользователь создаётся и MAX
привязывается только после верного кода (`services.execute`).

Почему так строго. В аккаунт с паролем телефон вписывается без проверки
(«Сменить телефон» принимает любой свободный номер). Раньше владелец номера,
нажав «Войти через MAX», попадал в такой аккаунт — тот, пароль от которого знает
кто-то другой, — а аккаунт получал отметку «телефон подтверждён» и забирал
гостевые заказы с этим номером. Теперь вписанный номер сам по себе ничего не
даёт. Владелец аккаунта с паролем подключает MAX из кабинета (профиль → «Вход
через MAX» → «Подключить MAX»): там сверяются и вход в аккаунт, и номер из MAX.
При привязке бот называет аккаунт («Вы подключаете этот MAX к аккаунту
i•••@mail.ru»), чтобы человек, которому ссылку переслали, заметил чужой аккаунт.

Номер считается подтверждённым **только** когда аккаунт создан штатной передачей
контакта MAX с проверяемой HMAC-подписью (§11.5) — не текстом и не вручную. В
админке поле «Телефон подтверждён» доступно только для чтения, а при смене
номера сбрасывается. Привязка из кабинета номер подтверждённым пока не делает —
до защиты от пересланной ссылки (DRF-2740).

#### Покупатель не может войти через MAX: «номер указан в аккаунте, но не подтверждён»

Его номер вписан в чужой аккаунт (ошибка при вводе или умысел). Сам покупатель
это не исправит. Что делает сотрудник:

1. Перезвонить **на этот номер** и убедиться, что обращается его владелец.
2. Админка → «Пользователи» → найти аккаунт по номеру → очистить поле «Телефон»
   и сохранить (отметка «подтверждён» снимется сама).
3. Попросить покупателя сразу нажать «Войти через MAX»: номер свободен, и
   занять его снова можно за секунды.

Всплеск таких отказов виден в логе: событие `max_auth_failed` с
`failure_reason=phone_unverified`.

### 9.5. Согласия (§12)

Перед передачей номера бот показывает текст согласия на использование номера для
регистрации, входа, оформления заказов и сервисных уведомлений. Согласие на
**рекламные** уведомления — отдельное и необязательное (не блокирует регистрацию).
Обновить: политику конфиденциальности, согласие на обработку ПДн, описание способов
входа.

### 9.6. Аналитика (§15)

События пишутся в `apps.analytics` (за фиче-флагом `analytics`, PII фильтруется):
`max_auth_started`, `max_auth_code_issued`, `max_auth_code_rejected`,
`max_auth_completed`, `max_auth_failed`, `max_auth_cancelled`, `max_account_linked`,
`max_account_unlinked` (+ параметры `operation_type`, `is_new_user`,
`failure_reason`). Код и телефон в события не попадают.

### 9.7. Проверка

Локально (unit/e2e): `docker compose run --rm web pytest apps/integration_max`.

На стенде:
1. Задать `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_BOT_USERNAME`, подписать webhook.
2. На странице `/account/login` нажать «Войти через MAX».
3. Мобильный — открывается бот по диплинку; десктоп — сканировать QR.
4. В боте нажать «Начать» (при первом входе — поделиться номером) → бот присылает
   код с кнопкой «Скопировать код» → ввести код на сайте → вход. Если номер уже
   указан в аккаунте с паролем — отказ с подсказкой ещё в боте (см. 9.4): войти
   паролем и подключить MAX в профиле.
5. Репетиция атаки двумя браузерами: попытку создать в одном, ссылку открыть с
   телефона — во втором (создавшем) браузере без кода входа нет, а чужой браузер и
   с кодом получает 404.
6. В профиле проверить «MAX подключён» и «Отключить MAX»; подтверждение личности
   перед удалением аккаунта — тоже через код.

Покупатель пишет «бот прислал код, которого я не просил» — значит, кто-то открыл
его ссылку или переслал ему свою: код ни в коем случае не сообщать, на сайте ничего
не вводить; попытка истечёт сама через 5 минут.
