# ADR-0015: Событие `user_deleted` и реестр условий сброса пароля

- Статус: принято
- Дата: 2026-09-24
- Связано: вход через VK ID / Яндекс ID (`apps/integration_oauth`), `docs/ARCHITECTURE.md` §2, §5

## Контекст

Вход через VK ID и Яндекс ID живёт в новом приложении слоя интеграций
`apps/integration_oauth` (модель `OAuthAccount`: пользователь ↔ аккаунт у
провайдера). Ему нужны две вещи от `accounts` (слой 0), который о слое интеграций
знать не должен:

1. **Удаление аккаунта.** `DeleteAccountView` не удаляет строку `User`, а
   обезличивает её (`is_active=False`, `phone=deleted-<pk>`) — каскад по FK не
   срабатывает, привязки остались бы висеть. Человек, удаливший аккаунт, не смог бы
   зарегистрироваться заново тем же VK ID, а в БД оставалась бы связь «аккаунт VK →
   обезличенный пользователь».
2. **Восстановление доступа.** Аккаунт, созданный через провайдера, заводится без
   пароля. `_reset_eligible` пускал к сбросу только пользователей с паролем (чтобы
   MAX-аккаунт с неподтверждённой почтой не получил пароль). Пользователю из VK ID
   «Забыли пароль» — единственный путь вернуть доступ, если провайдер недоступен, и
   ссылка на него стоит в письме «аккаунт создан».

Прямой импорт `integration_oauth` из `accounts` или обращение
`user.oauth_accounts.exists()` нарушают правило зависимостей: второе — то же чтение
чужой таблицы, только через related_name, и без установленного модуля падает.

## Решение

1. Новый доменный сигнал в `apps/core/events.py`:

   ```python
   user_deleted = Signal()
   # payload: user_id
   ```

   Издатель — `DeleteAccountView`, через `transaction.on_commit` внутри транзакции
   обезличивания. Подписчик `apps/integration_oauth/receivers.py` снимает все
   `OAuthAccount` пользователя.

2. Реестр условий сброса в `apps/accounts/services.py`:
   `register_reset_eligibility(check)` и `is_reset_eligible(user)`. Базовое правило
   прежнее (активный, не сотрудник, с паролем); модуль выше регистрирует
   дополнительное условие в `AppConfig.ready()`. `integration_oauth` регистрирует
   «есть привязка VK ID / Яндекс ID». MAX-аккаунты без пароля и без привязки
   по-прежнему сброс не получают.

## Последствия

**Плюсы:**
- `accounts` не знает об интеграциях входа; зависимость развёрнута вверх.
- Будущие способы входа (другие провайдеры) подключаются тем же сигналом и реестром.

**Минусы / компромиссы:**
- Реестр — глобальное состояние процесса; порядок `INSTALLED_APPS` на него не
  влияет (проверки вызываются лениво), но выключенное приложение не регистрирует
  проверку — и это желаемое поведение.

**Риски:**
- Сигнал отправляется после коммита: если подписчик упадёт, аккаунт уже обезличен,
  а привязка осталась. Колбэк входа это переживает: привязка к обезличенному
  пользователю считается свободной (`User.is_anonymized`) и снимается при следующем
  входе.
