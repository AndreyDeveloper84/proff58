# ADR-0013: Контракт B2B/НДС и доставки (Wave 1)

- Статус: принято
- Дата: 2026-07-22
- Связано: #444, #429, #430, #558, `docs/reviews/full-codebase-review-2026-07-01.md`
  (M-05, M-06), `docs/design/tz-master.md` §4, `docs/order-lifecycle.md` §5

## Контекст

Ревью кодовой базы 2026-07-01 зафиксировало два расхождения между продуктовым
контрактом и реализацией.

**M-06 (B2B).** Код выдавал верифицированному B2B отдельную оптовую цену, хотя ТЗ
фиксирует единый ценник. Гостевой B2B-заказ принудительно превращался в B2C, поэтому
гостевой запрос счёта был невозможен. Режима «с НДС / без НДС» в модели заказа и счёта
не существовало вовсе, а само ТЗ фиксировало только «включённый НДС 20%» — то есть
бизнес-решение было отражено неполно и его нельзя было проверить тестом.

**M-05 (доставка).** Приложение `apps.delivery` жило отдельно от checkout: API считал
подсказку по `cart_total`, который присылал **клиент**, а checkout принимал свободные
строки `delivery_method`/`delivery_address`, не выбирал серверную зону и не включал
доставку в `Order.total`. Начальные пороги бесплатной доставки (5 000 / 10 000 ₽)
разошлись с фактическим решением владельца, СДЭК-путь отсутствовал.

Обе проблемы — не баги реализации, а **отсутствующее решение**: пока контракт не
зафиксирован, любая правка кода лишь меняет одну недокументированную трактовку на
другую. Реализация выполнена в #430 (B2B/НДС), #429 (доставка) и #558 (B2B без
доставки); этот ADR фиксирует принятые правила как контракт, на который ссылается код.

## Решение

### A. Цена и НДС

1. **Единый ценник.** Числовая цена одинакова для B2C и B2B — отдельной оптовой цены в
   customer-facing слое нет. Записи `PriceRecord` с типом `wholesale`, приходящие из 1С,
   в расчёте цены не участвуют и в сортировку каталога не попадают
   (`apps/pricing/services.py`, `apps/catalog/api/views.py`, сортировка — по
   `Product.price`).

2. **Цена всегда включает НДС.** Ставка — `settings.VAT_RATE_PERCENT` (дефолт `22`,
   `config/settings/base.py`). Выделение налога из суммы с НДС — единственная точка
   расчёта `apps.pricing.vat.vat_breakdown`:

   ```
   НДС      = сумма_с_НДС × rate / (100 + rate)      # Decimal, ROUND_HALF_UP до копеек
   без_НДС  = сумма_с_НДС − НДС                      # остаток, не самостоятельное округление
   ```

   Инвариант `без_НДС + НДС == сумма_с_НДС` держится по построению: «без НДС» —
   остаток, а не второе независимое округление.

3. **Снимок НДС в заказе.** `Order.vat_rate`, `Order.vat_amount`,
   `Order.amount_without_vat` фиксируются на момент оформления. Заполняются **только для
   B2B**; у B2C поля нулевые — розничный чек налог не выделяет. Изменение
   `VAT_RATE_PERCENT` не переписывает историю: старые заказы и счета остаются со своей
   ставкой.

4. **Гостевой B2B-заказ разрешён.** Раз опта нет, «объявить себя юрлицом» не даёт
   ценового преимущества, поэтому прежний запрет (#282) снят: гость может запросить счёт
   без регистрации. Реквизиты валидирует сервер
   (`apps.orders.invoice.validate_b2b_requisites`: ИНН 10/12, КПП обязателен при ИНН из
   10 цифр, юр. адрес, e-mail), способ оплаты у B2B принудительно `invoice` — карта и
   наличные отклоняются.

### B. Доставка

5. **Стоимость считает только сервер.** Единственный источник правды —
   `apps.delivery.services.quote_for_order(zone_slug, goods_total, items)`, вызываемый из
   `apps.orders.services.place_order` внутри транзакции заказа, по **серверной** корзине.
   Клиент присылает лишь слаг зоны. Витринная `apps.delivery.services.calculate` —
   подсказка для UI и в сумму заказа не входит; фронт вправе показывать её только как
   предварительную оценку.

6. **Зоны и тарифы** (справочник в БД, дефолты — миграция `delivery.0004_adr444_zones`):

   | Зона | Тариф |
   |---|---|
   | Самовывоз | 0 ₽ всегда |
   | Пенза (курьер) | 500 ₽; бесплатно от **7 000 ₽** |
   | Пензенская область (СДЭК) | `is_external` — всегда по API перевозчика |

   Порог бесплатной доставки считается **по стоимости товаров после скидок, без
   доставки**. К внешней зоне порог **не применяется**: перевозчику платим по факту.

7. **Три статуса расчёта** (`Order.DeliveryCalcStatus`):
   - `not_required` — доставка не выбрана либо не требуется (самовывоз, B2B);
   - `calculated` — стоимость посчитана сервером, входит в `Order.total`;
   - `manual_required` — авторасчёт невозможен (у товаров не заполнены весогабариты либо
     перевозчик не вернул тариф). Тогда `delivery_cost = null`, `Order.total` —
     **предварительный** (только товары), финальный счёт не выпускается, пока менеджер не
     введёт стоимость.

8. **Снимки в заказе.** Тариф — `Order.delivery_snapshot`, слот доставки — отдельный
   `Order.delivery_slot_snapshot`. Правка или деактивация зоны/слота в справочнике не
   меняет историю уже оформленных заказов.

9. **Доставки для юрлиц в Wave 1 нет** (#558). У B2B-заказа независимо от присланной
   зоны: `delivery_calc_status = not_required`, `delivery_cost = 0`,
   `delivery_snapshot = {"reason": "b2b_delivery_not_supported"}`; курьерская доставка и
   слот отклоняются валидацией. Следствие: база НДС у B2B всегда равна товарной сумме, а
   `manual_required` для B2B недостижим — счёт всегда только на товары.

## Последствия

**Плюсы:**
- Стоимость доставки нельзя занизить с клиента: сумма считается по серверной корзине
  внутри транзакции заказа, а не по присланному `cart_total`.
- Единый ценник убирает целый класс расхождений «цена в каталоге ≠ цена в корзине» для
  верифицированного B2B и делает сортировку по цене одинаковой для всех.
- Снимки (НДС, тариф, слот) делают заказ самодостаточным документом: правка справочников
  и смена ставки налога историю не трогают.
- Контракт проверяем тестами: `apps/pricing/tests.py` (единый ценник, `vat_breakdown`),
  `apps/orders/tests/test_delivery_checkout.py`, `test_b2b_no_delivery.py`,
  `test_guest_b2b_validation.py`, `apps/delivery/tests.py`.

**Минусы / компромиссы:**
- Ставка НДС живёт в настройке приложения, а не в справочнике БД: смена ставки — деплой,
  а не действие администратора. Осознанно: ставка меняется раз в несколько лет, а снимок
  в заказе всё равно защищает историю.
- Пороги и тарифы зон меняются в админке, но «бесплатно от 7 000 ₽» продублировано в
  докстрингах и дизайн-ТЗ — при изменении бизнес-условия придётся править и текст.
- Гостевой B2B-заказ означает, что счёт можно запросить без верификации юрлица: защита —
  только валидация формата реквизитов и ручная обработка менеджером.

**Риски:**
- `manual_required` — не редкий край: весогабариты у товаров каталога массово не
  заполнены, поэтому СДЭК-заказы будут регулярно уходить на ручной расчёт. Нужен
  процесс у менеджера, иначе покупатель зависает с предварительным итогом.
- Отсутствие доставки у B2B — сознательное сужение Wave 1. Снятие ограничения меняет
  базу НДС (доставка попадёт в облагаемую сумму) и потребует нового ADR, а не правки
  этого.
- Фронт не имеет серверного preview-итога и вынужден сам складывать «товары +
  предварительная доставка» для показа. Пока это подписано как предварительный итог; при
  расхождении с сервером страдает доверие — кандидат на отдельный endpoint котировки.
