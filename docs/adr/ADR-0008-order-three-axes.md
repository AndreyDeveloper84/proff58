# ADR-0008: Модель заказа на трёх независимых осях статусов

- Статус: принято
- Дата: 2026-04-10
- Связано: `docs/order-lifecycle.md`, #50, `apps/orders/transitions.py`

## Контекст

Заказ в интернет-магазине с доставкой и интеграцией с 1С имеет три независимых
процесса с разными ответственными:
- **Обработка** (кто везёт, когда, откуда) — управляется 1С/менеджером;
- **Оплата** (получены ли деньги) — управляется сайтом (ЮKassa);
- **Синхронизация с 1С** (знает ли 1С об этом заказе) — управляется сайтом.

Традиционное «одно поле `status`» не позволяет независимо продвигать каждый процесс:
заказ может быть «доставлен», но «не оплачен», или «оплачен», но ещё не «передан в 1С».
Смешение создаёт комбинаторный взрыв состояний и усложняет бизнес-правила.

## Решение

1. **Три отдельных поля**:
   - `fulfillment_status` — `new → confirmed → assembling → shipping → delivered | cancelled`
   - `payment_status` — `pending | paid | refunded | failed`
   - `sync_1c_status` — `pending | exported | error`
2. **Матрица переходов** `fulfillment_status` хранится в `transitions.py`; недопустимые
   переходы отбраковываются без исключений (return False).
3. **Производный `display_status`** — человекочитаемый статус для UI/ЛК, вычисляется
   из комбинации трёх осей без хранения в БД.
4. **1С не трогает `payment_status`** — это инвариант, закреплённый в `use_cases`.
5. **`sync_1c_status` остаётся `pending`** после `GET /api/1c/orders/new` (at-least-once):
   переходит в `exported` только после явного подтверждения через `POST /api/1c/orders/confirm`.

## Последствия

**Плюсы:**
- Каждый процесс развивается независимо, без глобальных блокировок.
- Прозрачная аудитируемость: можно найти заказы «оплачены, но не выгружены в 1С».
- Матрица переходов легко тестируется изолированно.

**Минусы / компромиссы:**
- Три поля сложнее одного поля `status` для новых разработчиков.
- `display_status` приходится поддерживать синхронно при добавлении новых состояний.

**Риски:**
- При ошибке в логике `sync_1c_status` заказ может «застрять» в `pending` навсегда
  (защита: ручная команда или admin-action для перевода в `exported`).
