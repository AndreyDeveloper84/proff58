# ADR-0006: Единый контракт ценообразования (`price_for`)

- Статус: принято
- Дата: 2026-06-20
- Связано: #60, `docs/ARCHITECTURE.md` §4.1

## Контекст

Цена была размазана: денормализованный `Product.price`, история в `PriceRecord`
(sync_1c), прямое чтение в сериализаторах, в будущем — корзина и заказы. Разные
места считали бы цену по-своему, B2B-опт не выбирался, скидка трактовалась
неоднозначно. Для e-commerce это один из самых опасных участков: расхождение цены
в каталоге/корзине/заказе/1С недопустимо.

## Решение

1. **Единственный способ получить цену — `apps.pricing.services.price_for(product, user=None, qty=1)`.**
   Прямое чтение `Product.price` вне pricing-слоя запрещено.
2. **Роли данных:**
   - `Product.price` — **кэш розницы** (денормализация из 1С для быстрой витрины).
   - `PriceRecord` (sync_1c) — **история и типы цен** (retail/wholesale/…); источник опта.
   - **Заказ хранит снимок цены** (значение на момент оформления), а не ссылку — цена
     в заказе не «плывёт» при последующих изменениях.
3. **Результат — стабильный контракт** `PriceResult{base, final, currency, discount, price_type}`.
   `price_type ∈ {retail, wholesale, contract}` (contract — задел). Розница — быстрый
   путь без запроса; опт (B2B) — из `PriceRecord` с фолбэком на розницу.
4. **Изменение цены публикует событие** `price_changed(product_id, old_price, new_price,
   currency, source)` (издатель — 1С use-case), чтобы кэш/индекс/уведомления/аналитика
   реагировали без правки 1С.

## Последствия

- Каталог/корзина/заказ зависят от одного контракта; смена логики цены — в одном месте.
- B2B видит опт, не ломая B2C.
- Не входит (отдельные задачи): модели `PriceList/Promotion/Coupon`, ступенчатые цены
  по qty, перенос `PriceRecord` в pricing, кэш и bulk-резолвер опта для B2B-листингов.
