# ADR-0011: Отдельный tool_type `dinamometricheskie-klyuchi` для динамометрических ключей

- Статус: предложено
- Дата: 2026-07-20
- Связано: ADR-0001 (tool_type — атрибут, не категория),
  ADR-0010 (catalog processing foundation),
  `docs/catalog/phase5-batch50-closure-report.md` (taxonomy gaps),
  `docs/plans/2026-07-20-PHASE6_PROPOSAL_SHADOW_PLAN.md` (решение 5:
  первый taxonomy ADR — динамометрические ключи)

Документ — docs-only: **никаких изменений taxonomy, `load_tool_types`,
staging и миграций данных этот ADR не выполняет**. Создание option,
миграция PAV и любые run — только после принятия ADR отдельным решением.

## Контекст

В Phase 5 два динамометрических ключа (12957, 12959) получили широкий тип
`klyuchi-gaechnye` («Гаечные ключи») — в разрешённой таксономии из 327
options точного типа не было. В batch-50 товары того же семейства (12956,
13002) дали **abstention с `taxonomy_gap`**: research отказался повторять
широкую классификацию, модератор пометил расхождение с прецедентом Phase 5
как family divergence. Это единственный системный gap batch-50
(2 abstention + 3 товара в in-stock пуле + 65 SKU всего), и он блокирует
как закрытие needs_review-хвоста, так и будущие rules/research прогоны.

Граничный вопрос, который ADR обязан решить явно (решение 5 Phase 6 plan):
отношение динамометрических **ключей** к `klyuchi-gaechnye` и к
динамометрическим **отвёрткам**.

## Варианты

### Вариант A — отдельный `dinamometricheskie-klyuchi` (рекомендуется)

Новый option «Динамометрические ключи» только для ключей (щелчковых,
шкальных, рожковых, предельных). Отвёртки остаются `otvertki`, адаптер —
`adaptery`, ремкомплекты — вне этого option (запчасти), патрон — оснастка.

- Плюсы: точная гранулярность соответствует таксономии (сравн. узкие типы
  уровня `krep-shplinty`, `zap-shpindeli-valy`); закрывает системный gap и
  family divergence; миграционный impact минимален (ровно 2 PAV);
  однозначные routing-правила (`ключ динамометрический` в названии).
- Минусы: +1 option в и так большой таксономии; семейство отвёрток (8 SKU)
  остаётся без точного типа до роста семейства.

### Вариант B — umbrella `dinamometricheskiy-instrument`

Один тип для ключей, отвёрток и torque-адаптеров.

- Плюсы: один option вместо двух-трёх потенциальных.
- Минусы: размывает границу с `otvertki` (уже применён к 13936) и с
  измерительным инструментом (`adaptery` у 10537 — электронный прибор);
  требует миграции большего числа PAV и пересмотра корректного `otvertki`;
  routing-правила менее стабильны («инструмент» — слабый дискриминатор);
  противоречит принятой гранулярности таксономии.

### Вариант C — сохранить широкие типы

Ключи → `klyuchi-gaechnye`, отвёртки → `otvertki`, без новых options.

- Плюсы: нулевая стоимость изменений.
- Минусы: закрепляет семантически неточную классификацию (динамометрический
  ключ — прецизионный измерительно-затяжной инструмент, а не простой
  гаечный); воспроизводит family divergence при каждом research
  (batch-50 уже показал abstention вместо повторения прецедента);
  needs_review-хвост (12956, 13002) остаётся без пути разрешения.

## Решение (предлагаемое)

Принять **вариант A**: создать option `dinamometricheskie-klyuchi`
(«Динамометрические ключи») атрибута `tool_type`.

### Граница типов (явно)

- **`dinamometricheskie-klyuchi`**: ручные ключи с контролем момента
  затяжки — щелчковые, шкальные, стрелочные, рожковые, предельные,
  любых приводных квадратов (1/4"–1"). Включает 12956, 12957, 12959,
  13002, 13004 и остальные 60 SKU подсемейства.
- **`otvertki`**: динамометрические отвёртки остаются здесь (13936 и
  семейство 13931–13935, 46579, 46580). Отдельный
  `dinamometricheskie-otvertki` не создаётся — семейство мало (8 SKU,
  1 in-stock); вопрос пересматривается при росте > 20 active SKU.
- **`adaptery`**: электронные динамометрические адаптеры/измерители
  (10537) — измерительный прибор, не затяжной инструмент.
- **`klyuchi-gaechnye`**: только гаечные ключи без контроля момента.
  Динамометрические ключи туда больше **не маршрутизируются**
  (прецедент Phase 5 признаётся уступкой отсутствию option, а не
  правильной классификацией).
- **Вне option**: ремкомплекты (7170, 7171 — запчасти), патроны
  (27025 — оснастка), наборы с динамометрическим ключом в составе
  (маршрутизируются как наборы, не как ключи).

### Impact

- **PAV**: всего 4 существующих значения в зоне ADR; меняются ровно 2
  (12957, 12959: `klyuchi-gaechnye` → `dinamometricheskie-klyuchi`).
  `otvertki` у 13936 и `adaptery` у 10537 не затрагиваются.
- **Активные товары**: 19 active ключей получают корректный тип (2
  миграцией, 17 — при последующей обработке новым run).
- **Складские (in-stock)**: 6 ключей, из них 5 active (12956, 12957,
  12959, 13002, 13004) + 12987 (inactive). In-stock пул Phase 6 (190)
  уменьшится на 3 товара с этим gap после их обработки.
- **Закрытие хвоста batch-50**: needs_review 12956 и 13002 получают путь
  разрешения — **новым run** после создания option (в закрытом run они
  остаются audit, см. closure report).

### Миграция ранее применённых значений (описание, НЕ выполнение)

После создания option отдельным changeset:

1. Ремедиация 12957/12959 — новый `CatalogProcessingRun` (kind=manual
   или rules) из двух items; для каждого change `before_value` =
   текущий `klyuchi-gaechnye` (web, 85), `proposed_value` =
   `dinamometricheskie-klyuchi`, evidence ссылается на Phase 5/batch-50
   решения и этот ADR.
2. Поскольку collision policy Phase 6 запрещает перезапись существующего
   `tool_type`, remediation-change создаётся явно как **миграционный**
   (отдельный вид change с baseline = текущее значение); модерация и
   apply — только через `review_catalog_change` / `apply_catalog_change`,
   reviewer id=1, строго по одному, с pre/post-проверками по протоколу
   batch-50.
3. После apply старое значение фиксируется в `before_value` change;
   прямых ORM-update и массовых перезаписей не выполняется.
4. Порядок: option changeset → миграция 2 PAV → новый run для 17 active
   и needs_review-хвоста (12956, 13002) → затем rules/research по
   остальным SKU семейства.

### Negative cases (routing)

Routing-правила (будущие, для shadow rules engine Phase 6.0) обязаны
исключать:

- «отвёртка динамометрическая» → `otvertki`, не сюда;
- «адаптер динамометрический» → `adaptery`;
- «ремкомплект для динамометрического ключа» → запчасти, не сюда;
- «патрон динамометрический» → оснастка;
- «динамометр» (измеритель усилия) → измерительный инструмент, не сюда
  (в каталоге сейчас 0 SKU, но слово — часть стеммы «динамометр*»);
- «набор … с динамометрическим ключом» → наборы.

### Будущие правила маршрутизации (для ruleset v1, shadow)

Конъюнктивное правило-кандидат: `name ~ /ключ(и)?\s+динамометрическ|динамометрическ(ий|ого)\s+ключ/i`
AND `source_group = "Ключи, головки, воротки, удлинители"` AND NOT
negative-patterns выше → `dinamometricheskie-klyuchi`. Обязательные
negative fixtures: 7170, 7171, 10537, 27025, 13931–13936. Правило
проходит стандартный gate Phase 6 (≥ 100 независимо проверенных
predictions, precision ≥ 99%).

## Последствия

**Плюсы:**

- закрыт единственный системный taxonomy gap batch-50; needs_review
  12956/13002 получают путь разрешения новым run;
- семантически точная классификация 65 SKU; устранён источник
  family divergence между Phase 5 и будущими research;
- чистая основа для conjunctive routing-правила с negative fixtures.

**Минусы / компромиссы:**

- +1 option к 327; динамометрические отвёртки (8 SKU) остаются в широком
  `otvertki` до пересмотра;
- миграция 12957/12959 требует отдельного remediation-run с модерацией
  (стоимость ~одного batch-протокола).

**Риски:**

- дробление таксономии, если по каждому подтипу создавать option —
  смягчается порогом пересмотра (отвёртки: > 20 active SKU) и отдельным
  ADR на каждый новый тип;
- повторная миграция при возможном будущем umbrella-решении — признаётся
  низкой: вариант B отклонён по гранулярности.
