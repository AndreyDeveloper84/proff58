# Rollback — политика отката

Два уровня защиты: **pg_dump** (грубый, вся БД) + **rollback-map** (хирургический,
точечный откат конкретной операции).

## Rollback-map — обязателен для КАЖДОГО write
Фиксируется ДО записи, включается в post-audit, хранится в roadmap-доке.

| Операция | Что сохранить | Как откатить |
|---|---|---|
| recategorize | `{product_id: old_category_id}` | `update(category_id=old)` по карте |
| enrich | список созданных PAV + прежний `attrs_cache.tool_type` (обычно None) | удалить PAV + вернуть cache |
| combined (cat+тип) | **двойной:** old_category **и** created-PAV **и** cache→prev | откатить оба в одной транзакции |
| new option | `option_id` | удалить option (если usage=0) |
| понижение версии словаря (`N → N-1`) | план понижения + пара снимков по затронутым товарам | перенос через контур отката, затем `drop` опций (fail-closed по usage) |

## Принцип
- Все id в карте — явные (не «по правилу»), чтобы откат был детерминированным.
- pg_dump — точка восстановления, если что-то пошло не так вне карты.
- Volume staging непрерывен → дампы = реальные точки отката ([pgdump-policy](pgdump-policy.md)).

## Идемпотентность как страховка
После write повторный dry-run/preview должен дать **0** (нечего повторять). Это же —
проверка, что откат вернёт ровно исходное состояние.

## `tool_type`: rollback-map исполняется командой (Wave 7.1 / H5)

Для `tool_type` карта отката перестала быть текстом в roadmap-доке — она стала
**артефактом с исполнителем**. Полная процедура и fail-closed матрица:
[tool-type-reverse-migration.md](../tool-type-reverse-migration.md).

```bash
manage.py catalog_tool_type_snapshot --product-ids 101,102 --out before.json   # ДО записи
# ... write ...
manage.py catalog_tool_type_snapshot --product-ids 101,102 --out after.json    # ПОСЛЕ записи
manage.py catalog_tool_type_rollback --from after.json --to before.json          # dry-run
manage.py catalog_tool_type_rollback --from after.json --to before.json --apply  # write
```

Что это добавляет к общей политике выше:

- **снимков два, а не один.** По одному снимку «до» нельзя отличить изменение,
  которое мы откатываем, от чужого изменения поверх. Пара `from`/`to` даёт третье
  состояние — `conflict`, и оно не перезаписывается молча;
- **идемпотентность проверяется, а не подразумевается:** повторный запуск даёт
  `write=0, noop=N`;
- **`attrs_cache` восстанавливается вместе с PAV** — как и требует строка `enrich`
  в таблице выше, но по явной записи снимка, а не «пересоберётся сигналом»;
- **post-audit встроен:** после `--apply` снимок пересобирается и сверяется с
  целевым; расхождение — ненулевой exit, а не строка в логе;
- **частичного применения не бывает:** вся запись — одна транзакция, а план с любым
  конфликтом отклоняется целиком.

Снимок «до» обязателен **до** записи: восстановить его задним числом нельзя.
