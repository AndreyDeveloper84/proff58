# Карантин характеристик (трек P2)

Файловый реестр товаров, для которых движок характеристик (`enrich_attributes`)
**не должен извлекать значения** — целиком либо по конкретным осям.

## 1. Зачем

До P2 единственным способом исключить товар было вписать фразу из его названия в
`skip_if` правила. Но `skip_if` живёт в правилах и потому действует на **класс**
названий, а исключение обычно нужно **одному** товару:

* `sharoshki`: стоп-слово `бакелит` стояло во всех пяти правилах блока ради
  одного товара 18455. Любая новая бакелитовая шарошка была бы погашена молча;
* `korshchetki`: во всех пяти правилах стояла фраза `пластмассовой ручкой
  5-рядная` — кусок имени конкретного товара 18578 в общих правилах.

Обе фразы сняты (ХАР-13), а исключения перенесены в реестр карантина. Классовые
гейты (например `набор`/`предм` у `sharoshki.diameter`) остались в правилах — это
их законное место.

## 2. Границы контура

| Свойство | Решение |
|---|---|
| Хранилище | **файл** `data/attribute_quarantine.json`, не модель. Миграций БД нет |
| Путь по умолчанию | `<--path \| data>/attribute_quarantine.json`; переопределяется флагом `--quarantine` |
| Файла нет | пустой реестр, **не ошибка** |
| Потребитель | только `enrich_attributes`. `scraped_import` в контур не входит |
| Удаление PAV | карантин **никогда** не удаляет уже записанные значения |
| Уборка | отдельная команда `catalog_attribute_cleanup_quarantine` |

## 3. Формат записи

```jsonc
{
  "version": 1,
  "_note": "комментарий к файлу (необязателен)",
  "items": [
    {
      "product_id": 18455,          // обязательно, int > 0
      "reason": "owner_excluded",   // обязательно, закрытый enum (см. ниже)
      "added_at": "2026-08-14",     // обязательно, ISO-дата YYYY-MM-DD
      "added_by": "owner",          // обязательно, непустая строка
      "status": "active",           // обязательно: active | lifted

      "attributes": null,           // null/отсутствует = весь товар;
                                    // непустой список slug'ов = точечный карантин
      "code_1c": "...",
      "name_snapshot": "Шарошка бакелитовая 100мм М14 Р40",
      "tool_type": "sharoshki",
      "note": "человеческое обоснование",
      "ticket": "ХАР-13",
      "expires_at": "2026-12-31",   // после этой даты запись не действует
      "lifted_at": "2026-09-01",    // обязательны при status=lifted
      "lifted_by": "owner",
      "lift_note": "исследование закрыто"
    }
  ]
}
```

**`reason` — закрытый список:** `owner_excluded`, `name_ambiguous`, `data_defect`,
`wrong_tool_type`, `pending_research`, `rule_defect`.
`rule_defect` **требует непустой `ticket`**: дефект правил обязан быть заведён
задачей, иначе карантин превращается в вечную заглушку без владельца.

**Скоуп двойной:**

* `product` — `attributes: null` (или ключа нет): движок не извлекает ничего;
* `product + attribute` — `attributes: ["brush_shape"]`: не пишется только
  перечисленное, остальные оси товара обрабатываются как обычно.

## 4. Валидация — fail-closed до любой записи

Любое из перечисленного отвергает **весь прогон** (`CommandError`), а не одну
запись:

* `version` ≠ 1; `items` не список; неизвестный ключ верхнего уровня;
* **неизвестный ключ в записи** (опечатка `atributes` иначе молча превратила бы
  точечный карантин в карантин всего товара);
* отсутствие обязательного поля; `product_id` не положительное целое;
* `reason`/`status` вне enum; `rule_defect` без `ticket`;
* `status: "lifted"` без `lifted_at`/`lifted_by`;
* `attributes` — пустой список, не список, дубли, либо slug, которого нет среди
  управляемых правилами (`attribute_rules.json`);
* битая дата в `added_at`/`expires_at`/`lifted_at`;
* дубль `product_id` среди записей со `status: "active"`;
* **`product_id`, которого нет в `Product`** — один запрос на весь реестр до
  цикла. Escape hatch не предусмотрен: лучше остановить процесс, чем молча
  пропустить проблему.

Предупреждения (не отказ): истёкший `expires_at`; `tool_type` записи ≠
фактического; `name_snapshot` ≠ текущего названия.

## 5. Где стоит гейт и почему именно там

Короткое замыкание — **в команде** `enrich_attributes`, между вычислением
`tt_slug` и `rules.extract(...)`.

Класть его в `attribute_extract` рядом со `skip_if` **нельзя**: prune-цикл
команды идёт ДО цикла записи и удаляет PAV по условию «slug не входит в
извлечённое», если `pav.source ∈ PRUNABLE_SOURCES`. Пустой `values` ⇒ пустой
`current` ⇒ **все** engine-PAV товара уехали бы в удаление, то есть добавление
строки в реестр молча стёрло бы данные. `continue` на выбранной позиции
пропускает разом prune, счётчик `no_attributes` и цикл записи.

Частичный карантин `continue` не делает, но получает два гейта: в prune-цикле
(карантинный slug не удаляется) и в цикле записи (не создаётся и не
обновляется).

Регресс-пара тестов: `test_quarantine_never_deletes_existing_pav` (значение
сохранилось) и `test_prune_deletes_the_same_pav_without_quarantine` (без записи
в реестре тот же PAV удаляется) — второй нужен, чтобы первый не зеленел
вхолостую.

## 6. Отчётность

Консоль `enrich_attributes` (stderr): путь реестра, версия, число active /
lifted / истёкших, сколько записей попало в выборку и сколько из них частичных.
В итоговой строке — `в карантине N (частично M)`. `QUARANTINED` — **отдельная
ось**: это не `SKIPPED` (та про конкуренцию источников), и карантинный товар
**не попадает** в счётчик «без характеристик».

JSON-отчёт `--dry-run`: существующие ключи не менялись, добавлены секция
`quarantine` (метаданные реестра), `totals.quarantined` /
`totals.quarantined_partial` и массив `quarantined` с записями
(`product_id`, `tool_type`, `scope`, `attributes`, `reason`, `ticket`,
`added_at`, `note`, `managed_attributes`, `preserved_pav`). Данные берутся из уже
загруженных структур — дополнительных запросов к БД отчёт не делает.

`ImportRun.stats`: `quarantined`, `quarantined_partial` и блок `quarantine`
(путь, версия, число active, `product_ids` сработавших записей).

## 7. Плейбук: как завести запись

1. **Замер (read-only).** Убедиться, что фраза действительно уникальна внутри
   блока `tool_type`: правила применяются только к товарам своего типа, поэтому
   считать уникальность по всему каталогу нельзя. Если фразу разделяют два и
   более товара блока — это класс, и его место в `skip_if`, а не в карантине.
2. **Запись в реестр.** Добавить объект в `items` с обязательными полями плюс
   `name_snapshot`, `tool_type`, `ticket`, `note`. Ничего из файла не удалять.
3. **Правила.** Если карантин заменяет фразу в `skip_if`, снять фразу из правил
   и обновить `_note` блока. Классовые гейты не трогать.
   `data/attribute_rules.json` собран **не** через `json.dumps` (короткие
   массивы — в одну строку): править **только хирургически по тексту**, иначе
   пересбор даст диф в тысячу строк. Идентичность проверять разбором JSON.
4. **dry-run.** `enrich_attributes --dry-run --json-report <файл>`; сверить
   `totals.quarantined` и `quarantined[*].preserved_pav`.
5. **Тест.** Corrective-правка обязана иметь пару тестов: класс снова
   извлекается (фраза действительно снята) и конкретный товар по-прежнему без
   значений (карантин работает), плюс его существующие PAV целы.
6. **Apply.** Штатный гейт-цикл каталога (`docs/catalog/operations/README.md`):
   pg_dump → write → post-audit.

## 8. Плейбук: как снять карантин

Запись из файла **не удаляется** — иначе история исчезает и через месяц никто не
объяснит, почему товар был исключён.

1. У записи проставить `status: "lifted"`, `lifted_at`, `lifted_by`, при нужде
   `lift_note`. Без `lifted_at`/`lifted_by` реестр не загрузится.
2. Прогнать `enrich_attributes --dry-run` — товар снова появляется в обычных
   решениях (`create`/`update`).
3. Альтернатива для временного карантина — заранее проставленный `expires_at`:
   после этой даты запись перестаёт действовать сама и попадает в WARNING.

## 9. Уборка ранее записанного

Карантин запрещает писать новое, но не убирает старое. Для уборки —
`catalog_attribute_cleanup_quarantine`:

```bash
# план (ничего не удаляется), снимок = план уборки
python manage.py catalog_attribute_cleanup_quarantine --snapshot /tmp/q-plan.json

# запись: снимок обязателен, пишется ДО удаления
python manage.py catalog_attribute_cleanup_quarantine \
    --snapshot /tmp/q-cleanup.json --apply
```

* **dry-run по умолчанию**, запись — только с `--apply`;
* `--apply` без `--snapshot` отвергается;
* удаляются **только** значения движка (`source ∈ PRUNABLE_SOURCES` —
  regex/keyword/inferred). Ручные, 1С- и llm-значения не трогаются: карантин
  заведён против движка, а не против оператора;
* удаление и чистка `attrs_cache` — одной транзакцией;
* **post-audit** после записи перечитывает те же пары; остаток — ошибка;
* ключ восстановления — `product_id + attribute` (в снимке есть и `pav_id`, но
  после удаления id не возвращается);
* действуют только записи со `status: "active"` и неистёкшим `expires_at`.

## 10. Тесты

* `apps/catalog/test_attribute_quarantine.py` — реестр, короткое замыкание,
  частичный скоуп, валидация, отчёты, команда уборки, corrective-доказательство
  по снятым фразам; работает через явный `--quarantine` на своей фикстуре.
* `apps/catalog/conftest.py` — autouse-фикстура: остальные тесты каталога видят
  **пустой** реестр. Полтора десятка модулей зовут `enrich_attributes` без
  `--path`, то есть на боевом каталоге данных, а боевые `product_id` в тестовой
  БД отсутствуют — без подмены они падали бы на честном fail-closed.
* Боевой файл отдельно валидируется на схему/enum/уникальность без обращения
  к БД (`test_production_registry_is_valid`).
