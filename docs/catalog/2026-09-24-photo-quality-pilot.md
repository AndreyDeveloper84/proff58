# Пилот доработки контролёра качества фото (2026-09-24)

Локальное сравнение на пяти файлах аудита + read-only проверка текущего состояния
стенда. Реализация — доработка ADR-0014 (см. раздел «Доработка 2026-09-24» в самом
ADR). Живые данные и media на стенде этим пилотом не менялись.

## 1. Состояние стенда на момент задания (проверено заново, не по памяти)

Проверено `ssh proff58-vps` read-only 24.09.2026 (без записи в БД/файлы):

- в `.env` staging и prod нет строки `FEATURE_PRODUCT_IMAGE_AUTOPROCESS` → флаг
  выключен (значение по умолчанию `False`);
- `select processing_status, count(*) from catalog_productimage group by 1` на
  staging: **все 1131 записи — `none`**;
- контейнера `celery-rembg` среди запущенных нет.

Это подтверждает и уточняет память сессии (откат 23.09.2026): причина, по которой
живые карточки показывают исходники — автообработка полностью выключена и записи
сброшены, а не дефект кода выбора файла (`ProductImage.storefront_image`,
`_image_url`) — сам выбор уже проверен модульными тестами и не менялся в части
логики «взять `display`, иначе `image`».

## 2. Пять файлов аудита — предметный прогон

Команда (новая, часть доработки; входит в поставку):

```
python manage.py process_product_images \

  --artifacts-dir out/ --out report.json
```

| Файл | Класс фона | Решение | Причина | Соответствие ожиданию задания |
|---|---|---|---|---|

| `hanskonner-poster.webp` | white | `needs_review` | `suspect_backdrop` (0,1475 при пороге 0,10) | Рекламный кадр не принят автоматически; для полной защиты нужно ещё выставить назначение `promo` (эвристика — подстраховка, не замена ручной разметки) |
| `vihr.webp` | white | `needs_review` | `suspect_backdrop` (0,1949) | Совпадает с критерием приёмки №3: грязная подложка не выдана за успешную очистку, **без спецусловия по ID** |

Пороги эвристики `pale_content_share` подобраны РОВНО на этих пяти файлах (см.
докстринг `apps/catalog/image_quality.py`): 0,04–0,05 у чистых кадров
(Hanskonner, ЗУБР) против 0,15–0,19 у грязного фона и рекламного плаката. Порог
0,10 разделяет оба случая с запасом на этой выборке. Это НЕ калибровка на
представительном срезе каталога — см. ограничения ниже.

## 3. HUTER: проверка исходника у известного источника

Задание (§5.3) просит сначала проверить, есть ли у известного источника чистый
кадр, прежде чем полагаться на rembg. `ProductImage.source=huter` — источник
`huter.su` зарегистрирован в `ImageSource`, но автоматической проверки «найти
более чистый кадр у источника» в этой версии нет (задание прямо исключает
массовый поиск новых изображений из объёма работы, §5.3). Вывод по HUTER:
**не проверено** — нужен ручной просмотр карточки товара на huter.su human'ом
или отдельная задача на сверку источников, не входящая в этот пилот.

## 4. Более широкая выборка (30–50 изображений) — не выполнено, причина

В окружении разработки (`/home/shiro/proff58/media/products`, 66 файлов) все
локальные файлы оказались синтетическими одноцветными заглушками (сплошная
заливка `#C81D1E`, 1200×1200) — не реальными фото товаров. Прогон на них дал бы
100% `other`/`skipped` и был бы недостоверным результатом, поэтому в пилот не
включён. Живой каталог (боевой/стендовый `/media/`) в это задание не открывается
(инструкция: боевые данные не трогать; доступ к файлам стенда через SSH не
запрашивался, чтобы не создавать риск копирования боевых медиафайлов без
отдельного решения владельца).

**Непроверенные группы (честно, а не гипотеза):** серые/цветные подложки кроме
образца ВИХРЯ, прозрачность (`alpha`), кабели/цепи после rembg, длинные инструменты
(узкий кадр), низкое разрешение, наборы из нескольких предметов, реальные разные
ракурсы одного товара, `rembg_manual` на реальных данных, потенциальные ложные
срабатывания `suspect_backdrop` на глянцевых металлических/белых корпусах
(специфический блик может дать похожую на подложку картину — гипотеза, не
проверено). Для перечисленного нужна отдельная выборка живых фото каталога,
отобранная и одобренная владельцем перед просмотром.

## 6. Что дальше по плану задания (§5.4, §9)

- Маршруты `trim`/`rembg_black` остаются в режиме наблюдения
  (`PRODUCT_IMAGE_AUTO_ACCEPT_ROUTES` пуст по умолчанию) до отдельной
  разметки представительной выборки владельцем/менеджером и явного решения
  включить маршрут.
- Порядок пилота на боевых данных — по плейбуку задания: synthetic/локальный пилот
  (этот отчёт) → представительная выборка 30–50 живых фото → находки и разбор
  вручную → точечное применение по манифесту (`--manifest --apply`, только после
  отдельного одобрения и по зафиксированным ID) → возможный откат
  (`catalog_images_ops --mode processing-rollback`). Ни один из этих шагов эта
  сессия не выполняла на боевых/стендовых данных.
