Замер 01.09.2026 на копии данных стенда `dev.proff58.ru` (снимок каталожных таблиц
снят в тот же день, read-only). Задача — DRF-1428.

Повторить одной командой:

```bash
./manage.py catalog_facet_audit --markdown docs/catalog/facets-audit-<дата>.md \
    --outside-csv docs/catalog/appendix/outside-tree-<дата>.csv
```

Команда ничего не пишет и безопасна на боевом стенде. Если круг «фасет → фильтр»

## Главный вывод: пустой сайдбар — это отсутствие данных, а не привязок

Постановка задачи исходила из того, что фасеты «сосредоточены наверху»: 188 привязок
из 221 стоят на глубине ≤ 2, лист наследует общий набор раздела, и поэтому в сотне
листьев панель пуста. Перенос привязок вниз эту сотню не откроет — но причина иная,
чем «лист наследует чужое».

Причин две, и обе упираются в данные, а не в расстановку:

1. **В 115 листьях наследовать нечего в принципе** (5 506 товаров). Привязки стоят на
   корнях не всех разделов: лист под «Электрикой» наследует только привязки
   «Электрики», а их там нет. Единственное, что доходит почти всюду, — `tool_type`,
   но он не фасет сайдбара: `build_facets` эмитит его отдельной навигационной панелью
   (`facets.py`, ветка `is_nav`), поэтому в счёт осей сайдбара он не идёт.
2. **В остальных пустых листьях оси унаследованы, но у товаров нет значений.** Фасет
   рендерится только там, где значения есть (`facets.py`, «пустой фасет не отдаём»).

Проверка, которая разделяет «чинится привязкой» и «чинится наполнением», — искать
листья, где ось у товаров **заполнена**, а фасета нет. Таких листьев 26 из 172, если
считать любое непустое значение. Но ни в одном из них ось не покрывает и половины
товаров листа: лучший случай — `analog_code` у угольных щёток (46 товаров из 123, да
и то это список кодов, а не ось выбора), дальше `diameter` у малярного инструмента
(23 из 86) и `drive` у удлинителей (15 из 171).

**Почему малое покрытие — не «лучше, чем ничего».** Фасет поверх редко заполненной оси
не сужает выдачу, а прячет её. Покупатель выбирает «6 мм» и получает 5 шурупов вместо
100 — не потому, что остальных нет, а потому что у них поле не проставлено. Ровно та
же болезнь, что у пустого бренда (A4). Поэтому привязка осмысленна от покрытия ~50 %,
и до этого порога сегодня не дотягивает ни один лист.

Практический смысл: **массовый перенос привязок вниз отменяется**, точечные привязки
делаются по манифесту с порогом (см. ниже), а 55 листьев без единого способа сузить
выдачу открывает только трек наполнения характеристик.

## Часть A. Фильтры и фасеты

### Круг «фасет → фильтр» — сходится

Сверена **421 пара** «значение фасета → фильтр по этому значению» в 57 категориях
(до трёх значений на каждый фасет). Расхождений — **0**. Прежний замер (170 пар)
подтверждён на большей выборке.

Ловушка с именами параметров подтверждается кодом: разбор — `parse_attr_params`
(`apps/catalog/api/views.py`), префикс `attr_`; без префикса идут только `tool_type`,
`brand`, `price_min/max`, `in_stock`, `search`, `ids` (`apps/catalog/filters.py`).

### A1. Привязки на категориях вне витрины — 40, снимаются

Все 40 висят на легаси-корнях (`ruchnoy-instrument`, `osnastka-i-rashodniki`,
`almaznye-krugi` и др.), снятых с витрины при переезде на v2-дерево.

Проверено то, ради чего пункт и заводился: **ни один атрибут не живёт только на
мёртвой категории** — у каждого есть привязка в живом дереве. То есть фасеты никуда
не «пропали через мёртвого двойника»; это остаточный мусор, и снятие ничего не меняет
для покупателя. Команда уборки отказывается снимать привязку, если она у атрибута
последняя, — потерять фасет она не может по устройству.

### A2. Массовый перенос отменён, точечные привязки — по манифесту

Живых привязок 181 (плюс 40 мёртвых из A1), из них на глубине 1 — 28, на глубине
2 — 120, на глубине 3 — 33. Переносить их вниз бессмысленно (см. «Главный вывод»);
лишний унаследованный атрибут без значений просто не рендерится, вреда от него нет
(`disc_type` — в 8 листьях, `disc_diameter` и `bore` — в 6).

Точечные случаи закрывает `catalog_bind_leaf_axes` по явному списку
`data/catalog_leaf_filters.json`, с порогом: ось привязывается, только если заполнена
хотя бы у половины товаров листа и имеет минимум два значения. Обойти порог можно
полем `force` с обязательным письменным `reason` — чтобы решение «всё равно
привязываем» осталось в истории вместе с причиной.

Пять листьев, предложенных к привязке 01.09.2026 (DRF-1428), порог не прошли — все
восемь осей:

| Лист | Ось | Почему отклонена |
| -- | -- | -- |
| Пневмоинструмент | `drive` | значение одно — выбор ничего не сужает |
| Пневмоинструмент | `size` | заполнена у 3 из 285 товаров (1 %) |
| Удлинители и сетевые фильтры | `length` | значение одно |
| Напильники и рашпили | `disc_diameter` | заполнена у 2 из 136 (1 %) |
| Шурупы и глухари | `diameter` | заполнена у 8 из 101 (8 %) |
| Шурупы и глухари | `length` | заполнена у 8 из 101 (8 %) |
| Прочий строительный инструмент | `length` | заполнена у 11 из 244 (5 %) |
| Прочий строительный инструмент | `width` | значение одно |

Манифест оставлен в репозитории как есть: когда наполнение поднимет покрытие, тот же
прогон привяжет оси сам, без новой постановки.

### A3. Атрибуты без привязок — 12, пристроены

Все двенадцать (`lift_height`, `load_capacity`, `jack_type`, `article_1c` и др.)
принадлежат пяти домкратам из категории «Домкраты» (id=168) — след пилота парсера.
Все с `is_filterable=False`, то есть в фильтр не попадали бы и после привязки.

Решение: **привязать к «Домкратам» с `is_filter=False`**, а не удалять. Удаление
атрибута уносит с собой значения (41 строка `ProductAttributeValue`), добытые
парсером; характеристики при этом остаются на карточке товара, а сайдбар не
засоряется. Часть из них дублирует курируемый словарь (`load_capacity` ↔ `capacity`,
`jack_type` ↔ `domkrat_type`) — свести словари должен трек наполнения, у команды
уборки таких полномочий нет.

### A4. Бренд — счётчики честны, но выдача теряется

У **1 945** товаров в наличии из 6 150 поле `brand` пустое. Фасет брендов строится
`exclude(brand="")`, поэтому счётчики не врут: сумма по брендам меньше общего числа
товаров, и это видно.

Но эффект на витрине хуже, чем «фасет честно молчит». Товар с пустым брендом исчезает
при выборе **любого** бренда: покупатель фильтрует по «ЗУБР» и не видит зубровский
товар, у которого поле просто не заполнено. Это уже не отсутствие фильтра, а потеря
выдачи — треть наличия. Чинится наполнением бренда, отдельным треком.

### A5. Фильтры на странице поиска — DRF-1166

Отдельная задача; здесь фиксируется только требование: сайдбар PLP и сайдбар поиска
должны строиться одним механизмом (`build_facets`), а не двумя разными.

## Уборка привязок: как применяется

```bash
./manage.py catalog_cleanup_bindings                  # dry-run, ничего не пишет
./manage.py catalog_cleanup_bindings --commit         # применить + снимок отката
./manage.py catalog_cleanup_bindings --rollback FILE  # вернуть как было
```

Репетиция на копии данных стенда (01.09.2026): снято 40, создано 12, повторный
прогон — пустой план. Метрики листьев и круг «фасет → фильтр» после уборки не
изменились: 421 пара, 0 расхождений, столько же листьев с сайдбаром и без. То есть
для покупателя уборка — no-op, она приводит в порядок данные.

Перед применением на стенде — свежий `pg_dump` по `operations/pgdump-policy.md`;
снимок отката команда пишет сама в `var/restructure/`.
