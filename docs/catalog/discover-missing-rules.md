# `discover_missing_rules` — какое правило характеристик писать следующим

Read-only команда каталога, отвечающая на один вопрос: **какой `tool_type`
описать блоком правил следующим, чтобы получить максимум**.

До неё эта карта считалась разовыми скриптами и устаревала за месяц — каталог
меняется, и весь анализ приходилось повторять вручную. Теперь та же арифметика
живёт в репозитории и воспроизводится одной командой.

> **Команда ничего не пишет в БД.** Ни `ProductAttributeValue`, ни `attrs_cache`,
> ни `ImportRun`. Это её главное свойство: её можно гонять на живом стенде без
> гейт-цикла из [`operations/README.md`](operations/README.md). Свойство
> закреплено тестом `test_command_writes_nothing`, который сверяет снимок всех
> таблиц каталога до и после прогона.

## Быстрый старт

```bash
# карта по товарам в наличии, топ-20 типов
./manage.py discover_missing_rules --in-stock-only --active-only --limit 20

# полный machine-readable отчёт
./manage.py discover_missing_rules --in-stock-only --active-only \
    --json-report /tmp/discover.json

# один тип детально
./manage.py discover_missing_rules --tool-type krugi-shlif
```

## Флаги

| Флаг | Назначение |
|---|---|
| `--in-stock-only` | только товары с `available_quantity > 0` |
| `--active-only` | только `is_active=True` |
| `--tool-type SLUG` | ограничить анализ типом (можно несколько раз) |
| `--limit N` | показать N первых типов таблицы; **итоги считаются по всему скоупу**, срез влияет только на вывод |
| `--path DIR` | каталог с `attribute_rules.json` (по умолчанию `data/`) |
| `--json-report FILE` | записать полный отчёт в JSON |
| `--examples N` | сколько примеров названий на шаблон (по умолчанию 3) |
| `--min-pattern-share` | порог доли товаров типа, с которого шаблон предлагается (0.25) |
| `--max-false-positive-rate` | доля ложных срабатываний, выше которой шаблон отклоняется (0.33) |
| `--tail-threshold` | тип меньше N товаров — длинный хвост (6) |
| `--heterogeneity-dominance` | доля ведущего слова, ниже которой корпус разнороден (0.35) |
| `--sales-min-share` | доля товаров скоупа с продажами, ниже которой коммерческий вес нейтрализуется (0.01) |

Фильтры скоупа складываются **пересечением (AND)**, как у `enrich_attributes`.
Наличие считается по `available_quantity` — как у остальных операционных команд
каталога (витрина считает по `stock_quantity`, это другой контур).

## Как читать вывод

### Итоги пула

```
товаров в скоупе:            6150
есть характеристики:         3040 (49.4%)
нет характеристик:           3110
  из них тип без блока:      2756
  блок есть, но пусто:       354
без tool_type:               20
типов в пуле:                287
блоков в attribute_rules:    48
типов без блока:             239 на 2797 товаров
длинный хвост (< 6 тов.):    117 типов на 287 товаров
```

«Есть характеристики» — хотя бы один `ProductAttributeValue` с атрибутом,
**отличным от `tool_type`**: сам тип характеристикой не считается, иначе
покрытие было бы 100 % у всех типизированных товаров.

Товар без `tool_type` попадает в строку «тип без блока»: правил для него не
существует в принципе.

### Таблица кандидатов

```
  # tool_type          тов без хар    блок нов sales  extr facet     score  кум%  статус
  1 krugi-shlif         328      79 partial   2  1.00  0.69  1.00     454.0    2%  BLOCKED_BY_ATTRIBUTE
```

* `тов` — товаров типа в скоупе, `без хар` — из них без характеристик.
* `блок` — `absent` (блока правил нет), `partial` (есть, но шаблоны предлагают
  новое), `full` (всё уже описано).
* `нов` — сколько **новых** характеристик даст блок.
* `sales` / `extr` / `facet` — множители score (ниже).
* `кум%` — сколько процентов остатка (товаров без характеристик) закрывают
  первые N строк таблицы нарастающим итогом.

### Что предлагается писать

По каждому типу — предложенные характеристики с числами:

```
krep-styazhki (69 тов., score 74.0) — CREATE_RULE: можно писать блок правил
  diameter   number  N мм   попаданий 40 (58%), ложных 0
    regex: (?<![\d.,])(\d+(?:[.,]\d+)?)\s*мм(?![а-яёa-z])
    пример: Хомут-стяжка 100х2,5 мм, черные 100 шт
```

Строка с `~` в начале — шаблон, **отклонённый по шуму**: он проходит порог доли,
но наивная регулярка ошибается слишком часто. Рядом печатается `ОТКЛОНЁН:` с
числами и примеры ложных срабатываний.

Предложения печатаются при **любом** статусе: блокер объясняет, что мешает, но
не прячет картину — оператору нужно видеть, ради чего блокер стоит снимать.

## Ложные срабатывания: откуда берётся число

У каждого шаблона в [`apps/catalog/rule_discovery.py`](../../apps/catalog/rule_discovery.py)
**две** регулярки:

* `naive` — то, что человек пишет с первого раза (`(\d+)\s*м`);
* `guarded` — та же мысль с границами слова и отсечением соседних единиц.

`guarded` обязана быть подмножеством `naive`. Ложные срабатывания —
`naive_hits − guarded_hits`, то есть названия, которые наивная версия ловит, а
защищённая отбрасывает. Это измеримое число, а не предупреждение «бывают
ошибки».

Пример со стенда: у `sverla` наивный `N м` даёт **124 попадания и 188 ложных** —
«ф 3,2 мм» читается как «3,2 метра». Такой шаблон в рекомендации не попадает.

> Отдельно зафиксировано: наивная метровая регулярка **не** ловит «350Нм» —
> после числа идёт «Н», а не «м». Команда не приписывает себе чужих ошибок;
> реальный массовый класс ошибки здесь — «мм» и «мАч».

## Rule Impact Score

```
RIS = products × attributes × sales_weight × extraction_confidence × facet_visibility
```

Все пять множителей печатаются в отчёте, поэтому score можно пересчитать
вручную по его же числам — это проверяется тестом
`test_score_equals_product_of_five_factors`.

### `products`
Товаров типа в скоупе. Новая характеристика получит значение и у тех товаров,
у которых уже есть другие характеристики, поэтому знаменателем берётся весь тип,
а не только пробел.

### `attributes`
Сколько **новых** характеристик даст блок: шаблоны, прошедшие
`--min-pattern-share` и гейт по шуму, и ещё не описанные в блоке типа. Ноль
новых характеристик — ноль выгоды.

### `sales_weight`
Продажи за окно `SALES_WINDOW_DAYS` (`ProductSalesStat`, наполняется из
`ProductSalesFact`: заказы сайта и выгрузка `/api/1c/sales/upload`).

```
доля товаров скоупа с продажами < --sales-min-share (1 %)
    → 1.0 у всех типов + флаг sales_data_absent
иначе
    → 0.5 + 1.5 × доля товаров типа с продажами, диапазон [0.5, 2.0]
```

Два решения, которые важно понимать:

1. **Тип без продаж получает 0.5, а не 0.** Иначе товар, который не продавался
   именно потому, что у него нет характеристик и его не находят фильтром,
   навсегда остался бы без правил.
2. **Деградация нейтральная (1.0), а не нулевая.** С нулём весь рейтинг
   схлопнулся бы, и команда стала бы бесполезной ровно там, где она нужнее
   всего.

Порог **долевой, а не абсолютный**: осмысленность продаж зависит от размера
каталога, а не от числа строк. 1 % выбран не «на глаз» — это точка, где
множитель перестаёт что-либо различать: при базовой частоте продаж 1 % у типа
медианного размера (6 товаров) ожидаемое число продавшихся — 0.06, то есть почти
все типы получают одинаковый вес 0.5, и множитель просто делит рейтинг на два,
изображая учёт продаж.

**Состояние на 2026-08-14:** на стенде 1 факт продажи на 47 225 товаров
(0.016 % скоупа) — коммерческий вес в приоритизации **не участвует**, и команда
печатает это предупреждением. Пока 1С не начнёт слать `sales/upload`, множитель
остаётся нейтральным.

### `extraction_confidence`
Средняя доля товаров типа под одним предложенным шаблоном (100 % → 1.0,
половина → 0.5). Правило, срабатывающее у четверти корпуса, стоит вчетверо
меньше правила, срабатывающего у всех.

### `facet_visibility`
```
доля товаров в живой категории (is_active AND on_site)
× 1.0, если у этих категорий (или их предков) уже есть привязка
      CategoryAttribute(is_filter=True)
× 0.75, если привязок нет — фасет придётся заводить с нуля
```

Значение без фасетной привязки к категории товара или её предку витрине не
видно. Мёртвая категория обнуляет выгоду правила целиком — писать значения туда
можно, но покупатель их не увидит.

## Статусы

| Статус | Что значит | Что делать |
|---|---|---|
| `CREATE_RULE` | можно писать блок правил | писать |
| `BLOCKED_BY_CLASSIFICATION` | разнородный корпус — «свалка», а не тип | сначала разбор на подтипы |
| `BLOCKED_BY_ATTRIBUTE` | предложенных `Attribute` нет в БД | сначала `load_attributes` |
| `BLOCKED_BY_CATEGORY` | товары стоят в мёртвых категориях | чинить дерево |
| `SKIP_SET` | тип-набор | характеристики самого набора, не элементов |
| `TAIL_GENERIC` | длинный хвост | отдельный блок не окупается |

Порядок проверок = порядок приоритета блокеров: хвост → набор → разнородность →
мёртвая категория → отсутствующий атрибут → можно писать.

## Ловушки, которые команда помечает

### «Свалка» вместо типа
`prochaya-osnastka` (153 товара) — не тип, а свалка: правило писать не на чем,
нужен разбор на подтипы. Команда определяет это **по признаку, а не по списку
slug'ов**: берёт ведущее слово каждого названия («Струбцина», «Переходник»,
«Заклёпка») и смотрит, сходятся ли они. Корпус разнороден, если одновременно:

* товаров ≥ 20 (на маленьком типе признак не работает);
* доля самого частого ведущего слова < `--heterogeneity-dominance` (0.35);
* разных ведущих слов ≥ 10.

Тип, который просто велик, но однороден, под признак не попадает — это
проверяется тестом `test_homogeneous_corpus_is_not_flagged`.

### Наборы
У набора по конвенции владельца пишутся характеристики **самого набора**, а не
его элементов. `piece_count` — число предметов, `package_quantity` — фасовка,
путать нельзя. Для типов-наборов команда автоматически переводит шаблон «N шт»
в `piece_count`.

Тип считается набором по slug `nabory-*` **или** если ведущее слово «Набор» у
≥ 50 % названий. Порог именно долевой: у почти любого обычного типа найдётся
один-два товара «Набор головок», и признак «есть хоть одно такое название»
пометил бы наборами `golovki`, `otvertki` и `klyuchi-gaechnye`. Отдельные наборы
внутри обычного типа — задача
[карантина](attribute-quarantine.md), а не статуса типа.

### Длинный хвост
Медиана — 6 товаров на тип; 114 типов имеют 1–5 товаров. Отдельный блок правил
на такой тип не окупается, поэтому команда сводит их в одну строку итогов
(`длинный хвост`) и ставит статус `TAIL_GENERIC` вместо того, чтобы предлагать
сотню блоков.

## Контрольный кумулятив: два ряда, которые нельзя путать

В конце вывода печатаются **два** ряда «первые N типов без блока закрывают X
товаров»:

* `all` — все товары типов без блока: «какой объём каталога вообще относится к
  неописанным типам»;
* `gap` — только товары **без характеристик**: «сколько товаров реально получат
  значения». Тип, полностью охарактеризованный вручную, в этот ряд не попадает
  вовсе, поэтому типов в нём меньше.

Именно на этом расходятся ручные замеры каталога. Замер 2026-08-14
(`--in-stock-only --active-only`):

| N типов | `all` | `gap` |
|---|---|---|
| 10 | 695 | 692 |
| 20 | 1073 | 1062 |
| 50 | 1757 | 1731 |
| 100 | 2352 | 2309 |
| 150 | 2636 | 2581 |
| итого | 239 типов / 2797 | 237 типов / 2736 |

Ручные контрольные числа владельца (692 / 1062 / 1731 / 2309 / 2581 при
237 типах на 2736 товаров) воспроизводятся рядом `gap` **точно**.
