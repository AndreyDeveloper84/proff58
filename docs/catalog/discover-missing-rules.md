# `discover_missing_rules` — какое правило характеристик писать следующим

Read-only команда каталога, отвечающая на два вопроса: **где лежит максимальный
потенциал** и **что можно безопасно сделать следующим без дополнительной
архитектурной работы**. Ответ даётся не по `tool_type`, а по конкретным **осям**
с максимальным actionable impact.

До неё эта карта считалась разовыми скриптами и устаревала за месяц — каталог
меняется, и весь анализ приходилось повторять вручную. Теперь та же арифметика
живёт в репозитории и воспроизводится одной командой.

> **Команда ничего не пишет в БД.** Ни `ProductAttributeValue`, ни `attrs_cache`,
> ни `ImportRun`. Это её главное свойство: её можно гонять на живом стенде без
> гейт-цикла из [`operations/README.md`](operations/README.md). Свойство
> закреплено тестом `test_command_writes_nothing`, который сверяет снимок всех
> таблиц каталога до и после прогона.

## Почему счёт идёт по осям, а не по типу

Разбор типа `klyuchi-gaechnye` (210 товаров) показал, что усреднение на уровне
типа маскирует различие и ухудшает приоритизацию:

* ось `wrench_type` — **142 значения, все видимы** покупателю;
* ось `material` — **74 значения, все невидимы**: `Attribute` (id 23) в БД есть,
  но к категориям ключей (346 «Ключи», 340 «Наборы ручного инструмента») не
  привязан.

Один коэффициент `facet_visibility` на весь тип показал бы «блок с потенциалом
216 значений». Безопасно реализуемы из них только 142. Поэтому у каждой оси
считаются свои три числа и свой статус, а итог типа складывается из осей.

## Быстрый старт

```bash
# карта по товарам в наличии, топ-20 типов
./manage.py discover_missing_rules --in-stock-only --active-only --limit 20

# полный machine-readable отчёт
./manage.py discover_missing_rules --in-stock-only --active-only \
    --json-report /tmp/discover.json

# то же самое в Markdown — читать глазами и вставлять в задачу
./manage.py discover_missing_rules --in-stock-only --active-only \
    --md-report /tmp/discover.md

# один тип детально
./manage.py discover_missing_rules --tool-type krugi-shlif
```

## Флаги

| Флаг | Назначение |
|---|---|
| `--in-stock-only` | только товары с `available_quantity > 0` |
| `--active-only` | только `is_active=True` |
| `--tool-type SLUG` | ограничить анализ типом (можно несколько раз) |
| `--limit N` | показать N первых типов таблицы; **итоги считаются по всему скоупу**, срез влияет только на вывод |
| `--path DIR` | каталог с `attribute_rules.json` (по умолчанию `data/`) |
| `--json-report FILE` | записать полный отчёт в JSON |
| `--md-report FILE` | записать тот же отчёт в Markdown (см. [ниже](#markdown-отчёт)) |
| `--examples N` | сколько примеров названий на шаблон (по умолчанию 3) |
| `--min-pattern-share` | порог доли товаров типа, с которого шаблон предлагается (0.25) |
| `--max-false-positive-rate` | доля ложных срабатываний, выше которой шаблон отклоняется (0.33) |
| `--tail-threshold` | тип меньше N товаров — длинный хвост (6) |
| `--heterogeneity-dominance` | доля ведущего слова, ниже которой корпус разнороден (0.35) |
| `--sales-min-share` | доля товаров скоупа с продажами, ниже которой коммерческий вес нейтрализуется (0.01) |
| `--min-facet-fill-rate` | заполненность фасета, ниже которой предложение о привязке помечается малополезным (0.10) |

Фильтры скоупа складываются **пересечением (AND)**, как у `enrich_attributes`.
Наличие считается по `available_quantity` — как у остальных операционных команд
каталога (витрина считает по `stock_quantity`, это другой контур).

## Как читать вывод

### Итоги пула

```
товаров в скоупе:            6150
есть характеристики:         3040 (49.4%)
нет характеристик:           3110
  из них тип без блока:      2756
  блок есть, но пусто:       354
без tool_type:               20
типов в пуле:                287
блоков в attribute_rules:    48
типов без блока:             239 на 2797 товаров
длинный хвост (< 6 тов.):    117 типов на 287 товаров
```

«Есть характеристики» — хотя бы один `ProductAttributeValue` с атрибутом,
**отличным от `tool_type`**: сам тип характеристикой не считается, иначе
покрытие было бы 100 % у всех типизированных товаров.

Товар без `tool_type` попадает в строку «тип без блока»: правил для него не
существует в принципе.

### Три числа: потенциал, исполнимое, запертое

```
=== Значения: потенциал / исполнимое / запертое ===
potential_values:  4180
actionable_values: 1633
blocked_values:    2547
actionable_ratio:  39.1%
```

* `potential_values` — сколько значений **технически** можно извлечь;
* `actionable_values` — сколько из них можно **безопасно записать и показать
  покупателю сейчас**;
* `blocked_values` — сколько упирается в отсутствие `Attribute`, в отсутствие
  facet-привязки, в мёртвую категорию, в разнородность типа или в грязный пул.

Разница между `potential` и `actionable` — это **объём работы, запертой за
архитектурой**, и она ценна сама по себе: из неё строится очередь привязок.

### Таблица кандидатов

```
  # tool_type          тов без хар    блок нов     pot     act  act%   a-score   p-score  кум%  статус
  1 klyuchi-gaechnye    210     198 partial   2     216     142   66%     142.0     216.0    7%  CREATE_RULE
```

* `тов` — товаров типа в скоупе, `без хар` — из них без характеристик.
* `блок` — `absent` (блока правил нет), `partial` (есть, но шаблоны предлагают
  новое), `full` (всё уже описано).
* `нов` — сколько **новых** характеристик даст блок.
* `pot` / `act` / `act%` — три числа типа, агрегированные **снизу вверх из осей**.
* `a-score` / `p-score` — `actionable_score` и `potential_score`
  (`Σ значений × sales_weight`). **Сортировка — по `a-score`.**
* `кум%` — сколько процентов остатка (товаров без характеристик) закрывают
  первые N строк таблицы нарастающим итогом.

### Что предлагается писать: разбивка по осям

По каждому типу — оси со своими числами, своим статусом и своим следующим шагом:

```
klyuchi-gaechnye (210 тов., score 216.0) — CREATE_RULE: можно писать блок правил

  wrench_type
    potential: 142   actionable: 142   visibility: 100%   status: READY

  material
    potential: 74    actionable: 0     visibility: 0%   status: BLOCKED_BY_FACET
    next_action: FACET_BINDING_AUDIT

  potential_total:  216
  actionable_total: 142
  actionable_ratio: 65.7%
```

Ниже разбивки — те же оси подробно: regex, примеры названий и ложные
срабатывания. Строка с `~` в начале — шаблон, **отклонённый по шуму**: он
проходит порог доли, но наивная регулярка ошибается слишком часто. Рядом
печатается `ОТКЛОНЁН:` с числами и примеры ложных срабатываний.

Предложения печатаются при **любом** статусе: блокер объясняет, что мешает, но
не прячет картину — оператору нужно видеть, ради чего блокер стоит снимать.

### Рейтинг осей (сквозной по каталогу)

Работу выбирают не по `tool_type`, а по оси: одна и та же ось набирает объём
сразу в нескольких типах, и по типам этот объём не виден. Печатаются два
порядка:

```
=== Топ осей по actionable_values (что писать) ===
  diameter             potential  1204 actionable  1204 blocked     0  типов  38  READY×38

=== Топ осей по blocked_values (очередь архитектурной работы) ===
  material             potential   612 actionable     0 blocked   612  типов   9  BLOCKED_BY_FACET×9
```

Второй ряд и есть **очередь архитектурной работы**: что создать (`load_attributes`)
и что привязать (facet-binding).

### Куда уйдёт привязка

```
=== Куда уйдёт привязка (поле category блока) ===
привязок в корень раздела: 28; с низкой заполненностью: 19; неразрешимых: 3
  tool_type    категория блока   кат.  гл  накрыто   вне  под фасетом  заполн  флаги
  sverla       Оснастка            74   1      402     0         2416   16.6%  КОРЕНЬ
  klyuchi-...  Ручной инструмент  339   1      173    37         1031   13.8%  КОРЕНЬ
```

* `накрыто` / `вне` — сколько товаров типа цель накрывает и сколько остаётся
  снаружи. `вне > 0` значит, что часть товаров значения не получит даже после
  `load_attributes`.
* `под фасетом` — blast radius цели: сколько товаров скоупа окажется под фасетом.
* `флаги` — `КОРЕНЬ` (привязка уходит в `depth == 1`, а товары лежат глубже),
  `МАЛО` (заполненность ниже `--min-facet-fill-rate`), `НЕ РАЗРЕШЕНО` (имя не
  разрешается или узел мёртв — привязки не будет вовсе).

Типы без блока в раздел не попадают: их цель ещё не выбрана.

### Очередь facet-binding

Агрегат «привязка атрибута X к категории Y разблокирует N значений», по убыванию
выигрыша. Раньше такой список собирался вручную по одному типу — теперь команда
строит его сама:

```
=== Очередь facet-binding (что привязать, чтобы разблокировать) ===
всего заперто привязками: 612 значений; порог полезной заполненности 10%
  атрибут                кат.   уровень  разблок под фасетом  заполн  типы
  material                346    direct       74          210   35.2%  klyuchi-gaechnye
  material                339  ancestor      612         4180   14.6%  klyuchi-gaechnye, ...
```

* `уровень` — `direct` (категория товаров) или `ancestor` (узел выше). Предок
  предлагается, **только если объединяет две и более прямые категории**: иначе
  это тот же фасет, но с большим радиусом и худшей заполненностью.
* `под фасетом` — **blast radius**: сколько товаров скоупа окажется под фасетом,
  если привязать к этому узлу. Привязка наследуется всем потомкам.
* `заполн` — какая доля из них получит значение. Ниже `--min-facet-fill-rate`
  строка помечается `⚠`: фасет с заполненностью в единицы процентов не помогает
  выбрать, а засоряет сайдбар (прецедент каталога — фасет на 1,5 %).

В очередь попадают **только** оси со статусом `BLOCKED_BY_FACET`: у мёртвой
категории и отсутствующего атрибута лечение другое, и смешивать их в один список
значит подсунуть владельцу работу, которая ничего не разблокирует.

## Markdown-отчёт

`--md-report FILE` пишет тот же отчёт в Markdown — читать глазами и вставлять в
задачу без переверстки. Флаг **независим** от `--json-report`: можно указать оба
сразу, можно ни одного (тогда остаётся только консольная таблица).

```bash
./manage.py discover_missing_rules --in-stock-only --active-only \
    --json-report /tmp/discover.json --md-report /tmp/discover.md
```

Структура файла повторяет консольный вывод, но таблицами:

| Раздел | Что внутри |
|---|---|
| «Скоуп» | фильтры и все пороги прогона — без них числа невоспроизводимы |
| «Итоги пула» | те же строки, что печатает консоль |
| строка про продажи | цитатой-предупреждением, если коммерческий вес деградировал |
| «Кандидаты» | таблица по убыванию `actionable_score`: тип, товаров, без характеристик, состояние блока, новых атрибутов, `potential`/`actionable`/`blocked`, оба score, legacy RIS, кумулятивный процент, статус |
| «Рейтинг осей» | два порядка — `by_actionable` (что писать) и `by_blocked` (очередь архитектурной работы) |
| «Куда уйдёт привязка» | по каждому типу с блоком: разрешённая категория, накрытые товары, blast radius, заполненность и флаги `корень раздела` / `низкая заполненность` / `не разрешено` |
| «Очередь facet-binding» | что привязать, что это разблокирует, blast radius и заполненность |
| «Что предлагается писать» | по каждому кандидату — таблица осей (`potential`, `actionable`, `visibility`, статус, `next_action`) со строкой «итого», затем детальная таблица шаблонов и regex с примерами |
| «Контрольный кумулятив» | оба ряда, `all` и `gap`, в одной таблице |

`--limit N` действует и здесь: срез режет таблицу кандидатов и разделы с осями,
итоги и кумулятивы считаются по всему скоупу.

Разметка valid-by-construction, а не «на глаз»:

* значения в ячейках экранируются — труба внутри значения не разъезжает таблицу;
* регулярки и примеры названий печатаются **инлайн-кодом**, длина обрамляющих
  бэктиков считается по содержимому: `(ph|pz|tx|t|sl|hex|torx)` внутри таблицы
  выглядел бы разделителем колонок, а внутри кода с одиночным бэктиком сломался
  бы о бэктик в самом значении;
* у всех таблиц явное выравнивание колонок (числа вправо).

Это проверяется тестом `test_md_report_stays_valid_markdown_with_pipes_in_regex`:
он разбирает готовый файл и требует, чтобы во всех строках каждой таблицы
совпадало число неэкранированных труб.

Запись файла на read-only статус команды не влияет — в БД по-прежнему ноль
записей (`test_md_report_writes_nothing_to_db`).

## Ложные срабатывания: откуда берётся число

У каждого шаблона в [`apps/catalog/rule_discovery.py`](../../apps/catalog/rule_discovery.py)
**две** регулярки:

* `naive` — то, что человек пишет с первого раза (`(\d+)\s*м`);
* `guarded` — та же мысль с границами слова и отсечением соседних единиц.

`guarded` обязана быть подмножеством `naive`. Ложные срабатывания —
`naive_hits − guarded_hits`, то есть названия, которые наивная версия ловит, а
защищённая отбрасывает. Это измеримое число, а не предупреждение «бывают
ошибки».

Пример со стенда: у `sverla` наивный `N м` даёт **124 попадания и 188 ложных** —
«ф 3,2 мм» читается как «3,2 метра». Такой шаблон в рекомендации не попадает.

> Отдельно зафиксировано: наивная метровая регулярка **не** ловит «350Нм» —
> после числа идёт «Н», а не «м». Команда не приписывает себе чужих ошибок;
> реальный массовый класс ошибки здесь — «мм» и «мАч».

## Два score

Итог типа **агрегируется снизу вверх, из осей** — отдельного коэффициента на тип
нет:

```
potential_score  = Σ potential_values  × sales_weight
actionable_score = Σ actionable_values × sales_weight
```

**Рейтинг сортируется по `actionable_score`**, `potential_score` печатается
рядом. Инвариант `actionable ≤ potential` держится на каждом уровне — оси, типа
и каталога (`test_actionable_score_never_exceeds_potential_score`).

### Rule Impact Score (legacy)

```
RIS = products × attributes × sales_weight × extraction_confidence × facet_visibility
```

Поле `score` осталось в отчёте для преемственности со старыми замерами: все пять
множителей печатаются, поэтому его можно пересчитать вручную
(`test_score_equals_product_of_five_factors`). Приоритизацией он больше не
управляет — он считает потенциал одним коэффициентом на тип и усредняет
несопоставимые оси.

### `products`
Товаров типа в скоупе. Новая характеристика получит значение и у тех товаров,
у которых уже есть другие характеристики, поэтому знаменателем берётся весь тип,
а не только пробел.

### `attributes`
Сколько **новых** характеристик даст блок: шаблоны, прошедшие
`--min-pattern-share` и гейт по шуму, и ещё не описанные в блоке типа. Ноль
новых характеристик — ноль выгоды.

### `sales_weight`
Продажи за окно `SALES_WINDOW_DAYS` (`ProductSalesStat`, наполняется из
`ProductSalesFact`: заказы сайта и выгрузка `/api/1c/sales/upload`).

```
доля товаров скоупа с продажами < --sales-min-share (1 %)
    → 1.0 у всех типов + флаг sales_data_absent
иначе
    → 0.5 + 1.5 × доля товаров типа с продажами, диапазон [0.5, 2.0]
```

Два решения, которые важно понимать:

1. **Тип без продаж получает 0.5, а не 0.** Иначе товар, который не продавался
   именно потому, что у него нет характеристик и его не находят фильтром,
   навсегда остался бы без правил.
2. **Деградация нейтральная (1.0), а не нулевая.** С нулём весь рейтинг
   схлопнулся бы, и команда стала бы бесполезной ровно там, где она нужнее
   всего.

Порог **долевой, а не абсолютный**: осмысленность продаж зависит от размера
каталога, а не от числа строк. 1 % выбран не «на глаз» — это точка, где
множитель перестаёт что-либо различать: при базовой частоте продаж 1 % у типа
медианного размера (6 товаров) ожидаемое число продавшихся — 0.06, то есть почти
все типы получают одинаковый вес 0.5, и множитель просто делит рейтинг на два,
изображая учёт продаж.

**Состояние на 2026-08-14:** на стенде 1 факт продажи на 47 225 товаров
(0.016 % скоупа) — коммерческий вес в приоритизации **не участвует**, и команда
печатает это предупреждением. Пока 1С не начнёт слать `sales/upload`, множитель
остаётся нейтральным.

### `extraction_confidence`
Средняя доля товаров типа под одним предложенным шаблоном (100 % → 1.0,
половина → 0.5). Правило, срабатывающее у четверти корпуса, стоит вчетверо
меньше правила, срабатывающего у всех.

### `facet_visibility` (legacy, уровень типа)
```
доля товаров в живой категории (is_active AND on_site)
× 1.0, если у этих категорий (или их предков) уже есть привязка
      CategoryAttribute(is_filter=True)
× 0.75, если привязок нет — фасет придётся заводить с нуля
```

Множитель остался у legacy-RIS. **Рейтингом он больше не управляет**: он
усредняет несопоставимые оси и меряет «есть ли у категории хоть какой-то
фильтр», а не «привязан ли нужный атрибут». Актуальная видимость считается по
осям — ниже.

## Видимость оси: два источника и три числа

Ось видима покупателю, если категория товара жива (`is_active AND on_site`) и
фасетом объявлен **именно её атрибут** — у самой категории или у любого предка
(фасеты наследуются вниз). Проверка идёт **по каждому товару**, а не долей на
тип.

Источников видимости два, и путать их нельзя:

1. **Привязка уже есть** (`already_visible_values`) — значение будет видно сразу.
2. **Привязку создаст `load_attributes`** (`unlocked_by_binding_target`) — по полю
   `category` блока правил.

### Почему второй источник обязателен

`load_attributes` разрешает имя категории лестницей `_resolve_category`: живые
кандидаты важнее мёртвых, внутри отобранных приоритет у `depth == 1`. На фактах
каталога это значит, что **28 блоков из 48 направляют привязку в корень
раздела**, а не в профильную категорию, и у 19 это расходится с тем, где реально
лежат товары:

| Блок | Куда уйдёт привязка | Где товары |
|---|---|---|
| `sverla` | 74 «Оснастка» (корень) | 81 «Свёрла» (402 из 402) |
| `bury` | 74 «Оснастка» | 78 «Буры» (197/197) |
| `bity` | 74 «Оснастка» | 91 «Биты» (117/117) |
| `klyuchi-gaechnye` | 339 «Ручной инструмент» (корень) | 346 «Ключи» (173/210) |
| `otvertki` | 339 «Ручной инструмент» | 344 «Отвёртки» (96/97) |

Поэтому команда повторяет ту же лестницу (`resolve_binding_category`) и считает
видимость по категории, **куда привязка фактически уйдёт**. Считать по категории
товара значит учитывать привязку, которой не будет, и завышать оценку.

Обратная сторона: под корневыми фасетами оказываются тысячи товаров (74 → 2416
в наличии, 339 → 1031, 3 «Электроинструмент» → 343, 392 → 131), а значения
получают единицы. Это видно в разделе «Куда уйдёт привязка» — с blast radius,
заполненностью и флагом.

Три исхода, у которых **нет** будущей привязки: цель мёртвая
(`bound:*:dead` — фасет от скрытого узла живым потомкам не наследуется),
неоднозначная (`ambiguous:*`) и ненайденная (`not_found`). Все три дают оси
`BLOCKED_BY_FACET`.

У типа **без блока** цели ещё не существует: её выберет оператор. Тогда счёт
идёт по категориям самих товаров, а результат помечается
`binding_target.source = "presumed"` — предположение не выдаётся за замер и в
раздел «Куда уйдёт привязка» не попадает.

## Статусы оси

| Статус | Что значит | `next_action` |
|---|---|---|
| `READY` | ось готова к работе | `WRITE_RULE` |
| `BLOCKED_BY_ATTRIBUTE` | `Attribute` нет в БД | `LOAD_ATTRIBUTES` (**после** того, как правило появится в `attribute_rules.json`) |
| `BLOCKED_BY_FACET` | атрибут есть, но к нужным категориям не привязан | `FACET_BINDING_AUDIT` — решение владельца о привязке |
| `BLOCKED_BY_CATEGORY` | все товары оси в мёртвых категориях | `CATEGORY_REVIVAL` |
| `BLOCKED_BY_CLASSIFICATION` | тип — «свалка» | `SPLIT_TOOL_TYPE` |
| `BLOCKED_BY_PURITY` | пул грязный: шаблон ошибается чаще порога | `POOL_PURITY_AUDIT` |
| `SKIP_SET` | ось описывает состав набора, а не предмет | `SET_COMPOSITION_REVIEW` |

`BLOCKED_BY_ATTRIBUTE` и `BLOCKED_BY_FACET` разделены намеренно: у них **разная
цена и разная работа**. Первый лечится командой, второй — решением владельца о
структуре фасетов. Сваливать их в один «что-то не так с осью» значит скрывать
разницу между «запустить load_attributes» и «согласовать привязку».

Порядок проверок: набор → разнородность → шум → нет атрибута → мёртвая категория
→ нет привязки → готово.

## Статусы типа

| Статус | Что значит | Что делать |
|---|---|---|
| `CREATE_RULE` | можно писать блок правил | писать |
| `BLOCKED_BY_CLASSIFICATION` | разнородный корпус — «свалка», а не тип | сначала разбор на подтипы |
| `BLOCKED_BY_ATTRIBUTE` | предложенных `Attribute` нет в БД | сначала `load_attributes` |
| `BLOCKED_BY_CATEGORY` | товары стоят в мёртвых категориях | чинить дерево |
| `SKIP_SET` | тип-набор | характеристики самого набора, не элементов |
| `TAIL_GENERIC` | длинный хвост | отдельный блок не окупается |

Порядок проверок = порядок приоритета блокеров: хвост → набор → разнородность →
мёртвая категория → отсутствующий атрибут → можно писать.

## Ловушки, которые команда помечает

### «Свалка» вместо типа
`prochaya-osnastka` (153 товара) — не тип, а свалка: правило писать не на чем,
нужен разбор на подтипы. Команда определяет это **по признаку, а не по списку
slug'ов**: берёт ведущее слово каждого названия («Струбцина», «Переходник»,
«Заклёпка») и смотрит, сходятся ли они. Корпус разнороден, если одновременно:

* товаров ≥ 20 (на маленьком типе признак не работает);
* доля самого частого ведущего слова < `--heterogeneity-dominance` (0.35);
* разных ведущих слов ≥ 10.

Тип, который просто велик, но однороден, под признак не попадает — это
проверяется тестом `test_homogeneous_corpus_is_not_flagged`.

### Наборы
У набора по конвенции владельца пишутся характеристики **самого набора**, а не
его элементов. `piece_count` — число предметов, `package_quantity` — фасовка,
путать нельзя. Для типов-наборов команда автоматически переводит шаблон «N шт»
в `piece_count`.

Тип считается набором по slug `nabory-*` **или** если ведущее слово «Набор» у
≥ 50 % названий. Порог именно долевой: у почти любого обычного типа найдётся
один-два товара «Набор головок», и признак «есть хоть одно такое название»
пометил бы наборами `golovki`, `otvertki` и `klyuchi-gaechnye`. Отдельные наборы
внутри обычного типа — задача
[карантина](attribute-quarantine.md), а не статуса типа.

### Длинный хвост
Медиана — 6 товаров на тип; 114 типов имеют 1–5 товаров. Отдельный блок правил
на такой тип не окупается, поэтому команда сводит их в одну строку итогов
(`длинный хвост`) и ставит статус `TAIL_GENERIC` вместо того, чтобы предлагать
сотню блоков.

## Контрольный кумулятив: два ряда, которые нельзя путать

В конце вывода печатаются **два** ряда «первые N типов без блока закрывают X
товаров»:

* `all` — все товары типов без блока: «какой объём каталога вообще относится к
  неописанным типам»;
* `gap` — только товары **без характеристик**: «сколько товаров реально получат
  значения». Тип, полностью охарактеризованный вручную, в этот ряд не попадает
  вовсе, поэтому типов в нём меньше.

Именно на этом расходятся ручные замеры каталога. Замер 2026-08-14
(`--in-stock-only --active-only`):

| N типов | `all` | `gap` |
|---|---|---|
| 10 | 695 | 692 |
| 20 | 1073 | 1062 |
| 50 | 1757 | 1731 |
| 100 | 2352 | 2309 |
| 150 | 2636 | 2581 |
| итого | 239 типов / 2797 | 237 типов / 2736 |

Ручные контрольные числа владельца (692 / 1062 / 1731 / 2309 / 2581 при
237 типах на 2736 товаров) воспроизводятся рядом `gap` **точно**.
