## 3. Разбор промахов и докрученные regex

Проанализированы все 55 товаров без `power`, 50 без `chuck`, 61 без `energy_impact`
(лист: `scratchpad/parser-mvp/miss_before.txt`). Промахи разделились на три класса:
чинимые точечно, нечинимые (нет данных в названии) и требующие решения владельца.

### Докрутка 1 — `energy_impact`: усечённые единицы «Д» / «ж»

```json
"regex": [
  "(\\d+(?:[.,]\\d+)?)\\s*(?:дж|дж\\.|джоул|joule)(?![а-яёa-z])",
  "(\\d+(?:[.,]\\d+)?)\\s*(?:д|ж)(?![а-яёa-z0-9])"          // ← добавлено
]
```

**Обоснование.** Названия из 1С обрезаны по длине (~50 символов) либо содержат
опечатку, из-за чего «Дж» усечено до одной буквы:
`«Bosch GBH 5-38D; 1050Вт, SDS-MAX, 5,9ж»`, `«Makita HR2800; …, 2,9Д»`,
`«ЗУБР ЗПВ-32-1250 ЭВК SDS+, вертикальный, 3,5Д»`, `«Makita DHR 202RFE …, 1,9Д»`.
Паттерн добавлен **вторым** — полная форма «Дж» по-прежнему выигрывает, если есть
в строке. Негативный lookahead запрещает букву и цифру после — «д» перед словом
(«диаметр») и перед числом не срабатывает. Дало +4, все 4 сверены с паспортными
значениями моделей (GBH 5-38 D = 5,9 Дж; HR2800 = 2,9 Дж и т.д.).

### Докрутка 2 — `no_load_speed`: новое правило (диапазоны «0-900об/мин»)

```json
{"slug": "no_load_speed", "name": "Обороты х.х.", "kind": "number",
 "unit": "об/мин", "source": "regex", "priority": 40,
 "is_filter": false, "is_ai_feature": true,
 "regex": ["(\\d{3,5})\\s*об[/.\\s]?мин"]}
```

**Обоснование.** Атрибут `no_load_speed` уже существует и уже привязан к `cat=3`
(новый `Attribute` не создавался — граница соблюдена), но в правилах перфораторов
его не было, хотя обороты есть в названиях. Regex взят **дословно тот же**, что у
`bolgarki-ushm` / `pily` / `shlifmashiny` / `frezery` — контур остаётся единообразным.

Диапазоны он обрабатывает корректно за счёт того, что цифры берутся вплотную к
«об/мин»: `0-1050об/мин` → 1050, `120-310об/мин` → 310, `0-110/0-280об/мин` → 280,
`250-500об/мин` → 500. Это верхняя граница, т.е. паспортные обороты х.х. Удары
(`0-4800уд/мин`) не захватываются — паттерн требует «об/мин». Дало +17.

### Докрутка 3 — `chuck`: голое «SDS»

```json
"keywords": ["sds-plus", "sds plus", "sds+", "sdsplus", "sds"]   // ← "sds" добавлено
```

**Обоснование.** `«Перф. аккум. DH14DSL; 14,4V, 2х3,0А/ч, Li-ion, SDS»` — тип патрона
указан без суффикса. Ключевое слово добавлено **последним** в опцию SDS-plus, а
опция SDS-max перебирается движком раньше — поэтому «SDS-max»/«sds max» по-прежнему
выигрывают, подмены не будет.

**Известное ограничение:** keyword-движок ищет подстроку без границ слова, поэтому
«sds» ловится и внутри артикула — `«Перф. RSDS800K Ryobi»` дал SDS-plus по подстроке
в `RSDS800K`. Фактически значение верное (Ryobi RSDS800K — SDS-plus), но механизм
матча грязный. Оба попадания в текущей выборке верны; риск ошибки на будущих
поставках оцениваю как низкий (SDS-max в артикуле почти не встречается, а явное
упоминание max в названии перебивает). Если решите не рисковать — слово убирается
из правил, цена вопроса −2 товара.

### Докрутка 4 — `motor_type`: сокращение «бесщ.»

```json
"keywords": ["бесщеточн", "бесщетк", "безщеточн", "бесщ", "brushless", "bl-"]
```

**Обоснование.** `«Перф. DH45MEY; бесщ., 1500Вт, SDS-max…»` — распространённое
сокращение у HiKoki/Hitachi. Слов на «бесщ», кроме «бесщёточный», не существует,
опция brushless перебирается раньше brushed, так что «щеточн» не перехватит. Дало +3.

### Что сознательно НЕ докручено

| Класс | Пример | Почему |
|---|---|---|
| Данных нет в названии | `Перф. DeWalt D 25134 K`, `Перфоратор HITACHI DH28PCY` | извлекать нечего — задача для парсера (Phase 1–5) |
| Название обрезано до потери значения | `…SDS plus, 3,` (45576), `…36V,2х1,3А/ч, Li-i` | не угадываем |
| `battery_included` для `1х4,0Ач+ЗУ` | 568, 577 | наличие ЗУ ≠ наличие АКБ; правило требует derive-логики, а не keyword. Атрибут `is_filter=false` — ценность низкая, риск ошибки выше выигрыша |
| **Мощность из модельного кода** | `ВИХРЬ П-900к`, `ИНТЕРСКОЛ П-26/800ЭР`, `РЕСАНТА П-30-900К`, `ЗУБР ЗПВ-32-1250` | **вопрос владельцу — см. §7** |

## 7. Что требует решения владельца

### 7.1. Правила пока НЕ задеплоены на стенд — есть риск отката

Изменённый `data/attribute_rules.json` лежит **локально в рабочей копии** и во
временном `/tmp/rules_v2` внутри контейнера. В образе стенда — старая версия файла.

**Следствие:** если кто-то запустит `python manage.py enrich_attributes` без `--path`,
движок не найдёт новых правил и **удалит 26 записанных значений** (штатная логика
prune: значения `regex`/`keyword`, которые движок больше не извлекает, чистятся).

Чтобы результат закрепился, правила нужно закоммитить в `dev` и задеплоить. Push и PR
делаю только по явной просьбе — жду решения.

### 7.2. Извлекать ли мощность из модельного кода?

~20 товаров без `power` содержат мощность в маркировке производителя:

| Схема | Примеры | Товаров |
|---|---|---:|
| ВИХРЬ `П-<Вт>к` | `П-1000к`, `П-650к`, `П-800к-в`, `П-1200к-м` | 7 |
| Интерскол `П-<Ø мм>/<Вт>ЭР` | `П-24/700ЭР`, `П-26/800ЭР`, `П-32/1100АВС` | 6 |
| Ресанта `П-<Ø>-<Вт>К` | `П-28-800К`, `П-30-900к`, `П-32-1400КВ`, `П-40-1600КМ` | 4 |
| ЗУБР `ЗПВ-<Ø>-<Вт>` | `ЗПВ-32-1250 ЭВК`, `ЗПМ-40-1100 ЭК` | 2–3 |

Это не извлечение факта из текста, а **декодирование маркировки**: числа не
сопровождаются единицей измерения, и правило будет верным ровно настолько,
насколько верна наша трактовка схемы конкретного бренда. Сам не делал — выходит за
рамки «докрутить regex точечно». Дало бы +~20 к `power` (133 → ~153) и снизило бы
число товаров без характеристик с 25 до ~7.

**Вопрос:** делаем отдельным раундом с обязательной поштучной сверкой по каталогам
производителей, или оставляем эти товары парсеру (Phase 1–5)?

### 7.3. Оставить ли keyword «sds» в правилах патрона

См. §3, докрутка 3: механизм ловит подстроку внутри артикула (`RSDS800K`). Оба
текущих попадания верны, но если предпочитаете чистоту матча — убираем, теряем 2 товара.

### 7.4. Правка `input-category.md`

Цифры Phase 0 о «188 товарах без единой характеристики» и «188 опубликовано» не
соответствуют базе (см. §0). Готов поправить документ по вашему слову.
