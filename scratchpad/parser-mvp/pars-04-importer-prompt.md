## РЕШЕНИЯ ВЛАДЕЛЬЦА (приняты, не пересматривать)

### 1. Новый источник `scraper` с приоритетом **50**

Сейчас в `source_priority`: `manual 100 · rules 90 · import_1c 60 · regex 40 ·
keyword 30 · web/marketplace 25 · llm 20 · inferred 10`.

`scraper = 50` ставится намеренно **между `import_1c`(60) и `regex`(40)**:

- **выше `regex`** — спецификация с сайта производителя авторитетнее числа,
  вытащенного regex'ом из обрезанного названия 1С. Мы весь трек видели, как regex
  ошибается: диапазоны у ключей, «ЗП-24 Д» → 24 Дж, число зубьев вместо диаметра;
- **ниже `import_1c`** — если 1С прислала характеристику явно, она главнее.

Завести `Source.SCRAPER` в модели (значение ≤ 12 символов), добавить в
`source_priority` и в карту уверенности источников. Миграция — неразрушающая.

### 2. `voltage` для сетевого инструмента **не заполнять**

Сейчас у перфораторов 17 значений `voltage`, и **все у аккумуляторных**
(14 · 14.4 · 18×8 · 20×2 · 24 · 36). Фасет решает реальную задачу — подбор
аккумуляторной платформы.

Если импортёр начнёт писать `220`/`230` из карточек сетевых моделей, фасет утонет:
под этими значениями окажется большинство товаров, и фильтр перестанет помогать
выбирать аккумулятор. Плюс разнобой 220 против 230 раздробит выборку.

**Правило: `voltage` пишется только для аккумуляторного инструмента.** Признак
определить явно (наличие `power_source=battery` или напряжение < 60 В) и записать
в отчёт.

## ПЕРВЫЙ ШАГ — ЗАМЕР ПЕРЕЗАПИСИ, ДО ЛЮБОЙ ЗАПИСИ

При `scraper=50` импортёр будет перезаписывать regex-значения. Прежде чем это
случится, нужно знать объём и направление.

Прогнать read-only сравнение по выгрузке и показать:

- сколько значений **совпадает** с существующими regex — подтверждение, изменений нет;
- сколько **расходится** — по каждому: товар, атрибут, было / стало, из какого поля
  источника;
- сколько ложится в **пустые** поля (это 55 перфораторов без `power` — основная
  цель затеи).

**Расхождения разобрать поимённо и вынести владельцу.** Молча перезаписывать
проверенные regex-значения нельзя: у перфораторов сейчас 133 значения `power`, все
`regex`, и мы их сегодня чистили.

Если расхождений окажется много (условно >10 % от совпадений) — **остановиться**
и доложить: возможно, ошибается не regex, а карта.

## ЗАДАЧА

Команда `catalog_import_scraped <json> --category <slug> [--dry-run] [--limit N]`.

### Матчинг — `(бренд, нормализованная модель)`

**Артикул ключом не использовать.** Установлено на Phase 1: `РСВ-140807` висит на трёх
разных товарах, 13 226 товаров вообще без артикула, у Интерскола 0/8 совпадений.
Артикул — только подтверждение уже найденного совпадения.

- бренд из названия (`brand_slugs.py`), модель — из **названия карточки, а не из URL**:
  на сайте ВИХРЯ `…p-1200k-m/` отдаёт карточку «П-1600К-М»;
- **подстрочное сравнение запрещено**: `ЗП-2680` — подстрока `ЗП-26-800`. Сравнивать
  только после нормализации и целиком;
- pg_trgm с порогом — для остатка;
- **неоднозначное совпадение и «многие к одному» — в отчёт, не в базу**
  (`П-800к` / `П-800к-в`, дубли URL Интерскола).

### Запись

- характеристики → `ProductAttributeValue` с `source="scraper"`, `confidence` из карты;
- перезапись решает `source_priority`: `manual`, `rules` и `import_1c` не затираются;
- **фотографии не берём** — решение владельца, источник это сайты производителей;
- транзакция на товар, а не на весь прогон;
- `--dry-run` печатает полный план **без единой записи**: сколько совпало, сколько PAV
  создастся, сколько перезапишется, сколько отброшено по приоритету;
- итоговая статистика + JSON-отчёт: `matched`, `ambiguous`, `not_found`,
  `unmapped_attributes`, `skipped_priority`, `overwritten`;
- `attrs_cache` пересобрать **точечно** по затронутым товарам.

### Тесты

Матчинг (включая запрет подстрочного), идемпотентность повторного прогона, защита
`manual`/`rules`/`import_1c`, правило `voltage` только для аккумуляторных, `scraper`
перезаписывает `regex` и не перезаписывает `import_1c`.

## ГЕЙТ-ЦИКЛ ДЛЯ РЕАЛЬНОГО ПРОГОНА

Сначала **только `--dry-run`** и замер. Реальная запись — отдельным шагом:
read-only → preflight → dry-run с предсказанием чисел → pg_dump → write → post-audit
(хэш неприкасаемых полей идентичен, дублей PAV нет, `attrs_cache` ≡ EAV) → витрина
живыми запросами.

**Сначала локально, staging — по отдельному GO владельца.**

## ГРАНИЦЫ

- Не трогать: цену, остаток, `code_1c`, `article`, дерево категорий, `name`,
  `tool_type` (его ставит только rules-engine), значения `source="manual"`.
- Новые `Attribute` / `AttributeOption` не создавать — несопоставленное в отчёт.
  Кандидаты (`impact_rate`, диаметры сверления, `cable_length`) — отдельным решением.
- `attribute_rules.json` править только в части `source_priority` — правила извлечения
  из названий не трогать.
- Контур `tool_type` (манифест, gate, ruleset) не трогать.
- Глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.
- Phase 5 (гейт-цикл на полном объёме) и Phase 6 не начинать.
