# PARS-03 · Парсер · карта характеристик источник → наш атрибут
# Проект «Профессионал», ветка dev. Общение только на русском.
# Ничего не пишется в БД — это Phase 4. Здесь только карта и её проверка.

## КОНТЕКСТ

Роадмап: `docs/plans/2026-07-26-PARSER_ENRICHMENT_MVP_ROADMAP.md`, Phase 3.
Вход: `parser/` (в git с PR #608) и выгрузка Phase 2 — 32 карточки с четырёх источников.
Структура источников: `docs/parser-mvp/source-structure.md`.

**Парсер намеренно отдаёт сырьё**: значения как есть, с исходными подписями полей.
Приведение к нашим атрибутам — задача этой фазы.

Что уже известно про источники (перепроверять не нужно):

| Особенность | Где |
|---|---|
| `power` **отсутствует структурно** — только в тексте описания «…900 Вт…» | resanta.ru |
| `power` есть отдельным полем «Мощность, Вт» | vihr.su |
| `motor_type` есть только здесь; `voltage` отсутствует | interskol.ru |
| в поле «Реверс» лежит «щеточный» — мусор данных, не тип двигателя | zubr.ru |
| «Вес, кг» — брутто с кейсом (4.926 при нетто 2.7) | resanta.ru, vihr.su |
| `no_load_speed` приходит диапазоном `0-1100` | все |
| `voltage` строкой `220-230В, ~50 Гц` / `230/50` | все |
| `chuck` в трёх написаниях | все |

## ЗАДАЧА

Построить `data/catalog_processing_rules/scraped_attr_map.<категория>.json` — карту
«поле источника → наш `Attribute`» с правилами нормализации.

Для каждой записи:

- источник и точное имя поля (или путь в JSON-LD / RSC-payload);
- целевой `Attribute` (**только существующие** — новые не создавать);
- правило нормализации: число + единица, десятичная запятая, регистр, синонимы;
- для `select`-атрибутов — сопоставление значений с существующими `AttributeOption`;
- `confidence` — насколько сопоставление надёжно;
- что делать при неоднозначности.

**Обязательные правила поведения:**

- **диапазоны — в отчёт, а не в базу.** Мы весь трек чистили каталог именно от значений,
  взятых из диапазонов: «Набор головок 10-32 мм» → `size=32` — размер, которого у
  инструмента нет. Не повторять эту ошибку на входе из источников;
- **вес брутто не сопоставлять с весом нетто** — либо отдельный атрибут, либо в отчёт;
- **«щеточный» из поля «Реверс» у ЗУБРа не сопоставлять с `motor_type`** — это мусор
  данных источника;
- всё несопоставленное — в `ignore` или в отчёт `unmapped`, никогда молча.

## ПРОВЕРКА КАРТЫ

- прогнать карту на выгрузке Phase 2 (32 карточки) и показать: сколько полей
  сопоставлено, сколько попало в `unmapped`, сколько отброшено правилами;
- **поштучно сверить результат нормализации** на выборке — не менее 30 значений,
  критерий отбора детерминированный, cherry-pick запрещён. По образцу Phase 0.5, где
  26 из 26 проверялись глазами;
- каждая запись карты обязана указывать на **реально существующий** `Attribute` —
  проверить запросом к БД (read-only).

**Готово когда:** карта покрывает ≥ 80 % характеристик источника по частоте, и каждая
запись указывает на существующий атрибут.

## ГРАНИЦЫ

- **В БД ничего не писать** — импортёр это Phase 4.
- Новые `Attribute` / `AttributeOption` не создавать; если для поля нет подходящего
  атрибута — в `unmapped` и вынести владельцу, не заводить самостоятельно.
- `data/attribute_rules.json` не трогать — это правила извлечения из названий, другая
  подсистема.
- Контур `tool_type` (манифест, gate, ruleset) не трогать.
- Парсер (`parser/`) менять только если выяснится, что он теряет нужное поле; такие
  правки — отдельным коммитом с объяснением.
- Глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены.
- Staging не трогать. Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.
- **Phase 4 (импортёр) не начинать.**

## ПРИЁМКА

- карта построена, каждая запись указывает на существующий `Attribute` — проверено;
- покрытие ≥ 80 % по частоте, цифра посчитана и показана;
- прогон на 32 карточках Phase 2: сопоставлено / `unmapped` / отброшено — с разбивкой;
- поштучная сверка ≥ 30 значений, критерий отбора записан, точность посчитана;
- диапазоны, вес брутто и «Реверс» ЗУБРа обработаны по правилам выше — показать на
  конкретных примерах;
- в БД ничего не записано;
- протокол `scratchpad/parser-mvp/phase3-report.md`;
- раздел «требует решения владельца»: поля без подходящего атрибута, спорные
  сопоставления, `source_priority` (regex=40 против marketplace=25 — понадобится
  на Phase 4).

## Что оркестратор будет проверять при приёмке

1. **Диапазоны не сопоставлены как значения** — это ровно та ошибка, которую мы весь
   день вычищали из каталога.
2. **Каждая запись карты указывает на существующий атрибут** — проверено запросом.
3. **Сверка не cherry-pick**, критерий воспроизводим.
4. **`unmapped` не пустой и осмысленный** — карта, где сопоставилось всё, обычно врёт.
5. **В БД ничего не записано.**
