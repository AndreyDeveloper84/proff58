## 1. A — сужение паттерна

```diff
   "regex": [
     "(\\d+(?:[.,]\\d+)?)\\s*(?:дж|дж\\.|джоул|joule)(?![а-яёa-z])",
-    "(\\d+(?:[.,]\\d+)?)\\s*(?:д|ж)(?![а-яёa-z0-9])"
+    "(\\d+[.,]\\d+)\\s*(?:д|ж)(?![а-яёa-z0-9])"
   ]
```

Мотив: усечённый паттерн предназначен для обрезанных 1С названий («…5,9Дж» приезжает
как «…5,9ж»). Целое число + кириллическая Д/Ж — это модельная маркировка, а не энергия
удара: «Перфоратор ЗУБР ЗП-24 Д» давал `energy_impact = 24 Дж`. На текущих 188 товарах
таких названий нет, но правило поедет на будущие поставки.

Все 4 реальных попадания усечённого паттерна дробные (5,9 / 2,9 / 3,5 / 1,9) — сужение
их не задевает. Полная форма по-прежнему выигрывает: порядок паттернов в правиле,
а не позиция в строке (движок берёт первый сработавший паттерн, `_extract_one`).

### Почему находка казалась настоящей

Статический поиск подтверждает вывод прогона: **в репозитории нет кода, который
пишет в `data/attribute_rules.json`.** Все обращения — на чтение
(`read_text` / `json.load`): `attribute_extract.py`, `provenance.py`,
`enrich_attributes`, `load_attributes`, `attribute_coverage`,
`catalog_seed_tool_type_filters`, `catalog_taxonomy_audit`. Тесты, которые пишут JSON,
пишут в `tmp_path`. `pytest-randomly` не установлен — порядок детерминированный,
«редкий тест при неудачном порядке» тоже исключён.

Наблюдавшийся симптом описан как «дописан regex в `energy_impact` и добавлена опция
`no_load_speed`». Это **дословно** содержимое коммита `10f7453` (PR #593):

```diff
-    "(\\d+(?:[.,]\\d+)?)\\s*(?:дж|дж\\.|джоул|joule)(?![а-яёa-z])"
+    "(\\d+(?:[.,]\\d+)?)\\s*(?:дж|дж\\.|джоул|joule)(?![а-яёa-z])",
+    "(\\d+(?:[.,]\\d+)?)\\s*(?:д|ж)(?![а-яёa-z0-9])"
   ]
 },
+{
+  "slug": "no_load_speed",
+  ...
```

То есть «грязь после pytest» была собственной незакоммиченной работой Phase 0.5,
замеченной в `git status` после долгого прогона и приписанной прогону. Это же
объясняет, почему работа «дважды терялась»: её принимали за мусор теста и откатывали.

Теперь работа закоммичена, и симптом исчез — что и подтверждает диагноз.

### Что осталось сделать

Ничего в коде. Действующее правило (формулировка владельца): **рабочая копия общая,
грязный `git status` может быть параллельным потоком — выяснять источник до
`git checkout`, стадировать точечно.**

## 5. Побочная находка: общая тестовая БД ловит дедлоки при параллельных прогонах

Второй и третий полные прогоны дали лишние падения, **каждый раз разные**:

| Прогон | Результат |
|---|---|
| 1-й (чистое дерево, я один на БД) | `2 failed, 1839 passed, 1 skipped` |
| 2-й | `2 failed, 1853 passed, 2 errors` — `test_processing_concurrency` |
| 3-й | `7 failed, 1848 passed, 2 errors` — `integration_max/test_availability_fanout` и др. |
| 4-й (изолированная тестовая БД) | **`2 failed, 1853 passed, 1 skipped`** ✅ |

Причина видна в трейсе 3-го прогона:

```
django.db.utils.OperationalError: deadlock detected
DETAIL: Process 16455 waits for ShareLock on transaction 539339; blocked by 16540.
        Process 16540 waits for ShareLock on transaction 539336; blocked by 16455.
CONTEXT: while inserting index tuple in relation "catalog_category_path_key"
(host=localhost user=proff database=test_proff58)
```

Два pytest-процесса работали в одной тестовой БД `test_proff58` (`--reuse-db` включён
в `pyproject`, имя БД фиксированное). Это то же самое свойство общей рабочей копии,
что и в §4, только на уровне БД.

Проверено: в изоляции `test_processing_concurrency.py` — `8 passed`; полный прогон на
отдельной БД (`DATABASE_URL=…/proff58_wt`, `--create-db`) — ровно два известных
окруженческих падения. **1853 = 1839 базовых + 14 новых тестов, регрессий нет.**
Временная БД `test_proff58_wt` удалена, `.env` worktree возвращён.

**Практический вывод:** при параллельных потоках гонять полный pytest на своей БД
(`DATABASE_URL` с другим именем + `--create-db`), иначе дедлоки читаются как регрессия.
