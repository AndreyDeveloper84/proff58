# PARS-02 · Парсер · активация режима B (закрытые источники)
# Проект «Профессионал». Общение только на русском.
# Требуется участие владельца: разовый вход в видимом окне браузера.

## КОНТЕКСТ

Phase 2 построила режим B (`parser/browser_client.py`): Playwright, persistent context +
`storage_state`, темп 5–10 с, лимит за прогон, остановка без ретраев при 403/429/челлендже,
без автоматического решения капчи. Код готов и покрыт тестами, но **не активирован**:
у нас нет сохранённой сессии.

Целевые источники — `vseinstrumenti.ru` и `dns-shop.ru`. Они отвечают 403/401 на обычный
запрос. Решение владельца: добирать оттуда недостающие карточки, потому что это
замещение ручного труда контент-менеджера, а не массовый обход каталога.

**Порядок работ зафиксирован:** сначала производители (режим A, уже работает, покрывает
~40 товаров из выборки Phase 1), закрытые источники — **только добор того, чего у
производителей нет**.

## ЗАДАЧА 1 — HEADED-BOOTSTRAP (с человеком, без него не начинать)

1. Подготовить и показать владельцу точную команду запуска в headed-режиме.
2. **Владелец сам** открывает окно, проходит челлендж, если он появится, и подтверждает,
   что видит нормальную страницу каталога.
3. Сессия сохраняется в `storage_state`; путь и содержимое (без секретов) зафиксировать
   в протоколе.
4. Проверить, что headless-режим на сохранённой сессии открывает карточку и получает
   HTTP 200.

**Капчу не решать программно** — ни своими силами, ни внешними сервисами. Если челлендж
появляется на каждом запуске и сессия не держится — это результат: доложить, а не
подбирать обходы.

## ЗАДАЧА 2 — РАЗВЕДКА СТРУКТУРЫ (после bootstrap)

Для каждого источника, на 2–3 карточках, **не больше**:

- где лежат характеристики: JSON-LD, microdata, HTML-таблица, JS-состояние;
- есть ли артикул производителя и в каком виде;
- как устроен листинг категории и пагинация;
- что из нужных нам полей отсутствует.

Зафиксировать в `docs/parser-mvp/source-structure.md` отдельным разделом — рядом с уже
описанными производителями, не переписывая их.

## ЗАДАЧА 3 — ИЗВЛЕКАТЕЛИ

Добавить извлекатели под структуру этих источников по образцу существующих четырёх.
Тесты — **на fixtures, без сети**, как в Phase 2.

## РЕЖИМ ДОСТУПА — жёстко

- темп **5–10 с между карточками**, никакого параллелизма;
- лимит за прогон: по умолчанию ≤ 100–150 карточек, параметром;
- **при 403 / 429 / челлендже — СТОП и доклад**, не цикл ретраев: срабатывание защиты
  означает неверный профиль работы;
- фотографии не берём;
- за разведку — единицы запросов, не десятки.

Профиль должен быть неотличим от работы человека: если он таким не получается — значит
задача решается не так, и это повод остановиться, а не ускоряться.

## ГРАНИЦЫ

- Режим A и извлекатели производителей не трогать — они приняты.
- В `apps/`, `config/`, `data/` ничего не менять; БД не трогать вообще.
- Phase 3 (карта характеристик) и Phase 4 (импортёр) не начинать.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.
- Учесть: `parser/` теперь **в git** (PR #608) — правки идут коммитами, а не поверх
  untracked-файлов.
