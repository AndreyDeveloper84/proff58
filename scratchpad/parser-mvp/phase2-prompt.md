## ДВА РЕЖИМА ДОБЫЧИ — решение владельца 2026-07-28

Источники делятся на две группы, и клиент должен поддерживать оба режима за общим
интерфейсом.

### Режим A — HTTP (основной, для сайтов производителей)

`resanta.ru`, `vihr.su`, `interskol.ru`, `zubr.ru` отдают всё обычным HTTP: на Phase 1
прошло 24 запроса, 23 × 200 и один 404 по своей ошибке, **ни одного отказа**. Здесь
браузер не нужен — тяжелее и хрупче без выигрыша.

### Режим B — браузер (добор недостающих карточек с закрытых источников)

`vseinstrumenti.ru` и `dns-shop.ru` на обычный запрос отвечают 403/401. По решению
владельца недостающие карточки добираются через браузер — это замещение ручного труда
контент-менеджера, а не массовый краулинг. Отсюда жёсткие правила профиля:

- **Playwright, persistent context + `storage_state`** — за образец взять
  `C:\Users\user\PycharmProjects\wb_p\monitoring\browser\client.py` (там же `config.py`):
  сохранение профиля и куки между запусками уже отлажено;
- **разовый headed-bootstrap**: первый запуск в видимом окне, челлендж при появлении
  проходит **человек**, сессия сохраняется. Дальше — headless на сохранённой сессии.
  **Автоматического решения капчи не делать** — ни своими силами, ни внешними сервисами;
- **человеческий темп**: 5–10 с между карточками, **никакого параллелизма**, лимит за
  прогон (по умолчанию ≤ 100–150 карточек, параметром);
- **при 403 / 429 / челлендже — СТОП и доклад.** Не «подождать `retry_after` и
  повторить»: если защита сработала, значит профиль неверный, и это решение владельца,
  а не задача цикла ретраев. Логику ожидания из `wb_p` здесь **не переносить**;
- режим B включается **только явным флагом** (`--mode browser`), по умолчанию — HTTP;
- фотографии не берём и в этом режиме тоже.

**Порядок работы:** сначала производители (режим A) — они покрывают ~40 товаров из
выборки Phase 1; закрытые источники (режим B) — только добор того, чего у производителей
нет, а не первичный обход каталога.

## ЗАДАЧИ (по роадмапу, Phase 2)

Модули складывать **вне `apps/`** — парсер не часть Django-проекта. Расположение
предложить и обосновать в отчёте (роадмап §4 «Архитектура»).

- [ ] `client.py`: общий интерфейс для обоих режимов (см. «Два режима добычи»).
      **Режим A (HTTP, по умолчанию):** таймаут 20 с, последовательные запросы, до
      3 ретраев с возрастающей задержкой, обработка 429 и 5xx, без ретраев на 4xx,
      троттлинг ≥ 2–3 с на хост, честный `User-Agent` с контактом.
      **Режим B (браузер, по флагу `--mode browser`):** Playwright с persistent context
      и `storage_state` (образец — `wb_p/monitoring/browser/client.py`), headed-bootstrap
      с ручным прохождением челленджа, темп 5–10 с между карточками, лимит за прогон,
      **остановка и доклад при 403/429/челлендже вместо ретрая**.
- [ ] `schemas.py`: pydantic-схемы карточки и выгрузки, валидация URL, очистка строк.
- [ ] `product.py`: сначала JSON-LD, HTML-селекторы только для недостающего.
      Для `interskol.ru` — отдельный извлекатель RSC-payload. Обязательные поля —
      `source_url`, `name`; товар без них отклоняется.
- [ ] `category.py`: `collect_product_urls(source, limit)` — **из sitemap** у Ресанты,
      ВИХРЯ и Интерскола; для ЗУБРа — обход от корня (дерево 284 категорийных ссылок).
      Дедуп, сохранение порядка, потолок страниц.
      Интерскол: **один товар живёт под несколькими URL** (`/product/…`, `/catalog/…`,
      `…-copy`) — дедуплицировать.
- [ ] `main.py`: CLI (`--source`, `--category-url`, `--limit`, `--output`,
      `--errors-output`), атомарная запись через `.tmp` + rename, ошибки отдельным
      файлом, статистика.
- [ ] Тесты на fixtures из Phase 1 — **без сети**.

**Готово когда:** одна команда даёт валидный JSON минимум по 20 карточкам.

## РЕЖИМ ДОСТУПА — обязателен, важнее скорости

- соблюдать `robots.txt` каждого источника;
- **не чаще 1 запроса в 2–3 секунды на домен**, никаких параллельных потоков на хост;
- честный `User-Agent` с контактом, не маскировка под браузер;
- кэш скачанного, повторно не запрашивать;
- при 429/403/401 — **остановиться и доложить**, обходы не подбирать.

На Phase 1 это соблюдалось образцово (24 запроса, 3 с/хост, ни одного отказа) — планку
не снижать. Мы гость на сайте производителя, и агрессивный парсер закроет нам
единственный оставшийся законный источник.

## ЧЕГО НЕ ДЕЛАТЬ

- **Не писать импортёр и не трогать БД** — это Phase 4. Здесь только парсер и JSON.
- Не строить карту характеристик — это Phase 3.
- Фотографии не скачивать.
- В `apps/` ничего не менять; глобальные команды (`enrich_attributes` без `--path`,
  `rebuild_attrs_cache`) запрещены.
- Staging не трогать. Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`: там фронтенд-команда, а деплой делает `git reset --hard`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` только точечными путями.

## ЧТО УЧЕСТЬ ИЗ РАЗВЕДКИ (вход для Phase 3, не чинить здесь)

Нормализация понадобится, но карта значений — следующая фаза. Просто не терять данные:

- `no_load_speed` приходит диапазоном (`0-1100`);
- `voltage` строкой (`220-230В, ~50 Гц`, `230/50`), у Интерскола отсутствует;
- `chuck` в трёх написаниях;
- `power` **структурно отсутствует у Ресанты** — только в тексте описания
  («…900 Вт…»); у ВИХРЯ поле «Мощность, Вт» есть;
- `motor_type` есть только у Интерскола; у ЗУБРа в поле `Реверс` лежит «щеточный» —
  это мусор данных, не тип двигателя;
- «Вес, кг» у Ресанты и ВИХРЯ — брутто с кейсом (4.926 при нетто 2.7).

Парсер должен отдавать **сырое значение как есть** плюс исходную подпись поля.
Приведение к нашим атрибутам — Phase 3.

## Что оркестратор будет проверять при приёмке

1. **Ни одного обращения к БД** — парсер вне Django, это его определяющее свойство.
2. **Троттлинг соблюдён** — по логу видно паузы; в режиме B темп 5–10 с и лимит за прогон.
3. **Режим B не включается по умолчанию** и не решает капчу автоматически; при
   403/429/челлендже — остановка с докладом, а не цикл ретраев.
3. **Тесты гоняются без сети** — иначе они не тесты, а повторная разведка.
4. **Сырые значения сохранены с подписями полей** — иначе Phase 3 не на чем строить.
5. **Дедупликация Интерскола работает** — один товар не приезжает трижды под разными URL.
