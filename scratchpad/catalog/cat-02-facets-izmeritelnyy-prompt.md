# CAT-02 · Каталог · фасеты length/size для измерительного инструмента
# Проект «Профессионал», ветка dev. Общение только на русском.
# WRITE по каталогу — по гейт-циклу. Локально, затем staging.

## КОНТЕКСТ

CAT-01 установила: у уровней и угольников **данные уже есть и корректны** — 169 значений
`length` и 93 `size`, все с `source=regex`, сверка 136/136 = 100%. API по ним фильтрует
(уровни 159 → 31 при `length ≥ 1000`, сходится с БД), карточка показывает «Длина 400 мм».

**Но покупатель фильтра не видит:** в цепочке категорий `izmeritelnyy/*` заведён
`CategoryAttribute` только для `tool_type`. Панели `length`/`size` в фасетах нет.

То есть работа сделана и не доходит до пользователя. Это и надо закрыть.

## ЗАДАЧИ

### 1. Разобраться в модели показа (read-only)

- как устроен `CategoryAttribute`: что определяет попадание атрибута в фасет-панель,
  порядок, заголовок;
- что уже заведено в цепочке `izmeritelnyy/*` и в соседних разделах, где фасеты
  работают (например, `elektroinstrument` — там `chuck`, `power` отдаются панелью);
- как фасеты собираются в `attrs_cache` и что придётся пересобрать после изменения.

**Взять за образец работающий раздел**, а не изобретать конфигурацию.

### 2. Определить полный набор, а не только length/size

Посчитать по товарам измерительных типов, какие управляемые атрибуты реально заполнены
и с каким покрытием. Завести в фасеты те, где покрытие осмысленное — критерий предложить
и обосновать в отчёте (например, ≥ 20 товаров и ≥ 15% типа). Не заводить атрибут, у
которого два значения на весь раздел: пустая панель хуже отсутствующей.

Отдельно проверить `no_load_speed` — у него `is_filter=false`, он в фасеты не идёт
намеренно; не менять это без отдельного решения.

### 3. Гейт-цикл

1. **Read-only** — что есть сейчас, что появится, отпечаток каталога ДО.
2. **Preflight** — не заденем ли чужие настройки показа в соседних категориях.
3. **Dry-run** — список создаваемых `CategoryAttribute` с числами: сколько товаров
   получат панель, сколько значений в каждом фасете. Ожидание сформулировать ДО.
4. **pg_dump** + снимок отката.
5. **Write** — одной транзакцией.
6. **Post-audit** — `attrs_cache` пересобрать **точечно** по затронутым товарам
   (глобальный `rebuild_attrs_cache` запрещён); хэш неприкасаемых полей идентичен;
   дублей `CategoryAttribute` нет.

### 4. Проверить витрину живыми запросами — обязательно

Не «должно работать», а показать: фасет отдаётся, значения и счётчики совпадают с БД,
фильтр отсекает выборку. Проверить и API, и страницу категории. Приложить конкретные
запросы и ответы.

**Задача не считается выполненной, пока панель не видна на витрине.**

### 5. Сделать на staging

Локально — сначала, staging — следом, отдельным pg_dump. Именно на стенде это увидит
владелец.

## ГРАНИЦЫ

- Новые `Attribute` / `AttributeOption` не создавать — только связи показа.
- Значения характеристик не трогать: CAT-01 показала, что они корректны.
- `is_filter` у атрибутов не менять без отдельного решения.
- Контур `tool_type` не трогать; дерево категорий не перестраивать.
- Глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.

## ЗАВИСИМОСТЬ

На staging параллельно может идти прогон словаря (`TT-04`: remap `hoz-*`, миграция 0027,
seed `izm-areometry`). Обе задачи трогают `attrs_cache` — **одновременно не запускать**,
координировать post-audit.

## ПРИЁМКА

- фасет-панель `length`/`size` (и остальных отобранных атрибутов) видна на витрине —
  доказано живыми запросами, с числами;
- критерий отбора атрибутов записан и обоснован;
- гейт-цикл пройден локально и на staging, pg_dump снят;
- хэш неприкасаемых полей идентичен до и после;
- `attrs_cache` пересобран точечно, глобальные команды не запускались;
- протокол `scratchpad/catalog/cat-02-report.md`.
