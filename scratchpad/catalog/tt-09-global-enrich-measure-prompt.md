# TT-09 · Каталог · что сделал бы глобальный прогон, если бы `manual` не мешал
# Проект «Профессионал», ветка dev. Общение только на русском.
# ЭТО READ-ONLY ОКНО. Ни одной записи в БД, ни одной правки в data/.

## ЗАЧЕМ ЭТО НУЖНО

`tool_type` в каталоге: **38 833 значения, из них 38 781 с `source=manual`** и 52 с
`web`. У всех manual `confidence=100`, и у модели `ProductAttributeValue` **нет полей
дат** — то есть в данных нет ничего, что отличало бы «скрипт массового распределения
проставил по умолчанию» от «куратор решил по этому товару». Снятие `manual` может быть
только тотальным, включая 305 значений, аккуратно проставленных TT-08, и работу
CAT-01/CAT-06.

Одновременно `manual`(100) — это защита: `can_overwrite`
(`apps/catalog/provenance.py:49-56`) требует для авто строго `priority(new) >
priority(existing)`, и она единственная стоит между автоматикой и 38 тысячами значений.

Прежде чем её трогать, надо знать: **что именно автоматика хочет сделать с каталогом.**

## ЗАДАЧА 1 — предложения движка по всему каталогу

Прогнать **proposal-only** контур (`catalog_rules_shadow` — по контракту ничего не
пишет в БД; убедиться в этом чтением кода, а не по названию) по всем товарам, а не по
выборке. Получить полный список предложений `product_id → предлагаемый tool_type`.

Разложить на классы:

| Класс | Что это |
|---|---|
| **пусто → предложение** | у товара нет `tool_type`, движок предлагает |
| **совпадение** | предложение совпадает с тем, что уже стоит |
| **расхождение** | предложение отличается от текущего — вот это и есть цена вопроса |
| **нет предложения** | движок промолчал, товар остаётся как есть |

По каждому классу — число и доля. **Ключевая цифра всей задачи — размер класса
«расхождение»**: ровно столько значений изменилось бы, если снять `manual`.

## ЗАДАЧА 2 — анатомия расхождений

Для класса «расхождение» показать:

- разбивку **откуда → куда** (топ-30 пар `текущий тип → предлагаемый`), с числами;
- сколько из них **опубликованных** товаров — это те, что увидит покупатель;
- по каким категориям расходится сильнее всего;
- сколько расхождений приходится на типы, заведённые недавно (`gaikoverty`, `bp-leska`,
  `gaikoverty-ruchnye`, `svar-katody`, `zap-boyki`) — там движок может быть прав, а
  текущее значение устарело.

## ЗАДАЧА 3 — кто прав: ручная проверка выборки

Цифры сами по себе не говорят, хорошее это изменение или порча. Поэтому:

- взять **случайную выборку 50 расхождений** (фиксировать seed, чтобы воспроизводилось);
- по каждому глазами определить, кто прав: движок, текущее значение или **оба неверны**;
- посчитать долю. Это оценка точности, и она решает всё: при 90 % правоты движка снятие
  `manual` — улучшение, при 60 % — порча каталога.

**Не подбирать удобную выборку.** Случайная, с фиксированным seed, весь результат
в протокол — включая случаи, где движок ошибся.

## ЗАДАЧА 4 — то же для характеристик (побочно, короче)

`enrich_attributes` с `--dry-run` по нескольким крупным категориям (не глобально):
сколько значений он создал бы в пустые поля, сколько переписал бы существующие.
Здесь достаточно порядка величин — главный предмет окна это `tool_type`.

Напомню известное: прошлый глобальный замер показал `PLAN_CREATE=40` по типам, о
которых решения не было. Проверить, изменилось ли это.

## ЗАДАЧА 5 — варианты для владельца

Свести к 3–4 вариантам с ценой и риском каждого, например:

- ничего не менять — цена: каталог не улучшается автоматически;
- снять `manual` целиком и прогнать — цена: N значений изменится, из них M у
  опубликованных, точность движка P %;
- снять `manual` **послойно** — если найдётся признак, отделяющий массовый слой
  (например, товары, никогда не попадавшие ни в одну операцию окон);
- не трогать `manual`, а разбирать точечно recat-операциями, как TT-08 и CAT-09 —
  цена: медленно, зато каждый шаг обратим и проверен.

**Рекомендацию дать, решение не принимать.**

## ГРАНИЦЫ

- **Read-only.** Ни `enrich_*` без `--dry-run`, ни `catalog_taxonomy_apply`, ни правок
  `data/`, ни изменения `source` у единого значения.
- **`provenance.py` не трогать** — ни строки, даже «на попробовать».
- Контур `tool_type` (манифест, gate, ruleset, артефакты) не менять.
- Новые типы не заводить.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — `git fetch gitlab --prune` и сверка `origin/dev`
  с `gitlab/dev`. С шестой синхронизации команда GitLab возит и бэкенд.
- Рабочая копия общая: чужие изменения не откатывать.
- Параллельно работают **CAT-08** (чистка названий) и **CAT-09** (recat кластеров) —
  оба пишут на staging. Ваше окно не пишет, поэтому конфликта нет, но при сверке чисел
  учитывайте, что каталог под вами меняется: фиксируйте момент замера и, если числа
  «поплывут», объясняйте это чужими операциями, а не списывайте молча.
- На стенде `FEATURE_CATALOG_PROCESSING` выключен — команды контура вызывать с `-e`.
