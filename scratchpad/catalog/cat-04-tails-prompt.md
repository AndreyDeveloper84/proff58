## ЗАДАЧА 1 — довести CAT-03 до покупателя (первым делом)

1. Проставить `display_name` на **staging**: у `izmeritelnyy-ugolniki-i-lineyki`
   атрибут `size` → «Размер». Остальные привязки `size` (ключи, головки) — без
   переопределения.
2. Проверить **живыми запросами** обе страницы: угольники отдают «Размер», ключи —
   «Размер «под ключ»». Приложить запросы и ответы.
3. Baseline «до» снят в CAT-03 — сверить, что изменилось ровно ожидаемое.

Это одна запись плюс проверка, но именно она превращает CAT-03 из «механизм готов»
в «покупатель видит».

## ЗАДАЧА 2 — хвосты значений

**`CREATE=4`** — дельта по `nozhovki` (2), `pilki-polotna` (1), `vorotki` (1):
правила извлекают значения, которых в БД нет. Сверить каждое глазами (их четыре),
затем записать scoped-прогоном через `--path`.

**`PRUNE=17`** — значения, которые движок больше не извлекает после починок правил.
Проверить, что это действительно последствия наших правок (`size`, `diameter`,
`disc_diameter`, `motor_type`), а не что-то иное, и удалить в том же цикле.

Предсказать числа **до** прогона и сверить после — как во всех предыдущих циклах.

## ЗАДАЧА 3 — классификация в `izm-ugolniki`

CAT-01 заметила: в тип «Угольники и линейки» попали **фитинги и абразивы**. Это уже не
подпись, а неверный `tool_type` у товаров.

Разобрать: сколько таких, какие это товары, какой тип им подходит. **Ничего не менять** —
`tool_type` ставит только rules-engine, и переклассификация идёт через контур Phase 8.
Задача здесь — измерить и описать, чтобы стало входом для батча.

## ЗАДАЧА 4 — атрибуция записи 262 значений

CAT-01 установила: 169 `length` и 93 `size` лежат в БД с `source=regex`, но отдельного
прогона под эти типы в истории нет — последний `ImportRun` id=42. Либо это глобальный
прогон 2026-06-29, либо **запись мимо `ImportRun`**.

Выяснить по данным: сопоставить `created_at` значений с историей прогонов, проверить,
есть ли в коде пути записи PAV без регистрации `ImportRun`.

Если найдётся путь записи в обход аудита — **это находка уровня P1**, доложить отдельно,
не чинить в этой задаче.

## ГЕЙТ-ЦИКЛ (для задач 1 и 2)

read-only с отпечатком → preflight → dry-run с предсказанием → pg_dump → write одной
транзакцией → post-audit (хэш неприкасаемых полей идентичен, дублей нет,
`attrs_cache` ≡ EAV) → витрина живыми запросами.

Локально, затем staging.

- `tool_type` не менять — ни у одного товара (задача 3 только измеряет).
- Новые `Attribute` / `AttributeOption` не создавать.

  извлечения, это отдельная задача.
- Глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены;
  кэш пересобирать точечно.
- Контур `tool_type` (манифест, gate, ruleset) не трогать.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.
- На стенде `FEATURE_CATALOG_PROCESSING` выключен — если понадобятся команды контура
