## КОНТЕКСТ

Ступень 3 Phase 8 дала 8 отказов в `needs_review`, и часть из них — **дыры словаря**,
названные поимённо: катоды и электроды плазмотронов, ручные гайковёрты, бойки и
ударники. Пока этих типов нет, ступень 4 (batch 50) упрётся в те же места, и замер
покажет не качество матчера, а состояние таксономии — ровно как было на ступени 2 с
ареометрами.

**Почему пакетом.** Каждое изменение манифеста меняет `taxonomy_identity_hash` и требует
re-gate с перепривязкой gate-артефактов. Три отдельные задачи = три re-gate. Один пакет =
один. Процедура отработана в TT-01, повторяем её.

Текущее состояние: **329 опций**, `taxonomy_identity_hash = 524d4e31…`,
release `canonical_hash = 2929eccd…`, `reconcile` → `blocking = 0` локально и на стенде.

## ЗАДАЧА 1 — ПОДГОТОВИТЬ СОСТАВ И ВЫНЕСТИ ВЛАДЕЛЬЦУ (до правки манифеста)

**Типы заводит владелец, не окно.** Сначала предложение, потом утверждение, потом правка.

По каждому кандидату подготовить:

- предлагаемый `slug` и `value` (в стиле существующих 329: префиксы `izm-`, `krep-`,
  `bp-`, `hoz-` и т. д. — посмотреть соседей и не выбиваться);
- **обоснование, почему не подходит ни один из существующих 329** — перебрать
  родственные и показать, чем они отличаются. Именно так делалось для `izm-areometry`,
  где были перебраны все 17 `izm-*`;
- сколько товаров каталога получат этот тип (оценка по названиям, read-only);
- какие товары из `needs_review` ступени 3 он закрывает.

Кандидаты из ступени 3: **катоды/электроды плазмотронов**, **ручные гайковёрты**,
**бойки/ударники**. Если по ходу выяснится, что какой-то из них покрывается существующим
типом — так и написать: отказ с обоснованием ценнее лишней опции.

**Остановиться и дождаться утверждения состава.** Только после него — задача 2.

## ЗАДАЧА 2 — МАНИФЕСТ И RE-GATE (после утверждения)

1. Добавить утверждённые опции в `data/catalog_processing_rules/tool_type_taxonomy.v1.json`
   с метаданными по образцу соседей (`origin_kind`, `origin_ref`,
   `review_status=approved`, `review_ref=tt-07`).
2. Пересчитать `taxonomy_identity_hash` и `manifest_semantic_hash`, зафиксировать оба.
3. **Перепривязать gate-артефакты**: `phase7d-gate-sample-official.json`
   (`taxonomy_hash`) и `phase7d-labels.json` (производный `sample_hash`).

   **КЛЮЧЕВОЕ ТРЕБОВАНИЕ: разметку НЕ переразмечать.** Диф по обоим артефактам обязан
   быть **ровно две строки**. `rows=103`, `correct=102`, `unverifiable=1` не должны
   сдвинуться. Множество `product_id`, ground truth, `decision`, `rationale`,
   `reviewer_id`, `reviewed_at` — идентичны. Подгонка labels под ruleset — тот самый
   дефект доверия, ради которого затевалась волна 7.1.
4. Перевыпустить release manifest **тем же коммитом**, `--check` → ok.
5. Прогнать гейт **без поблажки**: `gate_passed=true`, EXIT=0, флаг
   `--allow-legacy-taxonomy-hash` в CI не возвращать (защищено guard-тестом).
6. Обновить документацию, где зафиксирован старый хэш: `CLAUDE.md` §7 и
   `docs/catalog/*` — сейчас там `524d4e31…`.

## ЗАДАЧА 3 — SEED НА ОБЕИХ БД

## ГРАНИЦЫ

- **Типы не заводить самостоятельно** — только по утверждённому составу.
- Не менять `value` существующих опций: идентичность поедет ещё раз.
- Не трогать matcher (`evaluate_product`, `facts_hash`), ruleset v2, applied corpus.
- Ступень 4 (batch 50) не начинать — она следующая, после этой.
- Глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены.
- Push и PR — только по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.
- На стенде `FEATURE_CATALOG_PROCESSING` выключен — команды контура вызывать с `-e`,
  конфиг стенда не менять.
- Regression — на отдельной БД (`--create-db`, `-p no:pylama`), без длинных немых
  команд; baseline сверить самостоятельно на актуальном дереве.
