# CAT-01 · Каталог · дозапись length у уровней и size у угольников
# Проект «Профессионал», ветка dev. Общение только на русском.
# WRITE по каталогу — строго по гейт-циклу.

## КОНТЕКСТ

Блокер `PLAN_CREATE=40` держался с 2026-07-27. Он замерялся **до** четырёх PR с
починкой правил (`size`, `motor_type`, `skip_if`, `diameter`, `disc_diameter`), поэтому
цифра устарела. Оркестратор пересчитал дельту зеркалом логики `enrich_attributes`
(своего `--dry-run` у команды нет) на локальной БД, 12 889 товаров с `tool_type`:

| | Значение |
|---|---|
| **PLAN_UPDATE** | **0** — ни одно существующее значение не перезаписывается |
| PLAN_CREATE | 263, из них опубликованных 180 |
| PLAN_PRUNE | 347 |

Состав `CREATE`:

| Атрибут | Всего | Опубл. | tool_type |
|---|---:|---:|---|
| `length` | 169 | 118 | `izm-urovni` |
| `size` | 68 | 41 | `izm-ugolniki` |
| `no_load_speed` | 17 | 16 | `perforatory` |
| `energy_impact` / `motor_type` / `chuck` | 9 | 5 | `perforatory` |

Последние 26 — дельта Phase 0.5, **на staging уже применена** (локальная БД отстаёт).
`PRUNE=347` — последствия наших же починок правил, на staging **уже отработаны**
гейт-циклами (249 + 70 + 11 = 330).

**Вывод: глобальный прогон не нужен.** Реальная новизна — 237 значений в двух типах:
уровни и угольники. Работаем scoped.

⚠️ Замер оркестратора — **локальный**. Числа на staging могут отличаться, и решение
исполняется именно там. Первый шаг задачи — перемерить на staging.

## ЗАДАЧИ

### 1. Перемерить дельту на staging (read-only)

Тем же способом — зеркалом логики команды, с `--path` на актуальный словарь. Получить
`CREATE` / `UPDATE` / `PRUNE` с разбивкой по атрибутам и `tool_type`, отдельно
опубликованные. **Сверить с локальными числами и объяснить расхождение**, если оно есть.

Если на staging `UPDATE > 0` — **остановиться и доложить**: значит правила перезаписывают
существующие значения, и это меняет характер задачи.

### 2. Поштучная сверка выборки — обязательна

По образцу Phase 0.5, где 26 из 26 значений сверялись глазами. Здесь объём больше,
поэтому:

- **все значения `size` у угольников** (68) — сверить полностью;
- **выборка `length` у уровней** — не менее 40 из 169, отбор детерминированный
  (каждый N-й по `id`), **cherry-pick запрещён**;
- по каждому проверенному: название → извлечённое значение → верно/неверно.

Ожидаемая ловушка: у уровней `length` — это длина корпуса («Уровень 600 мм» → 600), но
в названии могут быть и другие числа (количество глазков, ширина). У угольников `size` —
длина стороны. Если точность окажется ниже ~95%, **не применять**: доложить и предложить
правку правил отдельной задачей.

### 3. Гейт-цикл — только по двум типам

Scope: `izm-urovni` и `izm-ugolniki`. Перфораторы не трогать — там дельта уже применена.

1. **Read-only** — отпечаток каталога ДО (`code_1c`, `article`, `name`, `category_id`,
   `price`, `stock_quantity`, `status`, `is_active`, slug опции `tool_type`).
2. **Preflight** — нет `content_locked`, нет `manual`-значений среди управляемых
   атрибутов в scope.
3. **Dry-run** — план с точными числами; ожидание сформулировать ДО прогона и сверить.
4. **pg_dump** — после dry-run, до записи; плюс rollback-map (снимок PAV в scope).
5. **Write** — одной транзакцией, scoped, через `--path`.
6. **Post-audit** — repeat-preview = 0; дублей PAV нет; `attrs_cache` сходится с EAV;
   хэш неприкасаемых полей идентичен до и после; `attrs_cache` пересобрать **точечно**
   по затронутым товарам.

### 4. Проверить витрину

`length` и `size` — фильтруемые атрибуты. После записи проверить живыми запросами, что
фасеты по уровням и угольникам отдают значения и фильтры отсекают выборку. 159
опубликованных товаров получат новые значения — это видно покупателю.

## ГРАНИЦЫ

- **Глобальный `enrich_attributes` (без `--path`) запрещён** — работаем scoped.
- `rebuild_attrs_cache` глобально запрещён — только точечная пересборка.
- Правила не править: если сверка покажет ошибки извлечения, это отдельная задача.
- Новые `Attribute` / `AttributeOption` не создавать.
- `source_priority` не трогать.
- Контур `tool_type` не трогать: matcher, ruleset, манифест, артефакты гейта.
- Staging — только по гейт-циклу с pg_dump; push и PR — по явной просьбе владельца.
- **Перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`.
- Рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями.

## ЗАВИСИМОСТЬ ОТ ДРУГИХ ОКОН

Одновременно идут `TT-01`…`TT-03` (словарь `tool_type`). Они меняют **опции типов**, эта
задача пишет **значения характеристик** — пересечения нет, но обе трогают `attrs_cache`.
Если та цепочка в работе, координировать post-audit.

## ПРИЁМКА

- дельта на staging перемерена, расхождение с локальными числами объяснено;
- `UPDATE = 0` подтверждён на staging (иначе остановка и доклад);
- сверка: все 68 `size` у угольников + ≥ 40 `length` у уровней, критерий отбора записан,
  точность посчитана;
- гейт-цикл пройден: pg_dump снят, dry-run сверен с предсказанием, post-audit чистый;
- хэш неприкасаемых полей идентичен до и после;
- витрина проверена живыми запросами;
- протокол `scratchpad/catalog/cat-01-report.md`;
- раздел «требует решения владельца» — если точность ниже порога или всплывёт новое.
