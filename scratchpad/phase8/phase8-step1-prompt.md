ЗАДАЧА
Прогнать контур research-queue **end-to-end на пяти фиктивных cases** и доказать, что
он ведёт себя как заявлено, ДО того как в него попадёт хоть один реальный товар.

Цикл: `catalog_queue_create` → `catalog_queue_export` → обработка (скилл
`catalog-research`) → `catalog_queue_import` → `catalog_queue_status` →
`catalog_queue_finalize`.

Что обязано быть доказано:
1. batch создаётся и экспортируется **детерминированно** (повторный экспорт — байт в
   байт тот же файл; сверить sha256);
2. импорт валидирует результат **дважды**: по JSON-схеме и по домену/таксономии —
   `tool_type` вне canonical manifest обязан отвергаться;
3. findings попадают в модерацию, а не в каталог: **apply — отдельная авторизация**;
4. повторный импорт того же файла идемпотентен (не плодит дубли);
5. **отмена batch не меняет каталог ни на байт** — ключевой инвариант роадмапа.
   Доказывать снимком: хэш неприкасаемых полей (`code_1c`, `article`, `name`,
   `category_id`, `price`, `stock_quantity`, `status`, `is_active`, slug опции
   `tool_type`) до и после — как это делалось в H4/H5 и в гейт-цикле трека 2.

НЕГАТИВНАЯ МАТРИЦА — планка задана волной 7.1, ниже не опускаться
Минимум: битый JSON; результат, не проходящий схему; `batch_id`, не совпадающий с
именем файла; чужой/несуществующий batch; `tool_type`, которого нет в манифесте;
`product_ref`, отсутствующий в batch; повторный импорт; импорт в отменённый batch;
finalize без импорта; попытка apply без авторизации. Каждый сценарий — ожидаемый код
выхода и отсутствие записи в каталог. Испорченные артефакты создавать только во
временных каталогах.

ГРАНИЦЫ — жёстко
- **Ни одного реального товара.** Только синтетика, которую невозможно спутать с
  каталогом (явные маркеры в названиях, отдельные идентификаторы).
- **Ничего не применять к каталогу.** Apply — отдельное решение владельца, не в этой
  ступени.
- **Контур `tool_type` не трогать**: matcher (`evaluate_product`, `facts_hash`),
  ruleset v2, applied corpus, canonical manifest, артефакты гейта. Он принят.
- **Глобальные команды запрещены**: `enrich_attributes` без `--path`,
  `rebuild_attrs_cache`. Отдельный незакрытый блокер: dry-run по всему словарю даёт
  `PLAN_CREATE=40` по другим `tool_type`, решения владельца нет.
- Работать **локально**. БД staging не трогать; если для чего-то нужен стенд — только
  read-only и с явного GO владельца, по гейт-циклу.
- Push и PR — только по явной просьбе владельца.
- Рабочая копия общая: незнакомое изменение отслеживаемого файла НЕ откатывать
  (`git checkout --` по чужому файлу запрещён), стадировать точечными путями,
  никогда `git add -A`.
- Полный regression гонять на отдельной БД (`--create-db` + свой `DATABASE_URL`):
  при параллельных прогонах `DeadlockDetected` читается как регрессия.

## Что оркестратор будет проверять при приёмке

1. **Синтетика действительно синтетическая** — ни один реальный `product_id` не попал
   в batch. Это первое, что проверяется.
2. **Инвариант отмены доказан хэшем**, а не декларацией «каталог не тронут».
3. **Негативные сценарии проверены обеими сторонами** там, где есть guard: тест обязан
   падать при искусственном снятии проверки.
4. **Детерминированность экспорта** подтверждена повторным прогоном и сравнением sha256.
5. Арифметика regression от baseline 1941.
