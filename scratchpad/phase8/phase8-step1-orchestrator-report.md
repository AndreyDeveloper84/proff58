# Phase 8 / ступень 1 — отчёт для оркестратора

**Проект:** «Профессионал» (Django + DRF, каталог электро/ручного инструмента).
**Контур:** research-queue — очередь исследования каталога
(`catalog_queue_create|export|import|status|finalize` + модерация `CatalogChange`).
**Ступень:** Phase 8, ступень 1 — synthetic batch, 5 фиктивных cases.
**Дата:** 2026-07-27. **Ветка:** `dev`, локальный HEAD `3f50376`.
**Статус: ВЫПОЛНЕНА.**

---

## 1. Итог одной строкой

Контур research-queue прогнан end-to-end на пяти синтетических cases в
изолированной БД-песочнице: полный цикл create → export → обработка → import →
status → finalize пройден с EXIT=0 на каждом шаге, негативная матрица (17+
сценариев) пройдена целиком, шесть guard'ов доказаны мутационно, инвариант
«отмена batch не меняет каталог» доказан хэшем неприкасаемых полей до/после,
regression без третьего падения. Каталог за всю ступень не изменился ни разу —
один и тот же отпечаток на 15 независимых снимках. Найдено 6 отклонений
контракта от реализации (G1–G6); два из них требуют решения владельца до
первого commit на реальных данных.

## 2. Зачем ступень существовала

Роадмап (`docs/plans/2026-07-16-CATALOG_RESEARCH_QUEUE_ROADMAP.md` §Phase 8)
ставит synthetic batch первым шагом пилота именно затем, чтобы контур доказал
заявленное поведение **до** того, как в него попадёт хоть один реальный товар.
Ключевой инвариант роадмапа (§«Архитектурные инварианты», п. 12) — «любой batch
можно отменить без изменения каталога» — до этой ступени существовал как
декларация и юнит-тесты, но не как сквозное доказательство на живом цикле.

## 4. Синтетика — первое, что проверяется

Сид (`scratchpad/phase8/seed_synthetic.py`) **отказывается работать**
(`SystemExit`), если в БД есть хоть один товар без префикса `PH8-SYN`.
Создано 8 фиктивных товаров в категории-маркере `PH8-SYN SANDBOX (не каталог)`:
1–5 — cases batch, 6–8 — «свидетели» вне batch. Маркер продублирован в
`code_1c`, `article`, `name`, `original_name`, `source_group`.

Машинная проверка по всем выгруженным export-файлам:
`ВСЕ EXPORTED ITEMS СИНТЕТИЧЕСКИЕ: True` (у каждого item `code_1c` и `article`
начинаются с `PH8-SYN`, `name` и `source_group` содержат `PH8-SYN`).
Evidence в result-файлах — только домен `synthetic.invalid` (RFC 2606,
нерезолвимый): synthetic-прогон невозможно выдать за реальный research.

## 6. Инвариант отмены — доказательство, а не декларация

Отпечаток = SHA-256 канонической проекции ВСЕХ товаров песочницы по полям
`code_1c, article, name, category_id, price, stock_quantity, status, is_active`
+ slug опции `tool_type` из `ProductAttributeValue`.

```
ДО отмены   8a2dab32fc27754c6b3bb7c98cbe0cf93f2221505ef957ac7b1409299c93243c
ПОСЛЕ отмены 8a2dab32fc27754c6b3bb7c98cbe0cf93f2221505ef957ac7b1409299c93243c
diff полных построчных проекций — пусто
```

Отменялся batch **с незакрытыми находками** (2 × `CatalogChange(proposed)`,
items в `processing`) — то есть худший случай, а не пустой run.

**Инвариант с зубами.** Проверено, что отменённый batch не может «дострелить» в
каталог даже с одобрением модератора: `review → approved` проходит, но
`apply_catalog_change` под блокировкой перепроверяет статус run и отказывает —
`invalid / run_not_running`, item → `failed`, отпечаток не изменился.
Дополнительно отменённый batch отвергает и вход, и выход: import → EXIT=1,
export → EXIT=1, finalize → EXIT=1.

## 7. Негативная матрица — сводка

Пройдено 17+ сценариев. **Каталог не изменился ни в одном** (отпечаток
проверялся после каждого).

- **EXIT=1, `CommandError`:** битый JSON; нарушение JSON Schema (2 варианта);
  `option_slug` вне pattern; `--run` ≠ `run_id`; несуществующий batch;
  `export_checksum` не совпадает; `taxonomy_hash` не совпадает; changes без
  `identity=matched`; evidence не HTTPS; duplicate `product_ref`; файл вне inbox;
  path traversal; импорт в отменённый batch; finalize без импорта; export
  отменённого run.
- **EXIT=0 при отбраковке item** (каталог не тронут, `CatalogChange` не создан,
  item → `needs_review`): `tool_type` вне манифеста; `product_ref` вне batch;
  `input_hash` не совпадает; товар изменился после export.
- **Дыра:** имя result-файла с `run_id` **не сверяется** — файл под чужим именем
  импортируется успешно (EXIT=0). Guard существует только через опциональный
  `--run`.

**Мутационная проверка (требование «обеими сторонами»).** Guard'ы снимались в
рантайме без правки исходников: JSON Schema, `allowed_options`, identity gate,
сверка `export_checksum`, сверка `input_hash`, сверка `taxonomy_hash` — по
каждому «guard включён» ≠ «guard снят», вердикт GUARD ДОКАЗАН. Отдельно
подтверждена **эшелонированность**: снятие файлового слоя не открывает путь в
каталог — срабатывает item-уровневая пересверка. Параллельно проверено на
уровне pytest: искусственное снятие проверок роняет
`test_import_rejects_unknown_option` и `test_import_rejects_changed_input_hash`.

## 9. Отклонения (G1–G6)

| ID | Суть | Критичность для ступени 2 |
|---|---|---|
| **G1** | Имя result-файла не сверяется с `run_id`; guard только через опциональный `--run` | **Средняя** — на реальных данных перепутанные файлы двух batch импортируются молча |
| **G2** | Повторный export не побайтово идентичен (`exported_at`); детерминирован только `checksum` | Низкая — формулировку приёмки привести к «checksum-детерминизм» либо убрать `exported_at` из файла |
| **G3** | Нет management-команды отмены run — только ORM-переход статуса | **Средняя** — rollback-процедура пилота не воспроизводима инструментом |
| **G4** | Item-ошибки дают EXIT=0; отбраковка видна только в `stats.errors` | Низкая при dry-run; растёт к ступени 3 (CI по коду выхода не заметит) |
| **G5** | `review_catalog_change` не проверяет статус run (approve возможен в отменённом) | Низкая — apply всё равно блокирует; стоит решение «запретить review вне running» |
| **G6** | `taxonomy_hash` очереди = `b357be60…` (DB-order), не canonical `fc13be78…` | Информационно — семантика разная и обе нужны; риск путаницы в отчётах пилота |

## 10. Что осталось незакрытым

1. **Шаги 3–4 скилла `catalog-research` (identity gate + web research) не
   исполнялись** — на фиктивных товарах невозможно в принципе, имитация
   означала бы выдуманные evidence (прямой запрет скилла). Ступень 2 будет
   **первой** проверкой этой части контура — и именно там основной риск
   (галлюцинация evidence, ложный identity match).
2. Схема `catalog_research_result_v1.json` покрыта не целиком: не проверялись
   `maxItems` (items/changes/evidence), лимит файла 10 МБ, все пять значений
   `source_type`, `source: "llm"`.
3. Модерационный UI (CR-13) не проверялся — модерация выполнялась вызовом
   `review_catalog_change`.
4. Метрики/observability (CR-14) не трогались.
5. G1–G6 не исправлялись: правки контура — отдельное решение владельца.

## 11. Требует решения владельца

### 11.1 Калибровка перехода к ступени 2 (real batch 10, только dry-run)

Предлагается на утверждение, **не исполнено**:

**Считать достаточным основанием для ступени 2:**

1. цикл пройден на синтетике с EXIT=0 на каждом шаге — **выполнено**;
2. инвариант отмены доказан отпечатком до/после, включая отказ apply по
   отменённому batch — **выполнено**;
3. негативная матрица пройдена, каталог не изменён ни в одном сценарии —
   **выполнено**; guard'ы доказаны мутационно — **выполнено**;
4. regression без третьего падения — **выполнено**;
5. **решение по G1** (обязательность `--run` либо сверка имени файла) —
   предлагается закрыть **до** ступени 2 хотя бы на уровне runbook: на реальных
   товарах перепутанный файл уже имеет цену;
6. G4 можно отложить до ступени 3, если ступень 2 идёт строго dry-run и
   результат читается человеком, а не CI;
7. G2, G3, G5, G6 — не блокируют ступень 2; требуют решения до ступени 3
   (findings + модерация на реальных товарах).

**Отдельно требуется явное GO на то, чего ступень 1 проверить не могла:**
ступень 2 обязана включать **ручную сверку evidence по каждому из 10 товаров** —
это первая и единственная защита от галлюцинации источников, а автоматического
guard'а на достоверность evidence в контуре нет (проверяется только схема URL и
HTTPS).

### 11.2 Организационное: две параллельные ступени в одной рабочей копии

Ступень фактически исполнялась **двумя окнами одновременно** в общей рабочей
копии и общей песочнице `proff58_phase8`: оба независимо создали одноимённую БД,
одинаковых синтетических товаров и писали в общий `var/catalog-processing/`.
Файл протокола был перезаписан вторым окном (содержимое сведено, ничего не
потеряно — оба набора улик отражены и совпали до последнего хэша).

Выводы обоих окон **независимо сошлись** — это, парадоксально, усиливает
доказательство. Но как процесс это дефект оркестрации: при менее удачном
совпадении два окна могли уничтожить артефакты друг друга.
**Рекомендация:** не запускать две ступени Phase 8 параллельно; если запускается —
имя песочницы и каталог артефактов задавать уникальными per-window.

## 12. Коммиты

**Локальных коммитов не создано — намеренно.** Обоснование:
ни один отслеживаемый файл не изменён (коммитить в коде нечего);

двух окон одновременно, и коммит затянул бы в историю чужие незавершённые файлы.

Безопасная команда фиксации, если владелец решит иначе, — в §11.6 протокола.
