# TT-05 · Phase 8, ступень 3 — real batch 20, findings + ручная модерация
# Проект «Профессионал», ветка dev. Общение только на русском. Одна ступень = одно окно.

## КОНТЕКСТ

Ступени 1 (5 фиктивных cases) и 2 (10 реальных, строго dry-run) выполнены и приняты.
Что установлено и не требует перепроверки:

- контур работает end-to-end, инвариант «отмена batch не меняет каталог» доказан хэшем;
- негативная матрица 17+ сценариев, мутационные пруфы 6/6;
- **`--commit` на ступени 2 не выполнялся**, каталог не менялся;
- главный результат ступени 2: 9 из 10 товаров упирались в catch-all `izm-analizatory`,
  потому что типа «ареометры» в словаре не было.

**Что изменилось с тех пор — словарь вылечен:**

- заведён тип `izm-areometry` (TT-01), идентичность словаря `524d4e31…`;
- на стенде и локально: **329 опций, 329 уникальных slug**, `reconcile` → `blocking = 0`;
- legacy-слуги переименованы, дубль `steplery` устранён, `sort_order` выровнен;
- локальная БД обновлена из staging — числа сопоставимы.

## ЗАДАЧА

Прогнать **20 реальных товаров** через полный цикл, довести findings до модерации
и оценить качество на здоровом словаре.

Цикл: `catalog_queue_create` → `catalog_queue_export` → обработка скиллом
`catalog-research` → `catalog_queue_import --run <run_id>` → модерация → `status` →
`finalize`.

### Отбор — стратифицированный, это обязательное изменение

На ступени 2 критерий «первые 10 по id» дал 9 из 10 товаров одного семейства
(ареометры), и замер качества измерял не матчер, а дыру в таксономии.

Теперь: **стратификация по категориям** — товары без `tool_type` из разных разделов
каталога, чтобы выборка отражала реальное разнообразие. Критерий предложить,
обосновать и **записать дословно**, чтобы выборка воспроизводилась. Cherry-pick
запрещён.

### Ручная сверка evidence — обязательна на этой ступени

На ступени 2 она была отложена по решению владельца, потому что там был строгий
dry-run. Здесь findings идут в модерацию и далее могут попасть в каталог, поэтому:

- **по каждому из 20 товаров** проверить evidence: ведут ли ссылки на реальные
  страницы, относятся ли они к этому товару, подтверждают ли предложенный тип;
- автоматического guard'а на достоверность источников нет — проверяется только HTTPS
  и формат URL, всё остальное на глазах;
- результат свести в таблицу «товар → предложенный тип → evidence → подтверждено да/нет».

### G1 закрыт процедурно

**При каждом вызове импорта обязателен `--run <run_id>`.** Имя файла с batch не
сверяется (это известный дефект G1, решение владельца — закрыть процедурно, кодом не
чинить). В протоколе показать каждую команду импорта целиком.

## ЧТО СЧИТАЕТСЯ РЕЗУЛЬТАТОМ

Не «сколько типов предложено», а **насколько контур пригоден к применению**:

- сколько предложений верны, сколько ошибочны, сколько ушли в `needs_review` и почему;
- какие ошибки контур сделал бы, если бы применял — с разбором причин;
- хватает ли модерации, чтобы эти ошибки поймать.

## APPLY — ТОЛЬКО ПО ОТДЕЛЬНОМУ РЕШЕНИЮ ВЛАДЕЛЬЦА

Довести findings до состояния «одобрено и готово к применению» можно; **само применение
к каталогу — не в этой ступени**. Если по итогам сверки покажется, что applying
оправдан, вынести это владельцу отдельным вопросом с числами.

Если apply всё же будет разрешён отдельным сообщением — только по гейт-циклу:
pg_dump, снимок отката (контур отката из H5/H6 к этому готов), post-audit.

## ГРАНИЦЫ

- каталог не менять без явного разрешения; отпечаток неприкасаемых полей до и после —
  обязателен в любом случае;
- контур `tool_type` не трогать: matcher, ruleset v2, applied corpus, манифест,
  артефакты гейта;
- новые типы в манифест не добавлять — продуктовое решение владельца;
- глобальные команды (`enrich_attributes` без `--path`, `rebuild_attrs_cache`) запрещены;
- staging трогать только read-only, если понадобится; write — по отдельному GO;
- push и PR — только по явной просьбе владельца;
- **перед любой работой с GitHub** — сначала `git fetch gitlab --prune` и сверка
  `origin/dev` с `gitlab/dev`;
- рабочая копия общая: чужие изменения не откатывать, `git add` точечными путями;
- regression — на отдельной БД (`--create-db` + свой `DATABASE_URL`), `-p no:pylama`,
  без длинных немых команд: писать вывод в файл и показывать прогресс, иначе сторожевой
  таймер снимет окно (так уже было).
- **ступень 4 (batch 50) не начинать.**

## ПРИЁМКА
