**Проект:** «Профессионал» (Django + DRF, каталог электро/ручного инструмента).
**Контур:** детерминированный rules-engine распознавания `tool_type` для товаров из 1С.
**Стадия:** H5 «reverse migration hardening».
**Дата:** 2026-07-27. **Ветка:** `dev`. **Статус: ВЫПОЛНЕНА ПОЛНОСТЬЮ.**

## 1. Итог одной строкой

У контура появился обратный путь: применённые `tool_type` откатываются командой по
паре снимков с conflict-guard'ом и встроенным post-audit, а понижение версии словаря
`N → N-1` имеет read-only план, fail-closed блокирующий любой неоднозначный откат.
81 новый тест, 40 негативных сценариев, 12 guard'ов подтверждены обеими сторонами,
end-to-end выполнен на реальном манифесте из 328 опций.

## 2. Зачем стадия существовала

Контур был односторонним. Форвардный seed `load_tool_types` создаёт недостающие опции
и **никогда не удаляет** — значит опция, исчезнувшая из манифеста, оставляла товары
висеть на несуществующей записи. Применённые предложения откатывались только pg_dump'ом,
то есть вместе со всеми чужими изменениями, случившимися после записи. H5 заменяет
«политику отката в документе» на проверяемую процедуру.

## 5. Архитектура: два контура, один исполнитель записи

| Контур | Модуль | Команды |
|---|---|---|
| Откат применённого `tool_type` | `apps/catalog/tool_type_rollback.py` | `catalog_tool_type_snapshot`, `catalog_tool_type_rollback` |
| Понижение версии словаря | `apps/catalog/taxonomy_reverse.py` | `catalog_taxonomy_downgrade` |

Понижение версии **не имеет собственной ветки записи**: перенос товаров с исчезающих
опций оно исполняет через контур отката. Второй, менее строгой реализации записи не
существует — семантика конфликта и атомарности общая.

## 6. Ключевое решение: пара снимков вместо одного

`--from` — состояние, ожидаемое в БД сейчас; `--to` — цель отката.

| live | решение |
|---|---|
| `== to` | `noop` (идемпотентность повторного запуска) |
| `== from` | `write` |
| ни то, ни другое | **`conflict`** |

По одному снимку «до» отличить откатываемое изменение от чужого изменения поверх
**невозможно** — такой откат всегда молчаливая перезапись. Обходного флага нет: без
`--from` conflict-детекция невозможна, поэтому оба аргумента обязательны.

Снимок — канонический артефакт той же рецептуры, что release manifest H3
(byte-stable), с явными `product_id`, восстанавливаемым `attrs_cache.tool_type`,
`live_taxonomy_identity_hash` (дрейф словаря → отказ) и `canonical_hash`.

## 7. Главное доказательство: end-to-end на реальном манифесте

Взят настоящий `tool_type_taxonomy.v1.json` (328 опций); построена пара «N=2 → N=1»,
где в N-1 нет ровно тех четырёх опций с нулевым usage, которые H4 оставил как
тестовый материал (`hoz-schetchiki`, `metchiki`, `osnastka-rezbonarez`, `plashki`).

| Проверка | Результат |
|---|---|
| seed реального манифеста | live identity == `fc13be78…`, 328 опций |
| план понижения | `feasible=True`, `keep=324`, `drop=4`, `blocked=0` |
| выполнение drop | 328 → 324 опции |
| **приземление на цель** | live `taxonomy_identity_hash` == identity манифеста N-1 |
| товар на исчезающей опции | `feasible=False`, `orphaned_products`, опция не удалена |
| полная процедура с remap | товар переехал, `attrs_cache` обновлён, post-audit PASS, live identity == identity N-1 |

Строка «приземление на цель» — суть стадии: после процедуры живой словарь по
identity-рецепту H1 совпадает с целевым манифестом, то есть БД действительно
приземлилась на предыдущую версию.

## 12. Решение владельца: `option_uid` — вынесено, не принято

**Контекст.** Reverse-map машинно не может отличить «slug переименовали» от «одну
опцию удалили, другую добавили». Отсюда весь дизайн: remap только явный, решением
владельца. H4 показал развязку на метаданных; H5 уточняет: identity считается от пары
`(slug, value)`, поэтому и переименование slug, и смена `value` рвут binding
замороженного gate-sample и release manifest.

**Вариант A — ввести сейчас.** Схема + uid для 328 опций, `manifest_version` 1 → 2,
решение по рецепту identity (включить uid → сменить `fc13be78…` и **перевыпустить
gate-sample, labels и release manifest**, то есть повторить H4; не включать → половина
выгоды теряется), миграция `AttributeOption` + backfill, миграция потребителей, тесты.
Цена — стадия масштаба H1 плюс повтор H4. Выгода сегодня — **нулевая**:
`manifest_version` = 1, переименований и удалений не было.

**Вариант B — зафиксировать как долг.** Цена сегодня ноль; тот же объём позже, но
дешевле — процедура понижения версии уже готова. Риск: долг без триггера не возвращается.

**Рекомендация стадии — вариант B с жёстким триггером:**
> **РЕШЕНИЕ ВЛАДЕЛЬЦА, принято 2026-07-27:** вариант **B с жёстким триггером плюс
> закрытие форвардного reslug через `legacy_aliases`**. `option_uid` сейчас не
> вводится; `legacy_aliases` делаются потребляемыми в seed и reverse-map — это
> отдельная задача, планируемая **после `WAVE 7.1 ACCEPTED`**, чтобы не менять
> дифф волны на ревью. От смены `value` алиасы не защищают: там по-прежнему нужен
> `option_uid`, и триггер долга остаётся в силе.


> До первого переименования или удаления slug в манифесте вводится `option_uid`
> **либо** переименование slug запрещается процедурно (только `add` + deprecated,
> без reslug).

Обоснование: вариант A переоткрывает контракт, который волна только что заморозила и
защитила CI, при нулевой сегодняшней выгоде. Момент, когда ошибка варианта B
материализуется, контролируем — он проходит через манифест, ревью и
`catalog_taxonomy_reconcile`.

**Что остаётся незакрытым явно.** H5 закрыл обратный путь. Форвардный reslug — дыра:
`load_tool_types` при переименовании создаст новую опцию и оставит старую (no-delete),
товары останутся на старой. Отдельная задача, в ТЗ H5 не входила. Дешёвая
альтернатива полному uid для случая переименования — сделать существующие
`legacy_aliases` (сегодня audit-only) потребляемыми; от смены `value` это не защищает.

## 13. Требует решения / действий вне стадии

1. **`legacy_aliases` как потребляемый механизм** — решение владельца принято (§12), реализация вне scope H5, планируется после `WAVE 7.1 ACCEPTED`.
2. **Форвардный reslug** — закрывается пунктом 1; до его выполнения дыра остаётся.
3. **P1 из H4** (полный pytest модифицирует `data/attribute_rules.json`) — в этом окне

4. Release-evidence в `apps/catalog/tests/fixtures/` — вопрос из H3, H5 его не трогал.
