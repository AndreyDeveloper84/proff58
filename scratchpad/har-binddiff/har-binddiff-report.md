## 1. Что было сломано

`apps/catalog/management/commands/load_attributes.py`, метод `_apply`, ветка привязок:

```python
CategoryAttribute.objects.update_or_create(
    category_id=row["category_id"], attribute=attrs[row["attribute"]],
    defaults=dict(is_filter=..., is_seo_facet=...),
)
```

Цикл шёл по всем строкам плана, кроме `skip`. Для **новой** привязки `defaults` уместны.
Для **существующей** `update_or_create` записывал `is_filter`/`is_seo_facet` из файла правил
поверх текущих — молча, побочным эффектом загрузки схемы атрибутов. Настройка фасетов —
решение владельца каталога (правится руками и `catalog_seed_tool_type_filters`), и она
затиралась тем, что кто-то догрузил словарь характеристик.

План при этом расхождение уже считал (`changes` у строки привязки, `action="update"`), но
это не было отдельным решением: `update` исполнялся автоматически, наравне с `create`.

## 2. Что сделано

### Новый флаг: `--allow-binding-flag-updates`

Имя выбрано по стилю уже существующих в этой команде. У команды два семейства ключей:

* `--strict-*` (`--strict-bindings`, `--strict-live-categories`) — **ужесточают** проверку,
  превращают предупреждение в фатальную ошибку;
* `--allow-*` (`--allow-ambiguous`) — **разрешают** команде самостоятельное действие,
  которое по умолчанию запрещено.

Изменение флагов существующей привязки — это разрешение на действие, а не ужесточение
проверки, поэтому семейство `--allow-*`. Объект действия назван полностью
(`binding-flag-updates`), чтобы ключ нельзя было спутать с `--allow-ambiguous`, который
касается разрешения имени категории, а не содержимого привязки.

### Поведение

| Ситуация | Было | Стало |
|---|---|---|
| привязки нет | `create` с флагами из правил | без изменений: `create` с флагами из правил |
| привязка есть, флаги совпадают | `keep`, но запись всё равно шла | `keep`, записи нет |
| привязка есть, флаги расходятся, без флага-разрешения | `update` — молча перезаписывалось | `keep`; флаги сохраняются; расхождение в `changes` + `suppressed` (`reason = binding_flag_update_not_authorized`) |
| привязка есть, флаги расходятся, с `--allow-binding-flag-updates` | — | `update`, флаги применяются |
| категория не разрешена | `skip` | без изменений: `skip` |

Диф считается **всегда**, независимо от разрешения — владелец видит расхождение даже тогда,
когда оно не применяется. В плане это:

* `bindings[].current` / `bindings[].target` — текущие и планируемые значения обоих флагов;
* `bindings[].changes` — `[{"field": "is_filter", "from": false, "to": true}, …]`;
* `bindings[].suppressed` — те же записи с причиной, если разрешения нет;
* `summary.bindings.flag_diff` — **число существующих привязок с расхождением**, считается
  независимо от флага-разрешения (это и есть масштаб проблемы);
* человекочитаемая сводка: строка `существующих привязок с расхождением флагов: N` плюс
  построчно `= привязка «Категория» → attr: is_filter: False → True (сохранено, нет
  --allow-binding-flag-updates)`; при разрешении маркер меняется на `~` и хвост убирается.

### Apply

`_apply` теперь исполняет только `create` и `update`; `keep` и `skip` не пишут ничего.
`create` переведён с `update_or_create` на `get_or_create`: если привязка появилась между
построением плана и записью, это уже существующая строка, и её флаги тоже не должны
перезаписываться молча.

возникает не в момент загрузки схемы, а позже, когда владелец правит фасеты.

## 5. Риски и что осталось

1. **Флаг ничего не чинит задним числом.** Если чьи-то флаги уже были затёрты прежними
   прогонами, восстановить их этот флаг не может — он только не даёт затирать дальше.
   Восстановление, если понадобится, — отдельная задача со снимком.
2. **Изменение семантики `keep` в отчётах.** Строка привязки с расхождением теперь
   `keep`, а не `update`. Любой внешний потребитель JSON-плана, который считал «сколько
   изменится» по `summary.bindings.update`, увидит меньшее число; правильный счётчик
   масштаба теперь `summary.bindings.flag_diff`. Известных внешних потребителей в репозитории
   нет, но это единственное место, где формат плана изменился несовместимо.
3. **`create` переведён на `get_or_create`.** Если привязка возникла между планом и записью,
   её флаги останутся чужими, а план будет утверждать `create`. Это намеренно (правило
   владельца сильнее отчётности), но post-audit после боевого apply стоит сверять по факту
   в БД, а не по плану.
4. **Замер сделан на состоянии стенда 2026-08-11.** Число `flag_diff` не константа: оно
   станет ненулевым ровно тогда, когда владелец настроит фасеты вручную. Перед боевым apply
   `load_attributes` замер нужно повторить.
5. **Скоуп у команды узкий.** Из 154 привязок стенда правила покрывают 73; остальные 81
   команда не трогала и не трогает — ни раньше, ни теперь.
