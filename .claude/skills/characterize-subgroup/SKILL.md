# Характеризация подгруппы каталога

Воспроизводимый процесс: для одной 1С-подгруппы отделить аксессуары/подтипы и
добавить извлекаемые характеристики. По нему сделаны Буры/Коронки/Свёрла
(#210–212), хвост Оснастки (#214), типы Электроинструмента (#205).

**Принцип:** правила — это ДАННЫЕ (`data/*.json`), движок не трогаем. Всё, что
лежит на проде (фасеты/EAV/SEO), правится осторожно и проверяется на staging.

## Инструмент-измеритель

`./manage.py analyze_subgroup "<Имя подгруппы>" [--spec spec.json] [--examples N]`
— read-only, считает на `data/catalog_fixed.json`:

1. **Состав** — частоты первых слов (видны подтипы/аксессуары).
2. **Сплиты** — распределение + сколько товаров с «core»-первым словом попало в
   сплит (подсказка: подтип «бур садовый» — ок; аксессуар «адаптер» с core-словом
   — значит ключ жадный, уточнить).
3. **Покрытие атрибутов** — % CORE-товаров + топ-значения + примеры промахов.

Цикл: пишешь `spec.json` → гоняешь → правишь ключи/regex до 0 настоящих ложных и
максимального покрытия → переносишь в реальные правила.

## Шаги

### 1. Анализ
`analyze_subgroup "<Подгруппа>"` без spec — посмотреть состав. Определить:
- целевой тип (доминирующее первое слово, напр. «бур»/«коронка»/«сверло»);
- подтипы и аксессуары (адаптеры, удлинители, наборы, держатели, переходники).

### 2. Дизайн сплитов (subgroup-override)
Аксессуары/подтипы → отдельные tool_type через **скоуп по подгруппе**. Правило в
`data/tool_type_rules.json`, в категории `"Оснастка и расходники"`:

```json
{
  "tool_type": "Оснастка для буров",
  "slug": "osnastka-burov",
  "subgroup": "Буры",
  "match_keywords": ["удлинитель для бура", "адаптер", "державка"],
  "source": "name_keywords"
}
```

Скоуп обязателен: категория-широкий ключ ворует товары соседних подгрупп.
Гонять `--spec` до **0 настоящих ложных** (см. подсказку выше).

### 3. Дизайн характеристик
Запись tool_type в `data/attribute_rules.json` (поле `category` — для привязки
к фасетам через `load_attributes`):

```json
{
  "tool_type": "bury",
  "category": "Оснастка и расходники",
  "attributes": [
    {"slug": "diameter", "name": "Диаметр", "kind": "number", "unit": "мм",
     "source": "regex", "priority": 40, "is_filter": true,
     "regex": ["(?:^|\\s)(\\d{1,2}(?:[.,]\\d)?)\\s*[х*x]\\s*\\d"]},
    {"slug": "shank_type", "name": "Тип хвостовика", "kind": "select",
     "source": "keyword", "priority": 30, "is_filter": true, "is_seo_facet": true,
     "options": [
       {"value": "SDS-max", "slug": "sds-max", "keywords": ["sds-max"]},
       {"value": "SDS-plus", "slug": "sds-plus", "keywords": ["sds-plus", "sds+"]}
     ]}
  ]
}
```

- **Переиспользуй slugs** между типами для единых фасетов: `diameter`, `length`,
  `shank_type`, `purpose`, `material`. Один slug = один Attribute; опции/regex
  задаются per-tool_type. У общих select-опций держи одинаковые `value`.
- `number`: `m.group(1)` — значение; первый сработавший regex выигрывает (порядок!).
- `select`: первая опция со совпавшим ключом выигрывает (порядок!). Более
  специфичное — раньше (turbo раньше solid; brushless раньше brushed).
- Слабые атрибуты (<~30%) можно не вносить или внести как фасет с пометкой.

### 4. Тесты
- `apps/catalog/test_tool_type.py` (класс `RealRulesRegressionTests`): сплит на
  реальном `tool_type_rules.json` + негативы (целевой тип не уходит в сплит).
- `apps/catalog/test_attribute_extract.py` (фикстура `rules`): извлечение
  атрибутов на реальном `attribute_rules.json`.

### 5. Проверка
Перед пушем прогнать **то же, что CI** (`.github/workflows`):
```bash
ruff check .                              # lint (CI падает на B905 zip без strict= и пр.)
black --check apps/ data/                 # форматирование (только Python, не .md/.json)
python3 -m pytest apps/catalog/ -q        # тесты (нужен Postgres; см. скилл reliability/devops)
```
Симуляцию покрытия — через `analyze_subgroup --spec`. `ruff` обязателен: одного
`black` мало — CI делает `ruff check .` отдельным шагом (на нём упал #215).

### 6. PR
Ветка от свежего `origin/dev`, один коммит на подгруппу, PR в `dev`. В описании —
сплит, покрытия, runbook выката. НЕ создавать PR без запроса пользователя.

### 7. Выкат на staging (после мержа)
```bash
DC="docker compose -f docker-compose.prod.yml"
$DC exec -T web python manage.py load_attributes    # новые атрибуты/опции + привязки
$DC exec -T web python manage.py load_tool_types    # опции новых tool_type
$DC exec -T web python manage.py enrich_tool_type   # сплит (переносит товары)
$DC exec -T web python manage.py enrich_attributes  # извлечение характеристик
$DC exec -T web python manage.py attribute_coverage --tool-type <slug>
$DC exec -T web python manage.py shell -c "from django.core.cache import cache; cache.clear()"
```

## Грабли (проверено на практике)

- **«комплект»** ловит «боекомплект» — для наборов используй «набор».
- **«зенкер»** ловит «сверло с зенкером» (это сверло) — бери «зенковк».
- **«переходник»** в Коронках — 22 из 25 это настоящие коронки «+переходник»;
  жадные ключи аксессуаров уточняй формой «...для» («хвостовик для», «адаптер для»).
- **Порядок правил** в `priority_keyword` решает: широкий ключ (напр.
  «аккумулятор») держи ПОСЛЕДНИМ, иначе перехватит («газонокосилка аккумуляторная»).
- **Переход assigned→recategorize/moderation**: `enrich_tool_type` снимает старый
  tool_type-PAV и чистит attrs_cache (см. `_prune_tool_type`) — повторный прогон
  чистит застрявшие товары.
- `attribute_coverage` требует, чтобы у tool_type были атрибутные правила; для
  «чистых» типов (батареи, наборы) считай по опции напрямую через shell.
